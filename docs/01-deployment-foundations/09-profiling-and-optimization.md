# 09 性能分析：从瓶颈假设到对照结论

[返回总目录](README.md) · [上一章](08-benchmark-and-quality.md) · [下一章](10-troubleshooting.md)

## 1. 先判断慢在哪个阶段

端到端延迟可概念性分为接入、排队、预处理、Prefill、Decode、后处理与传输。流式传输可能和计算重叠，不能把所有计时项无条件相加。先用客户端时间、服务日志与队列指标找出占比，再选择 profiler。

同样是 TTFT 高，可能是长 prompt 计算，也可能是服务没有空槽位、首次图编译、图片解码、CPU 分词或代理缓冲。Decode 慢也可能来自 CPU 卸载、KV 访问、通信、线程竞争和温控。不能根据一个低 tokens/s 数字直接选优化参数。

## 2. 用带宽与算力建立初步判断

简化下，一轮计算耗时满足：

```text
T_iteration ≥ max(实际工作量 / 可持续计算吞吐,
                  实际搬运字节 / 可持续内存带宽)
```

这只是理想下界，不包含所有调度、同步和传输；实际通常更慢。厂商峰值 FLOPS 与带宽也不是该模型可持续达到的数值。

**假设算例，非实测：**单请求 Decode 每轮确实需要从某内存层读取 16 GiB 权重，实际可持续带宽为 200 GiB/s，则仅这部分读取就需约 80 ms，对应不超过约 12.5 token/s 的简化上限。它忽略 KV、计算与通信，不能拿来预测某张卡的真实速度。若有缓存、MoE、不同量化或多请求共享权重，前提也改变。

Dense 模型矩阵投影的每 token 工作量常以约 2P 浮点操作作量级估算，P 是参数量；Attention、输出层、架构与实现会带来差异，MoE 应按激活计算分析。Prefill 将多个 token 组织成矩阵运算，计算复用较强；单请求 Decode 对权重搬运更敏感。batch 增大后共享权重读取，可能提高总吞吐，但也增加计算、KV 与排队。

## 3. GPU Util 高低分别能说明什么

GPU utilization 通常是采样窗内某类设备活动的比例，不直接表示 Tensor Core 效率、内存带宽利用率或应用达标率。许多小 kernel 连续运行也可能让它很高，通信等待也可能影响观察结果。

利用率低时同时看 CPU、请求队列、token 预算、kernel 时间线和 I/O；利用率高但慢时，继续看计算效率、带宽、同步、KV、热限制和工作量。优化目标不是把利用率强行推到 100%，而是完成更多符合质量与延迟要求的任务。

## 4. 先做低开销采样，再做短时间 profiling

在 NVIDIA Linux 实验中，可另开终端进行如下采样，路径按项目目录调整；Ctrl+C 只结束这个采样进程。

```bash
nvidia-smi \
  --query-gpu=timestamp,index,memory.used,utilization.gpu,power.draw,temperature.gpu,clocks.sm \
  --format=csv -lms 500 \
  > /mnt/workspace/edge-llm-lab/logs/gpu-samples.csv
```

并行观察主机 CPU、RAM、I/O 与队列。例如 Linux 的 `pidstat`、`vmstat`、`iostat` 需相应系统工具包；macOS/Windows/Android 使用各自平台工具。500 ms 可能漏掉瞬间峰值，不能当成严格的内存峰值证明。

只有粗粒度证据指向引擎执行时，再使用 Nsight Systems、Nsight Compute、PyTorch Profiler、rocprof、VTune、Perfetto 或厂商工具。Systems 类时间线有助于区分 CPU 空隙、复制、计算与同步；kernel 级分析关注带宽、占用、指令与矩阵效率。按平台选一个工具先做短请求抓取，避免长时间 profiler 改变整体负载。

阅读 trace 时对齐请求边界。看到 memcpy 要确认数据与方向；看到长 kernel 要确认输入与算子；看到空白先判断是否 CPU、同步、队列或采样遗漏。性能计数器只是支持假设的证据，不是自动生成的结论。

## 5. 优化手段按作用位置选择

| 手段 | 主要作用 | 需要复查的代价 |
| --- | --- | --- |
| 缩短无效上下文 | 减少 Prefill/KV/Attention 工作 | 任务所需信息是否丢失 |
| 权重量化 | 减少权重容量/搬运，改变 kernel | 质量、反量化与计算效率 |
| KV 量化 | 降低状态容量与部分访存 | 长输入质量、后端支持、额外计算 |
| Flash Attention | 减少 Attention 中间数据读写 | 架构、shape、精度与 kernel 路径 |
| batch/microbatch 调整 | 改善执行组织 | 内存峰值、公平性、TTFT/ITL |
| 前缀缓存 | 节省相同前缀 Prefill | 命中率、容量、驱逐与隔离 |
| 推测解码/MTP | 一轮验证后输出多个候选 token | 草稿成本、接受率、质量与内存 |
| 线程/NUMA/卸载调整 | 降低 CPU/跨设备代价 | 带宽竞争、可移植性与系统响应 |
| 限流/副本/路由 | 控制排队与服务容量 | 资源成本、队列与缓存局部性 |

## 6. Flash Attention 与分页 KV 的区别

Flash Attention 通过计算分块和减少大中间矩阵物化，改善 Attention 的 I/O 行为。它不是 Q4 量化，也不意味着把历史 KV 自动压缩。是否明显改善取决于输入长度、批量、模型、后端及旧实现的瓶颈。

分页 KV/PagedAttention 关注状态分块管理与相应访问计算，提高不同长度序列的空间使用效率。两种技术可同时存在，不能拿它们当同一开关。开启 FA 后应从日志与 trace 确认真正生效；如果旧路径已经优化或瓶颈在权重读取，收益可能很小。

实验固定权重、KV 精度、上下文、batch 与输入，比较 on/off；同时检查内存、Prefill、Decode、HTTP 指标和质量。浮点计算顺序改变可能导致输出差异，不应只凭逐字不同判失败，但必须按任务规则确认正确性。

## 7. KV 量化：容量收益与长上下文质量一起看

从 FP16 KV 换到较低精度后，可以为更多历史或并发腾空间，但实际字节包含 scale 与布局，不一定精确减半/减四分之三。支持哪些 K/V 类型、是否依赖 FA、是否有 CPU 回退，需要按版本与后端确认。

建议先保持权重和调度不变，仅改 KV 类型。对短与长历史分别测质量、TTFT、TPOT、峰值内存，再决定是否把节省空间用于更多并发。若同时修改 KV、上下文与并发，就无法解释性能变化来自哪一项。

质量样例应包含长距离引用、数字实体、跨段依赖和实际任务。短闲聊通过不证明长上下文可靠。节省内存是一个结果，更多达标请求是另一结果，两者都要记录。

## 8. 推测解码与 MTP

推测解码先由草稿机制提出若干候选，再由目标模型批量验证，争取每轮提交多个 token。草稿可以来自小模型、模型专用预测头或其他机制，具体支持和统计接受率的定义依实现而定。

简化的收益条件是：`平均每轮提交 token / (草稿时间 + 验证时间 + 管理开销)` 高于原先目标模型的生成速率。接受率高仍可能因为草稿太贵而变慢；接受率低也可能浪费验证计算。额外权重与 KV 还可能使端侧容量不足。

MTP 通常依赖模型与引擎专门支持，不是给任意模型添加同一启动参数。算法在满足其采样验证条件时可以保持目标分布，但具体实现、量化、采样配置和模板仍需质量验收，不笼统保证“输出一定完全一致”。

## 9. CPU、卸载和数据路径优化

CPU 推理先从物理核心附近选择线程数量，再按实际测量调整；同时测试生成与 Prefill 的线程设置。更多线程可能增加同步和带宽争用，端侧还可能抢占 UI 线程。BLAS 改善某些矩阵阶段，不代表逐 token Decode 必然同幅提速。

多 NUMA 主机要让线程与权重/设备尽量靠近；实际效果需看内存分配和设备拓扑。GPU 卸载实验从可运行配置逐档增加，记录每档层数、峰值、复制与延迟。避免用总层数线性推算显存或性能。

数据链路也常值得优化：减少重复分词、避免每次重新加载模型、保持服务常驻、降低无效网络往返、修正代理缓冲。但这些是应用路径优化，应与引擎 kernel 收益分别报告。

## 10. 一个完整的优化实验应怎样叙述

使用下面的顺序，所有结果未测时留空：

1. **现象：**在哪个设备、输入和并发下不达标，指标与原始文件在哪里。
2. **假设：**哪段工作占主导，有哪些日志/trace 支持，还有哪些可能原因。
3. **干预：**只改变一个主要变量，写明实际生效的参数。
4. **对照：**相同负载、多轮交替测量，记录输出长度、质量和资源。
5. **结论：**收益、波动、代价、适用边界，以及是否保留此改动。

改善幅度可写 `(新值-旧值)/旧值`，但延迟下降与吞吐上升要明确方向。接近自然波动的变化不应宣称确定提升；必要时增加重复或报告置信区间。没有改善也是可用结论，它帮助排除错误假设。

**本章产物：**一个能被数据支持或推翻的瓶颈假设、一组对照记录、一份质量/资源回归与明确的接受或撤回决定。
