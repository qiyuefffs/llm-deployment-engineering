# 性能测试：把一次运行变成可比较的结果

**完整工程记录：** [完整压测工具与操作原文](../../engineering/benchmark-tools.md) · [oMLX完整实测](../../engineering/apple-mlx.md)

[总目录](../../SUMMARY.md) · [所属总章：性能优化](../../02-capability-layers/04-memory-performance.md) · [完整CPU实跑](../../practice/first-service/README.md)

## 本章概览

性能测试首先要说清测什么：模型执行速度、单个用户等待，还是服务在多请求下的容量。同一个“token/s”，可能来自引擎、单请求decode或整个HTTP压测窗口。计时边界不同，数字就不能直接比较。

本章按FlowUs中的压测工具总文、GB10突发测试、oMLX并发测试，以及本体系CPU实跑组织。先定义工作负载，再选择工具、保存明细、检查质量，最后解释吞吐和延迟的取舍。

## 1. 先写测试计划，再发请求

测试计划至少包含模型与制品、输入输出长度、并发或到达率、请求数、采样与思考设置、缓存状态、预热、测量范围、错误处理和通过标准。输入长度用匹配tokenizer计算；字符数不能直接代替token数。

例如，本体系CPU实跑计划固定Qwen3-0.6B-Q8_0、4线程、纯CPU、两槽位，c1/c2各4请求、输出上限32。目标是检查脚本链路和观察并发效应，样本量不够支持稳定P99或生产容量结论。先说明目的，就不会把一份教学结果夸大为服务器选型报告。

性能任务可以固定输出长度以比较计算，但必须检查真实usage和结束原因。`ignore_eos`等选项只在服务支持时使用，并应注明它偏离自然结束的业务行为。用于质量的任务应让模型有机会完整回答，两类结果分别保存。

## 2. 三种测量边界

| 边界 | 工具示例 | 回答的问题 |
| --- | --- | --- |
| 引擎执行 | llama-bench、vLLM离线bench | 固定计算负载的基础性能 |
| 本地Pipeline | OpenVINO GenAI等 | 分词、生成等管线开销 |
| HTTP客户端 | vllm bench serve、EvalScope、自写客户端 | 接口、排队、流式和完整请求表现 |

引擎tg高、HTTP吞吐低，不一定是引擎有故障。HTTP增加了模板、请求调度、缓存、队列与客户端开销；负载也可能完全不同。先把边界写到表头，再解释差异。

## 3. 核心指标怎样计算？

设请求发送时间为`t0`，首个有效正文到达为`t1`，流结束为`t2`，输出token数为`N`。客户端TTFT约为`t1-t0`，E2E为`t2-t0`，在`N>1`时，按这种边界估算的TPOT为`(t2-t1)/(N-1)`。结束事件与传输也包含少量开销，应说明测量方式。

流式事件可能一次携带多个token，事件间隔不能无条件当作逐token ITL。本体系小型客户端记录首正文与总耗时，不伪造逐token时间戳。正式工具应查清其ITL采样和聚合定义。

整个测试窗口的输出吞吐是成功请求实际输出token总数除以窗口总时间；请求吞吐是成功完成数除以窗口时间。它们都不同于“各请求token/s的平均数”。失败、超时和重试必须单列，否则快失败也可能让报告显得很好。

百分位必须说明样本量、样本对象和算法。请求级TTFT的P99与所有token间隔的P99不是一回事；4个请求算出的P99没有稳定容量意义。Goodput进一步限制只有同时满足质量和延迟目标的请求才计入有效产出，适合服务验收。

## 4. 先测单实例引擎基线

确认同设备没有另一个模型竞争后运行：

```bash
llama-bench -m artifacts/gguf/Qwen3-0.6B-Q4_K_M.gguf \
  -ngl 0 -t 4 -p 64 -n 32 -r 3 -o json > engine.json
```

保存程序提交、模型摘要、后端、线程、pp/tg长度与重复次数。本体系实际Q8 CPU结果是pp64为319.08±17.26token/s，tg32为69.88±0.22token/s。它们属于不同阶段；不可把pp与tg求平均变成“模型综合速度”。

第一次加载、编译、图捕获和预热与稳定生成分开记录。端侧用户关心首次打开等待，服务工程师还关心长时间运行，两者都值得测。

## 5. 再测 HTTP 并发曲线

先完成正常、流式与异常API检查，再开始压测。vLLM服务示例接续[部署章](../frameworks/vllm-service.md)，保持同一别名、端口与tokenizer：

```bash
for c in 1 2 4; do
  vllm bench serve \
    --backend openai-chat --base-url http://127.0.0.1:8001 \
    --endpoint /v1/chat/completions \
    --model Qwen3.6-35B-A3B-FP8 \
    --tokenizer /srv/models/Qwen3.6-35B-A3B-FP8 \
    --dataset-name random --random-input-len 2048 \
    --random-output-len 128 --num-prompts 100 \
    --max-concurrency "$c" --request-rate inf --seed 42 \
    --save-result --save-detailed --result-dir "results/c${c}"
done
```

这是新增测试计划，没有补造运行成绩。先从小并发运行，错误或资源压力出现时停止扩展，检查日志与容量。各档使用相同样本量与任务，正式比较还应多轮运行，控制热状态并观察方差。

vLLM bench的模型别名用于请求，tokenizer路径用于构造和计数，两者用途不同。使用某版本参数前先保存`vllm bench serve --help`；旧`benchmark_serving.py`脚本与新CLI不能随意混搭。

### 使用 EvalScope 的同类测试

作者oMLX工程使用EvalScope1.7.0。同一工具也能测兼容HTTP服务。独立环境安装`evalscope[perf]==1.7.0`后，先查看perf帮助；示例仍接上述服务：

```bash
evalscope perf \
  --parallel 1 2 4 --number 100 100 100 \
  --url http://127.0.0.1:8001/v1/chat/completions \
  --model Qwen3.6-35B-A3B-FP8 --api openai \
  --dataset random --min-prompt-length 2048 --max-prompt-length 2048 \
  --min-tokens 128 --max-tokens 128 \
  --tokenizer-path /srv/models/Qwen3.6-35B-A3B-FP8 --stream
```

工具默认采样、输出目录与参数以该安装版本为准，运行前保存完整配置。不要用两种工具各自默认的数据集和计时方式比较框架优劣。

## 6. 并发与到达率是不同实验

固定并发通常采用闭环：一个请求结束再补上一个。开放到达率则按计划时间发起请求，服务落后时队列可能持续增长。到达率inf表达尽快发起，结合客户端并发上限决定实际发出方式；没有上限时会形成突发。

作者GB10历史200请求突发平均TTFT约148秒，说明该负载的排队很重。它不代表模型计算首token要148秒，也不能据此估计轻载延迟。应补充有限并发和逐步到达率，再观察队列是否稳定。

## 7. 两组真实并发结果怎样分析？

本体系CPU结果如下。每组4请求、128输出token，原始文件见[HTTP汇总](../../practice/first-service/results/2026-10-18-windows-cpu/http-summary.json)：

| 客户端并发 | HTTP成功 | 输出吞吐 | 平均TTFT | 平均E2E |
| --- | --- | --- | --- | --- |
| 1 | 4/4 | 53.18token/s | 131.16ms | 601.56ms |
| 2 | 4/4 | 82.12token/s | 217.49ms | 778.99ms |

并发2增加了总产出，同时平均请求等待变长。这就是需要画吞吐与延迟两条曲线的原因。该小样本只说明本次观察，不能说明长时间稳定性或所有并发趋势。

oMLX历史测试也出现相同方向：c1/c2/c4输出吞吐29.38/41.11/55.15token/s，平均请求延迟7.582/10.257/13.459秒。但请求数分别20/10/10，缓存与原始文件不全，只能保留为历史参考，不能与CPU数据混排成硬件排名。

## 8. 同时观察资源与质量

NVIDIA可在独立终端按秒采样显存、计算利用率、温度和功耗，CPU与统一内存平台记录RSS、可用内存、swap、频率和热状态。进程结束时停止自己启动的采样器，标明采样频率；一秒采样可能漏掉很短的峰值。

服务指标补充活动请求、排队请求、KV占用、命中、抢占/重算、错误和引擎运行状态。客户端TTFT高而计算利用率低时，还要排查客户端、tokenizer、网络和队列，不能立即增加GPU预算。

质量检查至少确认完整答案、JSON合法性和典型任务。速度提高却输出乱码、错误或只剩思考，应判为质量未达标。性能报告的通过标准由项目目标决定，不由这次最快结果倒推。

## 十、oMLX完整并发结果与工作点选择

原空间中oMLX实测使用DeepSeek-V4-Flash-4bit、EvalScope1.7.0，输入目标128、输出上限256。配套操作记录的设备为M3 Ultra、512GB统一内存；性能页未保留完整依赖锁与cache状态，因此阅读时同时看服务条件与数字，不把热命中的首token代表首次请求。

### 10.1 原始三档成绩

| 客户端并发 | 请求数 | 输出吞吐token/s | 平均E2E秒 | P99 E2E秒 | 平均TTFT ms | 平均TPOT ms |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 20 | 29.38 | 7.582 | 8.58 | 25.0 | 34.2 |
| 2 | 10 | 41.11 | 10.257 | 12.8 | 3.2 | 47.5 |
| 4 | 10 | 55.15 | 13.459 | 19.34 | 3.7 | 69.8 |

c4的总输出吞吐约为c1的1.877倍，平均请求时间约为1.775倍。它说明这次负载中吞吐与单请求等待存在取舍。c2/c4的TTFT显著小于c1，可能与预热、缓存、短输入和运行顺序有关，资料不足以单独证明原因。

原P99保留供核对，但10/20条请求不足以稳定描述尾部。要判断交付容量，应增加持续时间和请求数、多轮复测，并确认样本构成、缓存和功耗状态一致。

### 10.2 一份更便于复测的计划

先完成模型列表、短题与SSE检查，固定EvalScope1.7.0、模型tokenizer和prompt。再让每档使用相同100条输入，保存不同结果目录；以下是补齐后的测量计划，表中历史数字不是这套新计划的结果：

```bash
evalscope perf \
  --parallel 1 2 4 --number 100 100 100 \
  --url http://127.0.0.1:8000/v1/chat/completions \
  --model DeepSeek-V4-Flash-4bit --api openai \
  --dataset random --min-prompt-length 128 --max-prompt-length 128 \
  --min-tokens 256 --max-tokens 256 \
  --tokenizer-path /srv/models/DeepSeek-V4-Flash-4bit --stream
```

模型ID应以`/v1/models`为准。工具的输出保存选项与随机数据生成行为按`evalscope perf --help`核对，并将实际版本及解析配置保存。随机长度约束不是自然业务文本；质量题单独测。

先测每档冷输入，再测固定前缀热输入。只想比较并发时，不要顺便更换模型量化、max_tokens、cache预算和模板。每轮后保存内存、swap、温度与后台任务，解释异常样本。

### 10.3 根据约束选工作点

如果应用只有单人交互，c1的平均E2E更有参考价值；如果允许多人排队且更看重总产出，可继续评估c2/c4。真实决策要先定延迟门槛，再计算满足门槛的完成量，而不是先挑55.15这个最大数字。

假设教学上以平均E2E不高于11秒筛选，上表c1/c2落在范围内，c4不在；再选c2需要额外检查尾延迟和质量。平均值通过不代表每个用户都能在11秒内完成，这就是需要请求级数据和P95/P99的原因。

## 十一、GB10的200请求突发：怎样把等待拆开

Qwen FP8历史服务max-num-seqs4，而客户端尽快发200请求。原总时间297.46秒、输出25600token、输出吞吐86.06token/s，平均TTFT148.43秒、P99 TTFT293.12秒。服务“全部成功”与用户“等很久”同时成立。

先将时间划分为客户端准备/连接、服务接收、排队、prefill、首正文传输和后续decode。客户端只知道总TTFT时，不能直接把148秒命名为prefill耗时。

### 11.1 三步区分计算慢与排队慢

先单请求同输入测一次TTFT，保留冷/热两次。然后固定并发1/2/4，观察平均和尾部；最后用有限到达率逐步增加请求。与此同时记录running、waiting、KV占用、preemption和设备活动。

如果单请求很快、突发TTFT随等待队列增长，优先处理到达率与容量；如果没有队列但TTFT仍很高，检查输入长度、processor、tokenizer、编译与prefill；如果服务指标正常而客户端慢，再看网络、连接复用与客户端调度。

### 11.2 为什么不能一直增加活动序列

seqs增大会增加活跃KV与计算负担，也可能提高批处理利用。达到带宽或内存瓶颈后，再增加并发只会让单请求变慢或触发抢占。应在固定输入输出下画出吞吐、TTFT、E2E和资源随并发变化的曲线，找到满足门槛的区域。

活动序列4不是只允许HTTP接收4个请求，200个连接也不是200个模型序列同时计算。模型服务与入口网关的排队、拒绝和超时策略需要分别说明。

## 十二、资源采样要与请求窗口对齐

只有一张`nvidia-smi`图片，不能说明整轮峰值、平均功耗和持续频率。NVIDIA环境可在另一终端进行固定周期采样：

```bash
nvidia-smi \
  --query-gpu=timestamp,index,memory.used,utilization.gpu,temperature.gpu,power.draw,clocks.sm \
  --format=csv -l 1 > results/gpu-resource.csv
```

某些字段在特定设备上不支持，应保留N/A并改用对应平台工具，不用0填补。运行结束对自己启动的采样器停止采集，保存压测开始和结束时间。统一内存还要记录主机MemAvailable、进程RSS、swap与磁盘活动。

CPU、Intel NPU与Mac采用各平台工具时，明确是进程、设备还是整机功耗。不同边界的瓦数不能直接排名。能耗至少需要在同一测量边界积分，再除以有效输出或完成任务量；瞬时峰值乘总时间不能替代真实能耗。

采样周期1秒可能漏掉短峰值；性能计时则需要单调时钟，不依赖系统时间突然校正。跨机日志用墙钟对齐，单请求耗时用单调时钟，两种时间都有用途。

## 十三、服务时延与语音RTF怎样放进同一报告

文本任务的TTFT/TPOT和语音的RTF回答不同问题。TTS的RTF是某个生成时间边界除以音频时长，小于1表示平均生成赶得上播放；首段音频等待则由编译、分块与缓冲决定，不能从RTF直接推出。

Intel的Whisper核心RTF0.0387、首轮进程8.97秒就是明显例子。用户第一次启动仍要等待初始化；模型常驻后表现还要另测。Kokoro CPU平均RTF0.183也不能掩盖RSS约3GiB超过原2GiB目标。

报告采用四个并列结论：功能是否完成、质量是否正确、性能是否达标、资源是否在预算内。全NPU TTS速度通过但质量失败，应明确整体未通过；不把四项压成一个模糊“成功”。

## 十四、从表格写出可执行的下一步

一份有用报告应能回答：现在推荐哪个配置、适合多长输入/输出和多大负载、超过边界会怎样、下一项最值得试什么。比如oMLX先补同样本量并发曲线，GB10先补有限到达率，AWQ先补质量回归，DFlash先拆分配置变量。

这样每个后续实验都解决一个明确问题。不要为增加测试数量而不断换工具、换数据和重跑已经足够的结果；保留可复查的原始材料，围绕剩余风险推进。
