# API、监控与验收：让服务的状态可见

[总目录](../../SUMMARY.md) · [工程交付总章](../../02-capability-layers/05-engineering-delivery.md) · [环境与运维](environment-operations.md)

## 本章概览

应用看到的是接口与答案，工程师还需要知道请求是否在排队、资源是否不足、错误是否增加。本章把API契约、健康、指标、质量与验收串起来，避免服务只有一个“启动成功”的截图。

内容依据FlowUs服务和压测文章整理；指标示例来自本书实际CPU演练。接口兼容按具体能力验证，不把“兼容OpenAI API”理解成所有字段、工具与错误语义完全相同。

## 1. 先约定接口与任务范围

至少写清地址、模型别名、请求字段、上下文与输出限制、采样、思考、流式、超时、取消和错误格式。应用若使用图片、工具调用、JSON约束或多轮缓存，要单列测试。

在部署目录中保存几份固定请求：正常短问答、长输入、JSON任务、流式、错误模型、畸形JSON与超限输入。请求用公开或脱敏材料，测试结果保存HTTP状态、响应、结束原因与usage。

## 2. 健康、就绪与功能分开

进程存活表示程序仍在；就绪表示模型已经完成加载并可接收请求；功能检查则验证接口和任务结果。它们相互补充，不能只靠操作系统进程状态。

llama-server与vLLM的健康接口按固定版本确认。本书CPU演练在畸形JSON返回500之后，`/health`仍返回`{"status":"ok"}`。这说明服务恢复可用，但该异常协议检查仍未通过，因为预期是明确4xx。

健康轮询不要持续提交长生成任务造成额外负载。周期功能探针可以使用受控短任务，记录频率与资源开销，避免把探针混入正式压测成绩。

## 3. 流式客户端看什么？

SSE按事件解析，可能先出现角色或空内容，再出现正文。记录首个有效正文时间；检查最终结束标记、usage和错误。网络断开、客户端取消和服务结束要区分，不要把部分文本当作完整成功。

模型思考内容、最终答案和工具参数的传输字段可能不同。若应用只读取`content`，就应确认所需最终答案确实在那里。不能收到任何字符串就标成功。

本书客户端使用标准库解析`data:`事件并保存正文、usage、finish_reason、TTFT和E2E。它是小型教学实现，没有逐token到达时间和重连机制；正式服务应针对这些能力补充验证。

## 4. 四组监控指标

| 范围 | 指标 | 用途 |
| --- | --- | --- |
| 客户端 | 成功/失败、TTFT、E2E、取消、超时 | 判断实际体验与错误 |
| 服务调度 | 活动/排队、KV、命中、重算 | 解释等待与容量 |
| 系统资源 | CPU/GPU、RSS/显存、swap、温度/功耗 | 发现资源和热约束 |
| 任务质量 | 完整答案、正确率、格式合法率 | 防止速度掩盖错误 |

高TTFT可能来自排队、prefill、编译或网络；高TPOT可能来自decode、带宽、批处理或资源竞争。将同一时间窗口的请求与服务指标对齐，才能缩小原因。

## 5. 一个真实 metrics 文件

CPU演练启用`--metrics`，采集到的[metrics.txt](../../practice/first-service/results/2026-10-18-windows-cpu/metrics.txt)包括：

```text
llamacpp:prompt_tokens_total 355
llamacpp:tokens_predicted_total 266
llamacpp:requests_processing 0
llamacpp:requests_deferred 0
```

这是演练采样时的累计与瞬时状态，包含功能检查和HTTP测试，不仅是性能组的128+128输出token。因此不能拿累计266除以某一组时间计算吞吐，也不能因为采样时排队为0就说测试全过程没有等待。

计数器看增量，瞬时值看时间序列，重启后计数可能归零。不同版本指标名与单位可能改变，应保存原始指标说明及采样方式。公开文件只保留必要指标，带请求文本、路径或设备标识的标签要先检查。

## 6. 验收分为功能、质量、性能和恢复

功能验收检查接口、流式与产物；质量验收检查任务答案；性能验收按目标负载与阈值；恢复验收检查错误请求、停止、启动和回滚。各项单独记录通过、失败与未测。

本书CPU演练HTTP八条性能请求均成功，三道功能题只有两道通过，畸形JSON返回500，所以总体`exercise_passed=false`。如实保留失败，能够指导下一步：核对小模型与模板的质量、处理异常协议，而不是继续提高并发。

对真实项目，阈值应来自需求。例如规定某输入分布、并发和质量标准下的P95 TTFT与成功率。尚未确定的阈值写待定义，不根据本次数据临时修改成“刚好通过”。

## 7. 交付一份可维护的结论

结论说明可运行设备与版本、模型身份、功能范围、目标长度与负载、质量和性能、失败输入、监控位置与恢复入口。把每个关键结论链接到实际文件。

知识体系用于解释如何做判断，项目目录负责保存具体运行记录。公开发布时只复制经过检查的工程必要字段；原始私人空间、凭据、内部节点和业务材料留在授权范围内。
