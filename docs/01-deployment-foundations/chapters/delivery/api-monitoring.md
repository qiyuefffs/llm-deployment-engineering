# API、监控与验收：让服务的状态可见

[总目录](../../SUMMARY.md) · [工程交付总章](../../02-capability-layers/05-engineering-delivery.md) · [环境与运维](environment-operations.md)

## 本章概览

应用看到的是接口与答案，工程师还需要知道请求是否在排队、资源是否不足、错误是否增加。本章把API契约、健康、指标、质量与验收串起来，避免服务只有一个“启动成功”的截图。

内容依据FlowUs服务和压测文章整理；指标示例来自本体系实际CPU演练。接口兼容按具体能力验证，不把“兼容OpenAI API”理解成所有字段、工具与错误语义完全相同。

## 1. 先约定接口与任务范围

至少写清地址、模型别名、请求字段、上下文与输出限制、采样、思考、流式、超时、取消和错误格式。应用若使用图片、工具调用、JSON约束或多轮缓存，要单列测试。

在部署目录中保存几份固定请求：正常短问答、长输入、JSON任务、流式、错误模型、畸形JSON与超限输入。请求用公开或脱敏材料，测试结果保存HTTP状态、响应、结束原因与usage。

## 2. 健康、就绪与功能分开

进程存活表示程序仍在；就绪表示模型已经完成加载并可接收请求；功能检查则验证接口和任务结果。它们相互补充，不能只靠操作系统进程状态。

llama-server与vLLM的健康接口按固定版本确认。本体系CPU演练在畸形JSON返回500之后，`/health`仍返回`{"status":"ok"}`。这说明服务恢复可用，但该异常协议检查仍未通过，因为预期是明确4xx。

健康轮询不要持续提交长生成任务造成额外负载。周期功能探针可以使用受控短任务，记录频率与资源开销，避免把探针混入正式压测成绩。

## 3. 流式客户端看什么？

SSE按事件解析，可能先出现角色或空内容，再出现正文。记录首个有效正文时间；检查最终结束标记、usage和错误。网络断开、客户端取消和服务结束要区分，不要把部分文本当作完整成功。

模型思考内容、最终答案和工具参数的传输字段可能不同。若应用只读取`content`，就应确认所需最终答案确实在那里。不能收到任何字符串就标成功。

本体系客户端使用标准库解析`data:`事件并保存正文、usage、finish_reason、TTFT和E2E。它是小型教学实现，没有逐token到达时间和重连机制；正式服务应针对这些能力补充验证。

## 4. 四组监控指标

| 范围 | 指标 | 用途 |
| --- | --- | --- |
| 客户端 | 成功/失败、TTFT、E2E、取消、超时 | 判断实际体验与错误 |
| 服务调度 | 活动/排队、KV、命中、重算 | 解释等待与容量 |
| 系统资源 | CPU/GPU、RSS/显存、swap、温度/功耗 | 发现资源和热约束 |
| 任务质量 | 完整答案、正确率、格式合法率 | 防止速度掩盖错误 |

高TTFT可能来自排队、prefill、编译或网络；高TPOT可能来自decode、带宽、批处理或资源竞争。将同一时间窗口的请求与服务指标对齐，才能缩小原因。

## 5. 一个真实 metrics 文件

CPU演练启用`--metrics`，采集到的[metrics.txt](../../practice/first-service/results/2026-10-18-windows-cpu/metrics.txt)包括：

```text
llamacpp:prompt_tokens_total 355
llamacpp:tokens_predicted_total 266
llamacpp:requests_processing 0
llamacpp:requests_deferred 0
```

这是演练采样时的累计与瞬时状态，包含功能检查和HTTP测试，不仅是性能组的128+128输出token。因此不能拿累计266除以某一组时间计算吞吐，也不能因为采样时排队为0就说测试全过程没有等待。

计数器看增量，瞬时值看时间序列，重启后计数可能归零。不同版本指标名与单位可能改变，应保存原始指标说明及采样方式。公开文件只保留必要指标，带请求文本、路径或设备标识的标签要先检查。

## 6. 验收分为功能、质量、性能和恢复

功能验收检查接口、流式与产物；质量验收检查任务答案；性能验收按目标负载与阈值；恢复验收检查错误请求、停止、启动和回滚。各项单独记录通过、失败与未测。

本体系CPU演练HTTP八条性能请求均成功，三道功能题只有两道通过，畸形JSON返回500，所以总体`exercise_passed=false`。如实保留失败，能够指导下一步：核对小模型与模板的质量、处理异常协议，而不是继续提高并发。

对真实项目，阈值应来自需求。例如规定某输入分布、并发和质量标准下的P95 TTFT与成功率。尚未确定的阈值写待定义，不根据本次数据临时修改成“刚好通过”。

## 7. 交付一份可维护的结论

结论说明可运行设备与版本、模型身份、功能范围、目标长度与负载、质量和性能、失败输入、监控位置与恢复入口。把每个关键结论链接到实际文件。

知识体系用于解释如何做判断，项目目录负责保存具体运行记录。公开发布时只复制经过检查的工程必要字段；原始私人空间、凭据、内部节点和业务材料留在授权范围内。

## 八、给接口建立一组固定验收输入

一组实用验收先覆盖正常路径，再覆盖最可能使服务失稳的边界。不要求一次塞入所有复杂功能，但应用会依赖的能力必须有明确结果。

| 输入 | 检查内容 | 结果应保存什么 |
| --- | --- | --- |
| 短问答 | 模板、正文、自然结束 | 请求、响应、usage、finish_reason |
| 确定答案题 | 质量基线 | 期望、原始输出与判分 |
| 多轮对话 | 历史与角色正确 | 完整messages和最终答案 |
| 固定JSON字段 | 格式与字段语义 | 原始字符串、解析结果、字段验收 |
| 流式长回答 | 正文、结束、取消 | SSE事件、时间、取消后状态 |
| 错误模型名/畸形JSON | 参数校验和错误协议 | HTTP状态、错误体、之后健康 |
| 超长输入/过大图片 | 边界提示与资源 | 错误类型、资源与后续可用性 |

JSON合法与JSON内容正确分别判断，例如`{"count":2}`可解析但期望count3仍失败。工具调用也要检查工具名、参数与调用顺序，不能只判断响应含tool_calls字段。

本体系CPU三道功能题两道通过，异常JSON得到500，都是可复查的失败例。硬件章节的历史成绩则按它们原有质量材料判断，不用这组小模型题替其他模型认证。

## 九、反向代理接入后重新验证SSE

服务直连正常，经过代理却等到最后一次显示，可能是代理缓冲；请求长时间无输出可能触发读超时。先比较直连与代理的相同流式请求，观察事件到达，不立即修改模型参数。

下面是本机实验反向代理说明片段，不包含对外发布配置。Nginx中的超时应按实际输入与SLO设定，600秒只是示例：

```nginx
server {
    listen 127.0.0.1:8088;
    location /v1/ {
        proxy_pass http://127.0.0.1:8001;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header X-Request-Id $request_id;
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 600s;
    }
}
```

接入后再验收首正文、增量、结束、错误、取消与请求ID。后端不一定自动将X-Request-Id写入日志，需要按它的支持配置。不要因为增加了header，就声称端到端追踪已经成立。

超时也要分层：连接超时、请求上传、服务排队、首输出、读空闲与整体deadline。把每层超时都设得很长可能掩盖队列失控，服务超过约定预算应有可识别的取消和恢复行为。

## 十、读懂Prometheus的计数器、瞬时值和分布

计数器记录累计事件，如输出token总数；瞬时值表示采样时状态，如活动/排队请求；分布指标用于计算区间延迟。计数器不能直接当每秒值，瞬时队列为0也不说明此前没有等待。

基于本体系真实llama.cpp指标，可写出以下PromQL来理解采样方式，实际抓取标签应选定对应实例：

```promql
rate(llamacpp:tokens_predicted_total[5m])
rate(llamacpp:prompt_tokens_total[5m])
llamacpp:requests_processing
llamacpp:requests_deferred
```

前两项是5分钟窗口的token速率估计，后两项是当前值。它们并不自动等于某次压测的精确吞吐；压测边界明确时仍用该次实际token/墙钟计算。应用重启导致计数归零，rate函数的重置处理与稀疏采样也要了解。

如果使用直方图算P95，先确认桶单位和标签；跨实例求平均P95通常没有明确的总体百分位意义。没有分布数据时不伪造尾延迟，用客户端原始请求计算并保存算法。

### 一个最小采集配置

```yaml
scrape_configs:
  - job_name: local_llama
    scrape_interval: 5s
    static_configs:
      - targets: ['127.0.0.1:18080']
```

配置假设Prometheus与llama-server在同一主机网络，server已经开启metrics。如果Prometheus在独立容器，127.0.0.1指容器自身，应按真实网络映射调整。图表显示无数据时，先验证抓取目标和端点，再检查指标名。

## 十一、从四种监控组合定位问题

TTFT高、waiting持续增长、running接近预算，说明先查到达率和容量；TTFT高、waiting低但prefill重，查输入长度、图像token与编译；TPOT随swap/频率下降，查内存和热约束；客户端慢但服务计时正常，查代理、网络与客户端。

这些是排查入口，不是仅凭一张曲线就确定根因。按同一时间窗把客户端请求ID、服务日志、指标和资源对齐，再用小负载或单变量对照验证。

Intel Kokoro CPU在残留NPU编译共存时P95 RTF0.290，清理后0.189，是后台竞争的实例；AMD395的分配失败与63215MiB可见量相互印证，是资源预算实例；Mac视觉500后EngineDead是功能缺失引发进程不可用的实例。

## 十二、验收报告怎样明确通过、失败和未测

每项验收列出输入、运行环境、目标、实际值、证据文件和结论。缺数据写未测；数值超标写失败；功能正确但性能未达目标也保留功能通过。不要用一个“部署成功”覆盖所有维度。

对历史工程，本体系保留了已知参数与真实汇总，缺原始文件的部分在来源页集中说明。新运行按前文目录保留完整材料，就可以把同一验收标准持续用于升级和回归。
