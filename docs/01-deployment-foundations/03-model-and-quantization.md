# 03 模型格式、转换与量化

[返回总目录](README.md) · [上一章](02-hardware-compatibility.md) · [下一章](04-memory-and-kv-cache.md)

## 1. 模型名称不是完整的模型标识

同一系列可能有 Base、Instruct、Thinking、Dense、MoE、文本和多模态版本。参数规模相同，也可能具有不同 KV 头数、位置编码、分词器和模板。部署前记录完整仓库、revision、架构、参数规模、许可证、文件名、字节数与哈希。量化仓库还要关联原始模型与转换工具版本。

模型目录通常包含 `config.json`、权重分片及索引、分词器文件、模板与生成配置。文件缺失可能表现为加载失败，也可能只是输出异常。不要把“下载完成”与“模型包完整”混为一谈。模型文件哈希只有和可信发布方值比较，才能验证与其一致；自己计算的哈希可追踪后续变化，但不能单独证明来源真实。

## 2. 分开五类概念

| 类别 | 例子 | 工程含义 |
| --- | --- | --- |
| 权重容器 | safetensors、GGUF、PyTorch checkpoint | 如何保存张量及部分元数据 |
| 图或中间表示 | ONNX、OpenVINO IR | 如何描述结构、算子、输入输出 |
| 编译制品 | TensorRT engine、厂商编译图 | 为特定工具链、设备与形状优化的制品 |
| 数值与布局 | BF16、FP16、FP8、INT4、分组、打包 | 数值如何表示、组织与传输 |
| 量化方法/工具 | AWQ、GPTQ、AutoRound、NNCF、bitsandbytes | 如何选择尺度、校准或生成目标表示 |

AWQ/GPTQ 不是文件后缀，GGUF 也不等于 Q4。safetensors 可装不同精度的权重，但不会自动解决目标框架的架构支持。编译引擎的可移植性取决于构建设置、硬件和 SDK，不应按普通权重文件随意跨设备复制。

GGUF 通常包含张量、架构信息、分词器与模板等元数据。Q4_K_M、Q5_K_M、Q8_0 是具体量化配置/类型的名称，不只是位宽数字。混合张量精度、scale、分组和对齐使文件体积偏离“参数数 × 4 bit”。

## 3. W4A16 与 KV 精度分别控制什么

`W4A16` 通常表示 4 位权重与 16 位激活，`W8A8` 表示 8 位权重与激活；具体数据类型、对称性和计算过程仍要看实现。4 位存储不意味着所有运算都在硬件上用原生 4 位执行，可能边解码权重边进行较高精度计算。

权重量化减少权重存储和搬运；激活量化影响中间数据与计算 kernel；KV 量化针对历史状态。三者可独立变化。模型文件是 Q4，不能推断 KV 也是 Q4；服务可能仍分配 FP16 KV。

FP16/BF16 常作为高精度部署基线，二者指数范围和有效精度不同。FP8、MXFP4、NVFP4 等数值格式还涉及缩放与硬件路径。能在软件中表示某种类型，不等于目标 GPU 有适配该模型的高效 kernel。不能把“新 GPU 支持某低精度”推广为旧卡也能获得相同收益。

## 4. 量化的收益与代价

假设 Dense 模型每轮 Decode 需要大量读取权重，较小权重可能减少带宽压力。但反量化、访存布局、矩阵尺寸、batch、CPU 指令集和后端实现会改变结果。量化可能让模型放入单卡从而避免 CPU 卸载，也可能仅节省空间而速度下降。

质量影响也不是均匀的：简单闲聊看不出变化，不代表数字抽取、代码、工具参数、长上下文和小语种不受影响。更大的低位模型与更小的高位模型谁更合适，需要在同一业务样例和资源约束下比较。

常见选择步骤是先确认架构支持，再选择设备有高效实现的量化配置；然后比较文件体积、启动/峰值内存、Prefill、Decode、端到端延迟与任务质量。若质量下降超过预先设定的容忍范围，即使吞吐更好也不能通过验收。

## 5. 转换与量化是一条可追溯流水线

```text
原始 revision → 原始模型/模板验证 → 格式转换 → 转换等价性检查
            → 量化 → 质量回归 → 设备性能测量 → 发布 manifest
```

转换失败先检查架构与工具版本，不要改扩展名或强行套另一模型结构。量化失败先确认输入类型与所需校准/importance matrix，不能认为每种类型都用同一条命令。避免从低精度权重反复再量化：丢失的信息不会因为换一种 Q4 恢复。

下面是 **Linux + 已固定 llama.cpp commit + 受支持的文本模型** 的概念性操作模板。`/models/source-model` 必须是完整且可信的原始模型目录，转换时需要安装该 commit 对应 Python 依赖；磁盘与 RAM 还需容纳中间高精度权重。这里没有下载模型，也没有声称本章运行过该转换。

```bash
# 在固定版本的 llama.cpp 源码根目录；先阅读 requirements 与脚本 --help
python convert_hf_to_gguf.py /models/source-model \
  --outfile /models/model-f16.gguf --outtype f16

./build-cpu/bin/llama-quantize \
  /models/model-f16.gguf /models/model-Q4_K_M.gguf Q4_K_M

sha256sum /models/model-f16.gguf /models/model-Q4_K_M.gguf
```

检查点：转换日志中的架构与张量数量是否合理；分词器与模板是否保留；输出文件能否被同 commit 引擎读取；相同消息是否正确停止；量化前后任务质量如何。若使用社区量化成品，仍需记录发布来源、原模型关系、量化方法、许可证与哈希，不把成品当成没有来源的黑盒。

## 6. 校准数据与评测数据怎样安排

部分方法需要代表性校准数据，部分配置可无数据执行，另一些可用重要性矩阵改善结果。校准样例应覆盖实际输入语言、长度、领域与格式，不能只选最容易的短问答。评测集应独立于校准集，防止用“校准时已见过的题”代替泛化能力。

一个小规模起点是准备正常任务、长输入、结构化输出、数字与实体保持、多轮对话、边界输入六类样例，给每项制定规则或人工标准。样本数由风险与差异决定，不能把几十题描述为全面能力认证。保留原始答案、量化答案、判定原因和截断状态。

困惑度可用于观察语言建模变化，但它不能替代业务正确率。只比较答案是否逐字相同也不合适：合法答案可能有多种表达，而错误输出也可能与基线共享大量文字。应按任务检查字段、事实、执行结果或引用。
