# 第三部分：核心概念解释库

[总目录](README.md) · [五层能力](02-capability-layers/01-hardware-backends.md) · [下一部分：项目复盘](04-project-review.md)

本部分保留原稿的概念组织方式。每项先给一句话解释，再说明工程作用和验证方法；具体命令在第二部分，完整数据在[来源索引](evidence/README.md)。

## 3.1 vLLM 为什么通常适合高吞吐服务？

**一句话：** 它把 KV 管理、请求调度和设备执行组合起来，让多个请求更有效地共用设备。

**工程解释：** 单请求生成经常无法用满设备。vLLM 利用持续批处理让已完成请求及时退出、新请求加入；通过 KV 管理减少内存浪费；再结合优化算子、图执行和分布式执行提高效率。实际收益取决于模型、硬件、精度、负载和版本。

**如何验证：** 同一模型与任务扫描并发，观察总吞吐、单请求延迟、KV、等待队列和错误率。比较应包含至少一个满足目标延迟的工作点。

**常见误读：** 不存在对所有端侧设备都更快的框架排名。低并发、CPU、部分卸载或特定不受支持模型，可能更适合其他路线。

## 3.2 PagedAttention 是什么？

**一句话：** 用块管理 KV，减少连续大块分配造成的浪费，并支持更灵活的缓存组织。

**工程解释：** 每条序列的长度会增长，请求也会随时完成。分页式 KV 管理把逻辑序列映射到物理块，避免按每个请求最大长度预留一整块连续空间。块大小、元数据、缓存复用与具体实现仍有开销。

**如何验证：** 看可用 KV 容量、活动序列、缓存占用、抢占/重算与目标长度下成功率。它改善内存管理，最终性能仍由执行与调度共同决定。

**常见误读：** 它不会让所有 token 的 KV 消失，也不等同于把 KV 换到磁盘。它与 Flash Attention 解决的问题不同，可以同时存在。

## 3.3 KV Cache 是什么？

**一句话：** 保存已处理 token 的 Key 和 Value，让后续生成复用历史状态。

**工程解释：** 逐 token 生成时，不必每步重新计算整个历史。代价是缓存随上下文和活动序列增长。标准注意力、GQA、MLA、滑动窗口等结构的缓存布局不同，需按模型计算。

**如何验证：** 读取模型层数、KV头数与维度，做预算；再用实际长输入和并发核对引擎分配、峰值和失败点。公式与算例见[第4层4.3节](02-capability-layers/04-memory-performance.md#43-kv-cache-怎样计算)。

**常见误读：** 权重量化与 KV 量化是两个配置。下载了 INT4 权重，KV 仍可能是 FP16/BF16。

## 3.4 Continuous Batching 是什么？

**一句话：** 在生成过程中动态加入和移出请求，让不同长度的请求共用执行批次。

**工程解释：** 静态批处理通常等待一批请求全部结束，短请求完成后其位置可能空着。持续批处理可以把空位交给新请求，提高设备利用；与此同时，调度、公平性、长输入与短输出之间会产生权衡。

**如何验证：** 用混合长度的多请求负载，保存请求开始与完成时间，观察总吞吐、活动请求与尾延迟。只测一条请求无法验证该机制的服务收益。

**实例：** oMLX 记录中并发1→4，总吞吐29.38→55.15 token/s，但平均请求延迟7.582→13.459秒。它说明批处理的容量收益和等待代价需要一起看，不是该机制的严格单项消融实验。

## 3.5 Chunked Prefill 是什么？

**一句话：** 把长输入的 prefill 分块调度，减轻它一次占用执行预算对其他请求的影响。

**工程解释：** 大量输入 token 一次执行可能占用较大工作区，并影响正在 decode 的请求。分块后，调度器能更灵活地安排 prefill 与 decode；块大小和每轮预算仍会影响效率。

**如何验证：** 固定长输入与短请求混合负载，比较 TTFT、ITL、吞吐、显存峰值和请求完成情况。记录 `max-num-batched-tokens` 等相关配置。

**常见误读：** 它没有删掉模型需要理解的上下文，也不保证首 token 和后续 token 延迟同时降低。

## 3.6 Prefix Cache 是什么？

**一句话：** 复用相同 token 前缀已经计算的状态，减少重复 prefill。

**工程解释：** 相同系统提示或长文档可能形成可复用前缀；实际匹配受 token序列、块边界、模型/适配器、缓存策略和实现影响。存在缓存条目不等于每条请求都命中。

**如何验证：** 分开跑冷前缀、重复前缀、不同前缀；记录实际输入 token、缓存命中及 TTFT。每组说明缓存是否清理，首轮与重复轮次不混合。

**常见误读：** 单次 TTFT 很短不能证明缓存有效。也不能用已缓存重复题代表首次处理新文档的性能。

## 3.7 TP：Tensor Parallelism

**一句话：** 把同一层的张量计算拆到多张设备上。

**工程解释：** 每张设备保存和计算一部分张量，在需要时交换结果。它能分担权重和计算，但通信频繁；模型头数与分片约束、量化 kernel、互连和实际后端都影响可用性。

**如何验证：** 先验证通信正确与带宽，再测相同输入的单卡/多卡；记录拓扑、每卡占用、通信时间和端到端指标。

**常见误读：** 两张16GB设备不自动等价于一张32GB设备；RTX 4080 也不能安装 NVLink 桥。

## 3.8 PP：Pipeline Parallelism

**一句话：** 把模型的不同层或阶段放在不同设备上，按顺序传递中间结果。

**工程解释：** 单条请求要经过多个阶段，各阶段计算不均会等待；多批次或多请求有助于填充流水线，但存在气泡和调度成本。它与 TP 可以结合，具体取决于框架支持。

**如何验证：** 看各阶段负载、传输、等待以及不同并发下的吞吐。只看到每张卡都有权重不足以证明流水线效率高。

**常见误读：** llama.cpp 的层卸载或 RPC 分层不能直接等同于 vLLM 中同名并行策略。要看实际执行模型。

## 3.9 DP 与 EP 补充

**DP：** 多个模型副本服务不同请求。它适合扩展总吞吐和服务容量，通常仍要求每个副本容纳模型；部署中的数据并行与训练中的梯度同步含义不同。

**EP：** 把 MoE 专家分配到不同设备。路由、专家负载不均和跨设备通信可能成为瓶颈。激活专家少不代表模型全部权重可以省略。

验证时看每个副本/专家的流量、利用率、内存和通信，不能只报总 GPU 百分比。

## 3.10 GGUF 是什么？

**一句话：** 保存模型张量与相关元数据的文件格式，常用于 llama.cpp 路线。

**工程解释：** GGUF 内包含架构、tokenizer及张量布局等信息，可以保存不同精度或量化类型；执行仍依赖后端实现。GGUF不是“4bit”的同义词，也不是独立推理框架。

**如何验证：** 检查模型来源、转换版本、元数据、文件校验、目标框架与量化 kernel。转换、加载和正确生成是三个检查点。

**常见误读：** `Q4_K_M` 中的 K 指 K-quant 家族，不能按 k-means 解释；M 是该混合方案的档位标记，不表示所有张量都严格4bit。具体布局以固定版本实现为准。

## 3.11 量化为什么不一定更快？

**一句话：** 位宽更低减少存储和部分数据搬运，但计算是否快取决于 kernel、硬件和负载。

**工程解释：** 反量化、打包、尺度读取、混合精度层和算子回退都有成本。某设备的 INT4 kernel 可能成熟，另一个设备可能需要转换或回退。较大的 batch 又可能改变带宽与计算的占比。

**如何验证：** 固定模型系列、输入输出和服务参数，对比权重占用、峰值、TTFT、TPOT、吞吐和质量。无法固定转换/校准条件时，说明比较的是制品组合。

**实例：** Intel短生成中 INT4 的生成速率高于 INT8，但TTFT略高；GB10 Gemma AWQ4/8也是不同制品组合的观察。两项都不能替代质量回归。

## 3.12 Flash Attention 是什么？

**一句话：** 通过分块与计算组织减少注意力计算对中间结果存储和数据搬运的需求。

**工程解释：** 它优化注意力执行；支持条件取决于设备、数据类型、head dimension、mask、模型与实现。它和 KV 块管理、请求调度属于不同层面。

**如何验证：** 固定同一框架版本、模型、负载和内存预算，核对实际 kernel 路径，比较 prefill、decode、峰值和质量。命令有开关仍要确认实际启用。

**常见误读：** 缩写相同的开关在不同框架不保证对应同一实现。不要把一个平台的收益百分比推广到所有设备。

## 3.13 推测解码、MTP 和 DFlash

**一句话：** 先提出多个候选，再由目标模型验证，尝试一次确认多个输出 token。

**工程解释：** 草稿模型或预测头产生候选，目标验证有接受和拒绝；不同方法的成本、约束和采样正确性各不相同。接受率高也可能因草稿计算昂贵而无收益。

**如何验证：** 固定目标模型、上下文、调度、内存和采样，仅切换方法；同时记录接受率、总吞吐、TTFT、ITL、质量和资源。

**实例：** Gemma MTP 有吞吐提升但流式间隔变长的记录；DFlash两套配置同时改了多个参数，约2.03倍只作为组合观察。详见[第4层](02-capability-layers/04-memory-performance.md)。

## 3.14 统一内存、mmap 与卸载

**统一内存：** CPU/GPU等共享物理内存资源，但仍有后端预算、系统预留与带宽竞争。不能把物理容量全部交给模型。

**mmap：** 把文件映射到进程地址空间，按系统策略访问和缓存页。映射大小、进程RSS与物理驻留不是同一个数字，也不表示整个权重已放到GPU。

**卸载：** 将部分层或算子放到设备，其余在CPU执行。实际性能取决于计算分工与传输，不只看卸载层数。

**如何验证：** 对照运行日志、设备分配、主机内存、swap和性能。AMD GTT/TTM实例说明，物理内存与运行时可分配量必须分别检查。

## 3.15 框架选型怎样落到工程决策？

按“任务功能 → 模型制品 → 设备支持 → 资源预算 → 目标负载 → 运维交付”逐项筛选。候选框架先完成同一最小请求和质量检查，再比较目标负载。

| 约束 | 优先验证的路线 | 决策依据 |
| --- | --- | --- |
| CPU/部分卸载/多后端 | llama.cpp等 | 能否容纳、线程与带宽、卸载成本 |
| Intel端侧 | OpenVINO与受支持SYCL/Vulkan等 | 模型IR、GPU/NPU分别执行、任务支持 |
| Apple本地 | MLX或Metal路线 | 制品、功能、统一内存与服务层 |
| 多请求设备服务 | vLLM等 | 模型/kernel、调度、并发SLO |
| 多卡或多机容量不足 | 受支持的分布式路线 | 通信、切分与故障恢复 |

先验证一条可以完成任务的路线，再比较替代方案。把理由、基线与限制写入[项目复盘](04-project-review.md)，后续升级就能知道为什么当时这样选择。
