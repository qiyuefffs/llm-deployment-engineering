## 本部分概览

前面五层回答了部署过程中怎样做，本部分解释其中十个经常遇到的概念。保持原框架的十个主题，每项按“一句话解释、工程解释、工程分析”阅读。完整命令与结果仍在专题章，不在这里重复一遍教程。

## 3.1 vLLM 为什么快？

**一句话解释：** 它把请求调度、KV管理和设备执行结合起来，提高多个请求共同使用设备的效率。

**工程解释：** 单请求逐token生成有串行依赖，未必用满设备。持续批处理让不同请求共用执行批次；KV管理减少容量浪费；优化kernel、图执行与分布式路线进一步影响计算效率。这些机制共同工作，而不是某一个名字代表全部性能。

**工程分析：** “快”要有比较对象和负载。用相同模型、精度、输入输出与质量比较目标并发，报告吞吐和延迟。CPU、低并发、部分卸载或未支持架构可能更适合其他框架，不能按框架名称排出通用速度榜。[完整部署](chapters/frameworks/vllm-service.md)中的GB10测试同时启用了多个机制，结果属于整套配置。

### 先用请求形态理解“效率”

一个人问一句话，设备可能主要等待逐步decode；很多人同时请求，框架可以把多个序列安排到一轮执行，共享部分权重读取成本。输入很长时，又需要让prefill与正在生成的请求合理交错。所以“高并发吞吐快”和“一个人首字快”不是相同目标。

GB10突发200请求得到86.06token/s，却有约148秒平均TTFT，说明调度效率不能脱离到达模式。框架没有义务让无限排队保持低延迟，服务入口和工作负载也参与结果。

## 3.2 PagedAttention 是什么？

**一句话解释：** 用块组织KV，让不断增长、长度不同的请求更灵活地分配与共享缓存。

**工程解释：** 逻辑连续的历史不一定对应物理连续大块内存。块表将序列位置映射到实际缓存，按请求增长、完成与共享管理资源。块粒度、元数据和调度仍有成本，不能理解成KV消失了。

**工程分析：** 看同样容量下可运行的序列与长度、块使用、抢占和重算，再看服务表现。Flash Attention优化attention执行的数据访问，与KV块管理作用不同，可以同时存在。详细实验方法见[缓存与调度](chapters/performance/cache-scheduling.md)。

### 从连续预留到按块增长

假设单条最大4096token，但某请求只用了100token。若为每条固定保留完整连续区，许多容量暂时没有使用；按块可以让它先占足够的块，再随生成增长。最后一个块仍可能留空位，也存在块表和管理开销，分页不是没有浪费。

MLX-VLM APC记录中8192块、每块16token，对应131072个块槽位token，但还要考虑跨请求共享、挤出和模型窗口。不能把这一乘积贴成单请求上下文上限。实际使用看统计、内存与目标请求是否完成。

## 3.3 KV Cache 是什么？

**一句话解释：** 保存已处理token的Key与Value，供后续生成利用历史信息。

**工程解释：** 复用状态减少重复计算，却增加随历史长度和活动序列增长的存储与访问。常规全注意力、GQA、MLA、滑动窗口和混合结构的预算不同。权重是INT4，不表示KV也是INT4。

**工程分析：** 先按结构估算，再核对引擎实际分配和目标长度。加载能成功、长请求才OOM，通常要重点看KV与prefill工作区。公式和教学算例见[第4层4.3节](02-capability-layers/04-memory-performance.md#43-粗略显存估算)。

### Q、K、V可以怎样直观理解

当前token产生Query，历史token提供Key与Value，attention根据匹配关系使用历史信息。KV缓存保留的是后续会反复用到的K/V状态；当前Query仍需计算，对历史状态的读取也仍有代价。

因此KV增长影响两件事：容量增加，以及后续生成需要访问更多历史。降低权重位宽不自动压缩KV，提高模型窗口也不自动给设备增加缓存空间。长上下文测试应同时看“有没有记住内容”和“能否在预算内运行”。

## 3.4 Continuous Batching 是什么？

**一句话解释：** 在生成过程中让新请求加入、完成请求退出，动态利用执行批次。

**工程解释：** 请求长短不同，静态整批等待容易留下空闲；持续调度可以补入新请求。活动序列上限、每轮token预算、输入长度、到达模式与KV共同影响执行。客户端并发也不等于每轮真正执行的序列数。

**工程分析：** 本体系CPU实跑中c2相对c1提高总吞吐，同时TTFT与E2E增加。说明容量和体验要一起验收。oMLX历史记录也有类似方向，但它没有单项消融，不能把全部差异归因于这一机制。见[压测实例](chapters/performance/benchmarking.md)。

### 一个简单的调度时间线

```text
轮1：A、B开始生成
轮2：A、B继续
轮3：A完成，B继续，C加入
轮4：B、C继续
```

这只是机制示意，不是某框架的真实trace。能否立即加入C取决于KV、每轮预算和prefill策略。请求结束后资源及时回收，批处理才能持续运作；取消或错误路径如果没有正确回收，也会影响后续容量。

## 3.5 Chunked Prefill 是什么？

**一句话解释：** 将长输入的prefill按调度预算分块，增加与其他请求交错执行的机会。

**工程解释：** 长输入一次执行可能占用计算和工作区，并干扰已开始decode的请求。分块不减少全部输入，块大小与预算会改变长请求自身效率以及其他请求等待。

**工程分析：** 固定长输入与短请求混合负载，比较长请求TTFT、短请求ITL、吞吐和资源。若只测单个短请求，就无法解释分块对混合服务的价值。参数与实验见[专题第4节](chapters/performance/cache-scheduling.md#4-chunked-prefill-给长输入分段)。

### 两个用户的体验可能朝相反方向变化

用户A提交一篇长材料，用户B正在生成短回答。一次处理完A的输入可能让B长时间收不到新正文；分块后A需要更多轮才能完成prefill，B可能更平滑。衡量时同时看A的TTFT和B的ITL，而不是只测其中一个。

分块预算也受模型和kernel效率影响。把块设得极小会增加调度和调用成本，不能只追求“越碎越公平”。固定混合输入的比例与到达顺序，才能解释参数变化。

## 3.6 Prefix Cache 是什么？

**一句话解释：** 复用相同token前缀已经计算的状态，减少重复prefill。

**工程解释：** 相同长系统提示或文档可能形成可复用前缀。是否命中受模板、token序列、块、模型身份和缓存策略影响。实现不应一概称为RadixAttention；各框架的缓存结构和语义需要分别查。

**工程分析：** 首轮冷请求、重复前缀和不同前缀分开测，保存命中与TTFT。把每次变化的编号放在长文档之前，可能破坏后续匹配；缓存也可能因容量挤出。热缓存成绩不能代表新文档第一次输入。见[完整实验顺序](chapters/performance/cache-scheduling.md#5-prefix-cache-复用相同-token-前缀)。

### 为什么改一个字符可能影响后面的复用

前缀复用依赖从序列起点开始的一致状态。最前面插入时间戳，即使后面文档相同，也可能改变整个后续前缀。即使字符看起来一致，不同模板、特殊token或processor也可能改变token序列。

先用稳定长前缀验证命中，再加入新的问题、换前缀和换租户做对照。缓存只应复用实现认为身份一致的状态；模型版本变化后，不能继续使用旧KV来“节省加载”。

## 3.7 TP：Tensor Parallelism

**一句话解释：** 将同一层的张量计算分给多张设备，再通过通信组合结果。

**工程解释：** TP分担权重和计算，也在层内引入通信。头数与分片、量化kernel、互连和后端支持都影响可用性。两张16GB设备不自动变成一张32GB设备，每个rank仍要分别预算。

**工程分析：** 先看物理拓扑与通信，再跑分片加载、小请求和目标负载。RTX4080没有NVLink，不能按有桥接互连的假设部署。DP作为多个模型副本，更适合模型能独立容纳时扩展请求容量；MoE的EP则分布专家，另有路由与负载不均问题。见[多设备专题](chapters/performance/parallelism.md)。

### 张量切分为什么需要通信

可以把一次矩阵计算理解为多个设备各做一部分，再在需要的位置组合或交换结果。不同算子采用不同切法，有的输出继续保持分片，有的需要归约/聚合。通信频率、消息大小和互连会影响能否抵消分担计算的收益。

模型分片还要满足头数、量化布局和模型实现限制。TP2不是看到两张卡就必然支持。先检查框架对该结构的分片规则，再看每rank内存与实际通信日志，不能只加一个参数就推导速度。

## 3.8 PP：Pipeline Parallelism

**一句话解释：** 把不同层或阶段放到不同设备，按顺序传递中间结果。

**工程解释：** 单个请求经过多个阶段，阶段计算不均时会等待；多请求有机会填充流水线，但存在气泡和传输成本。PP与TP可按支持情况组合，节点数不直接决定唯一映射。

**工程分析：** 记录各阶段内存、计算和等待，比较满足延迟要求的吞吐。llama.cpp的层卸载与RPC不能直接按vLLM同名策略解释。AMD五机记录证明了短上下文容量路线可运行，没有单机基线，因此不计算多机加速比。

### 流水线气泡是什么

单个请求先经过阶段A，再经过B。B等待A、A等待下一次依赖时，就有空闲窗口；多个请求有机会交错填充，但短请求和不均匀层分配仍会留下气泡。为了内存可容纳而增加PP，可能付出额外单请求延迟。

原W7900双节点671B路线配置TP8×PP2。它描述一套16rank组合，实际阶段和设备放置还需要检查，不能把PP2直接等同于所有情况下的“正好每台一半”。embedding、输出头和不均匀层可能使某rank更先达到容量上限。

## 3.9 GGUF 是什么？

**一句话解释：** 保存模型张量与元数据的文件格式，常用于llama.cpp路线。

**工程解释：** GGUF可以保存不同精度与量化类型，包含架构和tokenizer等信息；它本身不是量化算法，也不是执行框架。Q4_K_M属于K-quant系列，K不解释为k-means，M不是模型参数规模。

**工程分析：** 源目录完整、转换器支持、GGUF完整、执行器支持和正确生成是不同关口。FP8转F16不会恢复已损失信息，特殊张量类型也可能在后端失败。操作见[转换教程](chapters/models/gguf-conversion.md)，质量与速度见[量化教程](chapters/models/quantization.md)。

### 文件能解析，为什么仍可能无法生成

执行器可能认识GGUF容器，却不认识其中模型架构；认识架构却缺某张量类型kernel；权重可以分配，warm-up才进入未实现算子。Mac type42故障说明文件、模型和后端支持必须分别成立。

同一个模型名还可能来自不同转换器或fork约定。保留源revision、转换commit、输出摘要与目标执行器，就能把“这个GGUF不能用”变成具体可定位的问题。

## 3.10 vLLM 与 llama.cpp 怎样选择？

**一句话解释：** 先筛选能够完成目标任务的组合，再比较资源、性能和维护成本。

**工程解释：** vLLM侧重服务调度与设备执行，llama.cpp侧重GGUF和多后端本地执行，但两者范围有交集。Intel还可验证OpenVINO路线，Apple可验证MLX。格式、模型结构、功能、设备kernel和交付条件必须共同满足。

**工程分析：** 按“任务功能→制品→设备→容量→质量→目标负载→维护”做决策。先完成同一最小任务，再比较长输入、并发、错误与恢复。高吞吐且没有完整答案的方案仍未通过。选型理由写进[项目复盘](04-project-review.md)，方便升级时重查。

推测解码、MTP、DFlash及更多优化属于第四层专题，见[推测解码](chapters/performance/speculative-decoding.md)。它们沿用相同原则：固定条件、保留质量与原始数据，再谈收益。
