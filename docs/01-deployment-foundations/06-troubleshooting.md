# 第六部分：故障排查速查表

[总目录](README.md) · [上一部分：知识库目录](05-knowledge-base.md) · [附录A：命令](appendices/commands.md)

## 6.1 先定位失败阶段

```text
安装 → 构建 → 设备初始化 → 读取模型 → 分配内存
 → 执行算子 → 模板/采样 → API → 并发与持续运行
```

找到第一次失败的位置，再向上下游检查。保存第一条异常及其前后的日志，后面的进程退出和连接断开往往只是结果。

## 6.2 快速查表

| 现象 | 常见检查方向 | 先做什么 | 通过标准 |
| --- | --- | --- | --- |
| wheel无法安装 | CPU架构、Python ABI、平台 | 看uname/Python/包标签 | 包与环境匹配 |
| 安装成功但无设备 | 驱动、后端wheel、设备权限 | 系统枚举，再框架小算子 | 真正完成计算与同步 |
| CUDA/HIP构建失败 | 编译器、目标架构、头文件、库 | 保存首个编译错误与CMake配置 | 目标二进制构建并可运行 |
| GPU被识别但kernel失败 | 模型精度、算子、架构目标 | 小模型/简单精度对照 | 目标模型完成生成 |
| 容器看不到设备 | 宿主驱动、容器Runtime、映射 | 宿主先验，容器再验 | 容器内小算子通过 |
| 模型加载失败 | 文件缺失、分片、架构、版本 | 校验manifest与加载错误 | 完整加载并生成 |
| 加载后warm-up OOM | 图、workspace、KV预分配 | 对照峰值与捕获阶段 | 目标配置ready且有余量 |
| 长输入/并发OOM | KV、prefill预算、活动序列 | 固定变量逐步增加 | 目标负载无OOM |
| 设备总内存异常偏小 | 后端预算、驱动、共享内存 | 对照物理/Runtime/GTT/TTM | Runtime可用量有依据 |
| 生成乱码/角色标记 | 模板、tokenizer、制品转换 | 最小官方格式请求 | 正文与停止正确 |
| 只有思考没有正文 | 输出上限、思考配置、解析 | 检查finish_reason与原始响应 | 完整答案符合任务 |
| HTTP404/错模型 | 端口、路径、别名 | health与models，再请求 | API路径和别名一致 |
| 非流式可用，流式卡顿 | SSE、代理缓冲、客户端 | 本机curl -N直连 | 分段到达且正确终止 |
| 吞吐升但体验差 | 排队、长度、ITL、缓存 | 分析TTFT与尾延迟 | 目标SLO下的有效吞吐达标 |
| 多卡挂起/慢 | 拓扑、通信库、P2P、切分 | all-reduce，再小模型 | 正确通信与目标模型运行 |
| NPU能枚举却不能生成 | 图编译、算子、形状、精度 | 看编译与生成的分界 | 生成真实token而非只编译 |
| Mac文本可用视觉失败 | 插件视觉能力与预处理 | 看具体版本和encoder错误 | 图片任务单独通过 |
| 持续运行变慢 | 温控、换页、泄漏、资源争用 | 同步记录频率/温度/内存 | 稳态性能可维持 |

每次修改只处理一个有证据的方向。不要看到“显卡不工作”就同时重装驱动、框架和模型，导致无法知道哪个改动有效。

## 6.3 GB10：架构正确，为什么仍会编译失败？

E01 保存了特定 vLLM 提交与 CUDA13组合的错误：

```text
Instruction 'cvt with .e2m1x2' not supported on .target 'sm_121'
```

它指向所编译指令与目标架构的兼容问题。源笔记使用过 `TORCH_CUDA_ARCH_LIST=12.0` 绕过特定路径，但这只是该提交的尝试，不能推广为所有GB10程序都设12.0。

排查顺序：确认设备计算能力 → 查看框架是否支持该架构 → 找到具体失败kernel与精度 → 核对CUDA和源码修复 → 只重建相关环境 → 完成模型运行。llama.cpp使用的 `CMAKE_CUDA_ARCHITECTURES` 与PyTorch变量也不能混为同一开关。

## 6.4 构建依赖缺失：CURL错误

E10 的GB10 llama.cpp记录出现过CURL开发头文件缺失。区分“系统有curl可执行程序”和“编译器能找到libcurl头文件与库”：前者不代表后者。

处理时查看CMake报错指向的依赖，在当前OS安装对应开发包，或按固定源码文档关闭确实不需要的功能。保留修改后的CMake输出，并重新构建。不要从其他系统随意复制一个 `.so` 填进运行目录。

## 6.5 AMD共享内存：先看谁限制了分配

E03 中物理容量够大，但设备约识别63GB，一次约87GB分配失败；TTM实际限制比GTT请求值低。正确路径是比较三层：系统物理内存 → 驱动/内核预算 → HIP看到的可分配量。

```bash
free -h
rocminfo > rocminfo.txt
```

再按该驱动版本读取可用的GTT/TTM与设备日志。修改内核、DKMS或驱动之前先确认根因和恢复方式，本知识体系不提供一套适用于所有机器的GRUB改写脚本。

修复后先检查设备可见总量，再小模型，再目标模型短输入；最后补长上下文和API负载。容量问题修复不自动证明多机性能达标。

## 6.6 Intel：设备枚举、编译和生成要分开

E02 中OpenVINO能枚举NPU，但INT4编译失败；INT8运行420秒被超时终止，exit124。exit124说明外层超时，不是输出token的速度。

排查要记录：插件版本、模型IR、精度、输入形状、编译错误、是否生成过token。通过GPU路线运行同一任务可帮助区分模型材料与NPU执行问题，但不能证明NPU必定支持。

另一条“GGUF + OpenVINO”尝试在 `CPY/cache_r` 等路径失败，而配套IR + GenAI GPU成功。两条路线的制品和执行器不同，不要只换设备字符串继续比较。

## 6.7 Mac：编译成功但模型失败

E05 的特殊分支可以编译，但特定FP4/FP8模型触发 `Asserting on type 42`。先确定GGUF张量类型和Metal kernel实现，再判断是模型文件不完整还是当前后端缺支持。

同组资料中vllm-metal有明确错误：

```text
NotImplementedError: Multimodal encoder execution is not wired on Metal yet.
```

这指向该版本视觉能力缺口。修改图片URL、增加上下文或提高内存不能补出缺失encoder。记录文本可用、视觉未通过，选择支持该任务的路线。

## 6.8 API成功但结果不可用

检查HTTP状态 → JSON结构 → `finish_reason` → 思考/正文 → 任务答案。推理模型达到token上限时可能仅有思考；结构化输出可能是合法JSON但语义错误。

如果原始响应有正文而应用没有，检查客户端解析；原始响应就没有正文，则检查模型模式、模板和输出预算。先保存响应原件，不要用UI空白直接判断模型坏了。

Intel短生成记录停在思考阶段，就是应保留的质量边界：速度字段有值，不代表业务答案已完成。

## 6.9 多请求为什么首token很慢？

先分解排队、prefill和传输。E01的200请求突发中，服务活动序列预算为4，平均TTFT约148秒。应先看等待队列与到达模式，再分析每条输入处理时间。

可以依次做：单请求同长度 → 固定并发扫描 → 控制到达率 → 突发恢复。只有并发上升时变慢，优先检查容量和调度；单请求也慢，再查后端、输入长度和kernel。

## 6.10 多设备通信失败

先保证每个设备单独计算正确，再运行[通信检查脚本](examples/all_reduce_check.py)。检查设备数、rank、网络接口、通信库与拓扑，不以“所有进程都启动了”判断通信正确。

llama.cpp RPC另查worker端口、主机能否连接、后端是否初始化、各节点模型分配与网络路径。编译包含RDMA不等于运行时实际使用RDMA；缺单机基线时不计算加速比。

## 6.11 每次排错留下什么？

保留最小触发输入、版本与最终命令、第一次错误、资源状态、排查依据、修复项、复测结果和回滚方式。公开时只保留必要脱敏内容。

故障修复后，至少复跑最小请求与原触发输入；改动底层组件时增加对应功能与目标负载回归。把可复用结论回填到知识层，完整过程保存在[项目复盘](04-project-review.md)。
