## 1. 框架选型看工作负载

| 工具方向 | 可优先验证的场景 | 额外检查 |
| --- | --- | --- |
| llama.cpp / llama-server | GGUF、离线、跨后端、CPU/GPU 混合、小型共享服务 | 槽位/KV 配置、目标算子、模板、并发尾延迟 |
| vLLM | GPU API、调度、多卡、批量和并发服务 | 模型/后端/量化、KV 容量、运行时与编译 |
| SGLang | 需要缓存复用、结构化生成和复杂 serving 的部署 | 实际模型、路由、缓存行为与监控 |
| TensorRT-LLM 等 | 特定 NVIDIA 模型/硬件的性能工程 | 引擎或运行时路线、构建成本、版本与维护 |
| MLX-LM / OpenVINO GenAI 等 | 特定端侧平台 | 制品、设备代际、框架 API 与应用集成 |
| Ollama / LM Studio 等 | 快速体验、模型与服务管理 | 底层引擎、版本、隐含模板与实际参数 |

这些不是排名。llama-server 有持续批处理和 HTTP API，并非只能单人使用；vLLM 有 CPU 和硬件插件路线，并非只能 NVIDIA。SGLang 是推理/服务框架，不能简单等同于业务 Agent 编排系统。以兼容性、质量、目标延迟、运维成本和交付约束选择候选，再测量。

## 2. 持续批处理解决什么问题

普通固定批次若必须等最长请求结束，短请求完成后空出的资源不能及时用于下一请求。持续批处理在迭代边界释放已完成序列，并插入新序列，提高不同长度请求混合时的利用效率。

它也带来竞争：一个人独占设备时的 Decode 很快，多个请求共享后每个请求可能变慢，而总输出吞吐变高。工程目标应是规定延迟内完成更多合格请求，而非让 batch 无限增大。排队、KV 容量与公平性都需要考虑。

## 3. llama-server 的四种“大小”

`-np/--parallel` 是服务槽位数量；`-c/--ctx-size` 与上下文和 KV 容量有关；`-b/--batch-size` 是 logical token batch；`-ub/--ubatch-size` 是 physical microbatch。它们不是同一个并发开关。

旧版本或特定配置会将总上下文分给槽位，例如 `-c 8192 -np 2` 可能得到每槽约 4096；但这个算例不能作为所有版本的规则。当前主线还出现统一 KV、自动槽位与 `--kv-unified-per-slot` 等配置。应以固定 commit 的帮助与启动日志核对每请求限制、总池容量及实际分配，不将新参数照搬进旧 Case。

调优建议从 `-np 1` 开始，把输入+生成上限控制在已核对的容量内。然后同时扩大服务槽位与客户端并发，比较请求排队、内存、首段输出与总吞吐。只增加客户端并发而不确认服务有效槽位，会把排队变化误当成模型计算变化。

`-b/-ub` 不表示几个人同时请求。较大 microbatch 可能改善长输入效率，但增加临时空间和单次调度占用。确定它们的收益需要长短输入、多并发以及内存峰值对照。

## 4. vLLM 的核心容量参数

| 参数 | 主要含义 | 常见误读 |
| --- | --- | --- |
| `--max-model-len` | 单序列支持的总长度上限 | 不是仅输入长度，也不是越大越好 |
| `--max-num-seqs` | 一轮可调度的序列数上限 | 不代表所有这些请求都会按时完成 |
| `--max-num-batched-tokens` | 一轮调度的 token 预算 | 与序列数、输入长度是不同维度 |
| `--gpu-memory-utilization` | 执行器内存预算比例 | 不是计算利用率，也非整机隔离保证 |
| `--tensor-parallel-size` | 层内张量分片规模 | 不是副本数，也不保证线性加速 |

服务先处理请求上限，再由调度器在 KV、序列数和 token 预算内安排工作。出现重计算/抢占时，降低占用、调整调度或增加资源可能有效；单纯抬高最大请求数通常会加重尾延迟。

以下是 **Linux、已匹配驱动的受支持 GPU、完整且兼容的本地模型目录** 的小规模起点，值均为示例，不是为 27B Q4 验证过的配置。先根据官方安装矩阵选择版本和环境，不在 llama.cpp 构建环境中随意混装依赖。

```bash
: "${VLLM_VERSION:?先选择与设备及模型匹配的确切版本}"
python3 -m venv /mnt/workspace/vllm-lab-env
source /mnt/workspace/vllm-lab-env/bin/activate
python -m pip install "vllm==$VLLM_VERSION"
python -m pip freeze > /mnt/workspace/vllm-requirements-observed.txt

vllm serve /models/served-model \
  --served-model-name edge-model \
  --host 127.0.0.1 --port 8000 \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.85 \
  --max-model-len 4096 --max-num-seqs 4 \
  --max-num-batched-tokens 2048 \
  --enable-chunked-prefill
```

模型目录需自行准备，不应把 llama.cpp 的 GGUF 路径直接替代这一示例目录。vLLM 的 GGUF、量化及不同硬件支持有单独条件。`trust_remote_code` 只在确需模型自定义代码、确认来源并审查后开启，不作为加载失败的通用修复。

## 5. Chunked Prefill：平衡长输入与正在输出的请求

长 Prefill 若独占较长执行时间，正在 Decode 的请求会暂时无法输出。分块 Prefill 将输入计算拆成片段，与 Decode 组合调度。代价是长输入可能经过更多调度轮次，自己的 TTFT 不一定变好。

vLLM V1 在可用场景中通常默认启用分块 Prefill，具体版本核对官方说明。较小 token 预算可能改善 ITL，但拖慢大输入进入；较大预算可能改善输入处理，却占用更多工作区和执行时间。实际收益由请求组合决定，不能预设 2048 或 8192 是通用最佳值。

## 6. 前缀缓存：复用相同 token 前缀

公共 system prompt、工具定义或固定文档前缀可以复用已计算 KV。匹配依据是 token 及实现所需配置，不是语义相似。把每次变化的时间戳放在前部，可能破坏后面大段内容的共享；把变化部分放到后面有时有利，但不能改变任务语义或权限边界。

缓存减少部分重复 Prefill，不会替代新 token 的生成。缓存占内存，也会被驱逐；冷、暖缓存测试应分开。服务不同用户时，还需考虑缓存隔离、信息泄漏风险和计费/观测口径，不能为了命中率跨权限拼接上下文。

评测至少包含无公共前缀、固定公共前缀、前缀长度变化三种负载。记录命中 token 或服务提供的命中指标，不能只看第二轮快了就认定是前缀缓存；页缓存、编译缓存和预热也会产生相似现象。

## 7. 图捕获、编译缓存与冷启动

CUDA Graph/编译优化可减少运行期开销，但带来初始化时间、额外内存与形状限制。`--enforce-eager` 等模式可作为定位编译/捕获问题的实验，不应未经测量就作为最终最佳配置。

冷启动时间、首次模型请求、稳定运行延迟是三个指标。预先编译可能提高稳态表现却拉长首次启动，适合常驻服务，未必适合频繁唤醒的端侧应用。缓存与模型、后端、配置、编译器或驱动绑定，升级后不能假定继续有效。

## 8. 接口兼容性要按能力验证

“OpenAI 兼容”通常表示部分 API 协议约定相近，不代表模板、tool calling、JSON Schema、推理字段、多模态输入、usage 与错误码完全相同。为实际业务使用的字段写验收样例，检查客户端取消和流结束。

最小服务验收顺序是健康 → 模型列表 → 非流式短请求 → 流式请求 → 边界请求 → 业务格式。服务绑定地址、代理与鉴权由部署环境决定，本地调试从回环地址开始。把模型生成的工具参数交给应用校验，模型输出本身不是执行权限。
