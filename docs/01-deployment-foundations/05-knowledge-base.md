# 第五部分：个人知识库目录设计

[总目录](README.md) · [上一部分：项目复盘](04-project-review.md) · [下一部分：故障速查](06-troubleshooting.md)

知识库按本体系的五层分类，项目按部署执行顺序记录。概念负责解释原因，项目负责保存实际发生的过程，实验负责比较，故障负责缩短下次排查时间。

## 5.1 一级目录与内容边界

```text
大模型部署适配/
├── 00-总地图与入口
├── 01-硬件后端适配
│   ├── NVIDIA-CUDA
│   ├── AMD-ROCm-HIP-Vulkan
│   ├── Intel-OpenVINO-SYCL
│   ├── Apple-Metal-MLX
│   └── NPU与其他平台
├── 02-模型格式与量化
├── 03-推理框架与服务
├── 04-显存与性能
├── 05-工程交付
├── 06-项目记录
├── 07-实验与数据
└── 08-故障与版本变更
```

平台条目只保存平台特有知识；共同的KV公式、指标和API检查只写一处，再用链接引用。避免每个平台都复制一份“vLLM基础”，后来出现多套不同定义。

## 5.2 每个知识点按七个问题记录

### 1. 它是什么？

先写一句可直接理解的解释，再给必要的技术定义。例如“Chunked Prefill把长输入分块调度，减少一次prefill占用预算对其他请求的影响”。

### 2. 解决什么问题？

写实际触发条件：长输入占用工作区、短请求流式受干扰等。不要只写“提高性能”，要能判断什么时候值得尝试。

### 3. 在项目哪里用到？

链接项目、版本和请求阶段。例如用于prefill调度，而不是模型下载或权重转换。没有做过的条目标为官方资料整理或待验证，不写实测结论。

### 4. 常用参数有哪些？

记录固定版本的参数名、含义、默认值来源、依赖条件与影响。默认值没有核对时不凭记忆填写。相关参数相互影响时一起解释。

### 5. 常见故障是什么？

描述现象、阶段和影响：构建失败、加载失败、长输入OOM、TTFT高、质量错误等。不要把“GPU不兼容”作为所有错误的统一结论。

### 6. 怎样排查？

按底层到上层列最短路径：环境 → 设备 → 框架 → 制品 → 单请求 → API → 负载；附只读检查、最小复现与成功标准。

### 7. 怎样用数据证明？

提供输入、参数、原始结果、统计代码、质量和限制。数字写单位和计时边界。只有汇总笔记时注明历史转录，不把它升级成完整可复现实验。

## 5.3 一份条目示例：Prefix Cache

```text
名称：Prefix Cache
所属层：推理框架 / 显存与性能
定义：复用相同token前缀的状态，减少重复prefill。
适用：请求反复包含相同长系统提示或文档。
条件：框架支持；模板/token前缀一致；缓存能保留。
参数：记录当前版本开关及命中统计方式。
验证：冷前缀、重复前缀、不同前缀分组；固定长度和采样。
检查：TTFT、命中情况、资源；首轮单独统计。
故障：未命中、缓存挤出、命中但负载瓶颈在decode。
证据：项目run-id、请求、原始响应、服务指标。
限制：不把重复缓存题成绩代表新文档首次处理性能。
```

这是条目结构示例，没有附一次新的缓存实测结果。

## 5.4 项目、实验与故障怎样互相链接？

```text
概念条目：解释是什么、何时用
    ↓ 引用
项目记录：说明设备、模型、链路与最终结论
    ↓ 引用
实验记录：保存基线、单变量、原始数据与统计
    ↓ 遇到问题时引用
故障条目：触发条件、根因、修复、回归
```

一个实验可以用于多个概念，但数据只保留一个权威位置。本文的来源索引也是这种组织：正文解释知识，evidence集中保存历史实例条件和数字。

## 5.5 如何标记记录状态？

| 状态 | 含义 | 可写什么 |
| --- | --- | --- |
| 官方资料 | 已阅读文档，当前设备未测 | 支持说明和计划，不写本机速度 |
| 已编译 | 产物构建成功 | 构建结论，不写模型已运行 |
| 冒烟通过 | 小输入生成完成 | 对应短请求功能 |
| 部分通过 | 某功能/设备/长度可用 | 明确通过范围与失败项 |
| 已测基线 | 条件和结果已保存 | 该负载下的指标 |
| 可复现交付 | 环境、输入、代码、证据和验收齐全 | 按明确步骤复查的结论 |
| 待补证据 | 有历史汇总，原始文件不全 | 保留参考，不承诺精确复现 |

不要把不同状态都标成“完成”。例如vllm-metal文本可用、视觉未接通，应写部分通过；Intel NPU编译超时应写未通过该组合。

## 5.6 旧笔记怎样整理？

先保留原稿，再提取到对应知识层。检查过时安装方式、互相矛盾的版本、无法追溯的速度、失败输出和敏感内容。修订结论时链接实际依据。

同一篇包含安装、量化、服务和压测，可以保留完整项目文档，再把概念提炼到各层；不要把项目拆成零散代码后丢掉运行顺序。

原稿中的“GGUF是一种量化”“K是k-means”“物理内存等于GPU可用内存”“双4080安装NVLink”等表达已在本体系修订，详见[附录B](appendices/references.md)。

## 5.7 版本与维护

重要条目写更新时间、适用版本和来源。新框架改变参数时，更新当前命令；旧实验仍保留旧环境。模型revision或tokenizer变化时，重新检查输入长度、模板、质量和结果可比性。

维护从项目触发：部署时遇到新问题再补知识，实验形成结论再更新条目。不需要为了目录完整，给没有实践和资料依据的平台补一段泛泛结论。

## 5.8 私有知识与公开仓库

公开条目只保留工程必要信息：通用设备型号、公开版本、模型与许可、脱敏输入、命令模板和可公开结果。私人空间链接、账号、实际节点地址、路径、业务原始材料和授权信息不进入仓库。

公开摘录使用独立来源编号，不暴露私有页面标识。没有公开输入授权的图片/音频不转存；可用明确标注的教学样例说明操作，但不能假称该样例产生了历史成绩。

知识库最终应帮助你快速找到：这个问题在哪一层、以前哪次遇到、当时怎样验证、现在能复用哪些材料。具体检查入口见[故障速查](06-troubleshooting.md)。
