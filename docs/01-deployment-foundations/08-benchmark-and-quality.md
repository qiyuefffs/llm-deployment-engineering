# 08 压测设计、指标口径与质量验收

[返回总目录](README.md) · [上一章](07-serving-and-scheduling.md) · [下一章](09-profiling-and-optimization.md)

## 1. 先写问题，再选择压测工具

“模型能跑多快”至少包含三类问题：引擎执行是否高效、服务在并发下能处理多少请求、应用答案是否及时且可用。`llama-bench` 适合引擎计算；HTTP 流式负载适合服务；任务样例与自动/人工判定负责质量。一个工具不能自动覆盖全部问题。

压测前写清假设，例如“打开某 Attention 实现能否降低长输入 Prefill 时间且不破坏短请求延迟”。它决定固定哪些输入、测什么指标、如何确认实际实现生效，以及什么结果算失败。

## 2. 指标的可操作定义

| 指标 | 建议定义 | 必须说明 |
| --- | --- | --- |
| TTFT | 客户端发出请求到收到首个有效模型内容 | 是否含网络/排队；内容还是最终答案；空帧排除规则 |
| E2E | 发出请求到正常流结束/响应完成 | 包含什么前后处理；超时与取消怎样计数 |
| TPOT | 一条请求首输出后，平均每个后续 token 耗时 | 实际输出 token 数、是否含推理 token |
| ITL | 连续两个生成 token 的时间间隔 | 客户端可能只能观察片段，不能假装逐 token |
| 输出吞吐 | 成功请求实际输出 token 总数 / 统一测量墙钟时间 | 测量窗起止、失败请求 token 是否计入 |
| 请求吞吐 | 完成请求数 / 测量墙钟时间 | 长度分布、成功定义、队列是否排空 |
| Goodput | 满足质量/延迟等预设条件的请求数 / 测量时间 | 门槛必须在实验前声明 |
| 资源 | 峰值/常驻 RAM、VRAM、功率、温度等 | 工具、采样间隔、设备域、是否漏峰值 |

当 N≥2 且计时边界一致时，常见请求级估算为：

```text
TPOT ≈ (E2E - TTFT) / (N_output - 1)
```

若 E2E 包含较多流结束/传输开销，此式得到的是客户端近似值。最好同时保存最后内容时间和正常完成时间。N=0/1 时记为不适用，不用 0 掩盖。

**演算示例，非实测：**TTFT=1 秒，完成时间=6 秒，输出 101 token，则 TPOT≈50 ms/token，对应后续平均约 20 token/s。这不等于系统总吞吐。并发时不能将每个请求的 `N/E2E` 简单相加，代替整个实验窗口内的服务吞吐。

## 3. SSE 测量最容易出现的错误

第一个 SSE 事件可能只包含角色、心跳或空内容。一个内容片段也可能包含多个 token；最后 usage 块可能没有文本。因此先定义有效内容字段，区分 `content`、推理字段和 tool call 参数，不能只统计事件数。

优先使用服务提供且语义明确的 token usage，必要时用匹配分词器核对完整输出。把每个片段独立分词后相加不一定等于对完整文本分词，因为片段边界会改变切分。客户端只能测片段间隔时，报告为“片段间隔”，不要标成精确 ITL。

请求耗时使用单机单调时钟；跨机器日志关联另需时钟同步和 request ID。服务端生成速度与客户端 TTFT 不同，反向代理缓冲、网络和客户端解析都会影响后者。

## 4. 闭环并发与开放到达率

闭环测试保持 C 个客户端活跃：一个请求结束后再发下一个。它适合寻找交互并发容量；服务变慢时，发送速率也随之下降，容易隐藏外部流量持续到来的排队压力。

开放测试按到达速率发请求，通常需要指定恒定间隔或到达分布与随机种子。服务跟不上时队列持续增长。要记录实际发出速率、排队位置、超时和客户端是否本身限速，不把工具卡住造成的低负载误认为服务稳定。

并发数与 req/s 不是同一个负载参数。Little's Law 在稳定、统计边界一致时给出 `平均在途数 = 到达/完成速率 × 平均停留时间`，可用于一致性检查；饱和且队列无限增长时不能拿它推导稳定容量。

## 5. 建一张有业务意义的负载矩阵

| 维度 | 起点样例 | 目的 |
| --- | --- | --- |
| 输入长度 | 短、中、长、接近上限 | 区分 Prefill 与上下文边界 |
| 输出长度 | 短回答、长生成 | 区分 Prefill/Decode 占比 |
| 并发 | 1、2、4，之后按设备容量增加 | 找到延迟拐点与有效并发 |
| 内容 | 中文、代码、结构化任务 | 覆盖分词与格式差异 |
| 缓存 | 无共享、公共前缀、冷/暖 | 识别复用收益与偏差 |
| 设备状态 | 冷机、暖机、持续运行 | 观察编译、页缓存与温控 |

这些是设计维度，具体数值由需求与资源决定。每一格都记录**实际**输入和输出 token，不只记录 `max_tokens`。固定生成长度的合成测试便于比较计算，但真实应用应保留 EOS、截断与思考预算；两类结果分别解释。

先做少量预检，确认服务稳定、输出合理、没有超限；然后保存基线。可按 A-B-B-A 或交替顺序多轮测量，降低温度与时间漂移影响。重复次数依据波动决定，不把某一轮最好值当成最终结果。P99 需要足够样本支撑，小样本的极端分位数应明确局限。

## 6. llama-bench 引擎测试模板

下面在 [05](05-llama-cpp-practice.md) 的源码目录中运行，要求已有 CUDA 构建及该模型容量。它不会请求 HTTP 服务，也不证明对话质量。

```bash
./build-cuda/bin/llama-bench \
  -m ../models/model.Q4_K_M.gguf -ngl 99 \
  -p 512,2048 -n 128 -r 5 -o json \
  > ../results/engine-baseline.json 2> ../logs/engine-baseline.log
```

通常 `pp512/pp2048` 和 `tg128` 对应不同测试项，**不能默认 tg128 就是接在 2048 token 历史之后**。长历史 Decode 需要核对该版本的组合/深度测试参数（如 `-pg`、`-d`）或使用固定历史的服务测试。保存工具帮助与 JSON 字段解释后再汇总。

比较 Flash Attention 时固定其余参数，按该版本显式使用 `-fa on/off`，并从日志确认实现。CPU 比较需用对应二进制与设备设置；线程、batch 和量化也属于对照变量。

## 7. vLLM HTTP 测试模板

以下针对 [07](07-serving-and-scheduling.md) 的本地服务；要求安装版本支持相应选项。模型别名与真实 tokenizer 目录分开指定，防止 benchmark 用错分词器。

```bash
vllm bench serve \
  --backend openai-chat --host 127.0.0.1 --port 8000 \
  --endpoint /v1/chat/completions \
  --model edge-model --tokenizer /models/served-model \
  --dataset-name random --num-prompts 100 \
  --random-input-len 1024 --random-output-len 256 \
  --max-concurrency 4 --save-result \
  --result-dir /mnt/workspace/edge-llm-lab/results
```

合成 random 数据主要用于性能特征测量，不是业务质量评测；实际 token 长度、EOS、模板和输出需看工具报告。100 次只是演示命令的起点，不是长期可用率或 P99 的认证。通用 `wrk/hey` 统计 HTTP QPS 时，若没有正确解析 SSE，就不能自动提供有效 TTFT/ITL。

## 8. 保存原始记录，之后才能重算

每条请求建议至少记录以下字段；`null` 表示尚未测量，不是一个真实运行样本：

```json
{
  "run_id": "待填", "request_id": "待填", "input_id": "待填",
  "input_tokens": null, "output_tokens": null,
  "request_start_monotonic_s": null,
  "first_content_monotonic_s": null,
  "last_content_monotonic_s": null,
  "request_end_monotonic_s": null,
  "http_status": null, "finish_reason": null,
  "error_type": null, "quality_pass": null
}
```

另存模型/框架/启动参数、负载配置、随机种子、输入文件哈希、响应、客户端版本与资源采样。包含敏感内容时，响应按权限存储；公开包提供脱敏可复现样例和脱敏规则。统计成功/失败/超时/取消时，分母用全部已发请求并分别列出，避免只筛选成功请求后宣称“全部成功”。

## 9. 质量与异常验收

最小质量集应覆盖真实目标任务、结构化字段、数字/实体保持、长上下文、多轮角色和输出完整性。代码任务可检查测试执行结果；JSON 抽取可检查 schema 与字段值；问答需要事实或引用标准。生成有效 JSON 与字段内容正确是两道检查。

异常至少覆盖超上下文、非法 JSON/消息、错误模型名、客户端取消、服务繁忙和设备内存不足。观察错误是否可解释、服务是否恢复、是否遗留状态。测试输入可以生成，但生成过程和判定规则应公开；不要把随机 prompt 的成功率写成真实任务准确率。

验收前声明 SLO，例如“指定输入分布下 TTFT、TPOT 与成功率需达到项目门槛”。具体门槛由业务决定，本文不虚构数字。若优化提升吞吐但破坏 SLO，需降低并发、改队列策略或拒绝该配置。

## 10. 端侧还要测能耗和持续性

任务能耗可由相同测量边界的功率积分得到，报告 J/任务或 J/输出 token；有空闲基线时分别说明总能耗与扣除空闲后的增量能耗。GPU 板卡功率不等于整机功率，手机电池电流也未必有足够精度。

持续测试记录每个时间窗的延迟、吞吐、温度、时钟和功率。出现速度下降时对齐时间轴，区分温控、内存压力、缓存变化与其他进程。采样工具会引入开销，应说明方法，并避免将 profiler 开启时的性能混入正常基线。

**本章产物：**负载定义、预热/缓存说明、逐请求原始文件、质量与异常记录、资源时间线、带口径的汇总表。只有汇总截图，没有原始记录，就无法复查多数性能结论。
