# 端侧大模型部署适配与推理优化：工程知识体系

把一个模型部署到设备上，需要连续回答五个问题：**能否正确运行，资源是否够用，性能是否达标，长期运行是否稳定，其他人能否接手维护。** 本知识体系围绕这五个问题展开，面向大模型部署工程师、推理优化工程师和多硬件适配工程师。

这里保留原稿的“一条主线、五层能力、七个工程模块”，展开原理、计算、操作、排查和交付。以本仓库已有的 **GGUF / Q4、llama.cpp、GPU Notebook 部署与性能对照** 为实践入口，再解释如何迁移到桌面、移动设备和其他硬件。云端 GPU 适合建立基线和验证方法；端侧结论需要在目标终端重新测量，尤其是统一内存、功耗和温度限制。

第一次建议按顺序阅读；遇到具体问题，从导航进入对应章节。这里的命令是带前提的工程模板，算例是明确标注的理论计算。章节不新增硬件实测结果，也不把官方能力介绍写成作者已经完成的适配经历。实测 Case 独立存放在 [cases/](../../cases/README.md)。

## 一条工程主线

```mermaid
flowchart LR
    A[需求与验收门槛] --> B[硬件和模型兼容核对]
    B --> C[模型制品与内存预算]
    C --> D[最小正确推理]
    D --> E[服务与性能基线]
    E --> F[瓶颈假设与对照实验]
    F --> G[质量及稳定性回归]
    G --> H[部署包与监控交付]
    G -->|未达标| B
```

优化目标应当写成“在指定设备和输入分布下满足质量、延迟、资源限制”。不能仅写“提高 tokens/s”。端侧特别需要同时记录冷启动、长时间性能、峰值内存、温度和能耗；瞬间峰值速度不足以代表实际体验。

## 原图需要结合正文理解的地方

| 容易误读的内容 | 本文采用的工程定义 |
| --- | --- |
| GGUF、AWQ、GPTQ 并列为格式 | GGUF 是容器；AWQ/GPTQ 是量化方法；还需区分精度、布局和 kernel |
| “vLLM 服务化、llama.cpp 端侧” | 这是常见起点；llama-server 也能服务化，vLLM 也有 CPU 与插件路线 |
| `TPOT / ITL` 放在同一指标框 | 请求平均 TPOT 与逐 token 间隔不同；SSE 片段也不一定是一个 token |
| “提高 GPU 利用率”作为结果 | 利用率是观察项；结果应是质量合格、延迟达标、吞吐或能耗改善 |
| “支持该后端” | 需要具体到版本、芯片、架构、算子、精度、上下文和 API 能力 |
