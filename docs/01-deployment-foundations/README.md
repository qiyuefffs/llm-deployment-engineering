# 第 1 章：大模型部署基础知识——从硬件适配到性能验收

部署工程师要解决的问题，可以先记成五句：**能不能运行、内存够不够、回答是否正确、性能是否达标、服务能否稳定交付。**

本章把原有知识清单收敛成一条工程主线。适合先花 15～20 分钟建立全貌，再通过 [llama.cpp 实战](../../cases/llama-cpp-flash-attention/CASE.md)理解参数和指标。这里的估算都是说明概念的例子，不是新增实测结果。

> 更新与资料核对日期：2026-10-17。支持矩阵、默认参数和命令以所用框架的固定版本为准；本章不提供一套适用于所有设备的启动参数。

## 2. 一条请求经历了什么？

用户发送问题后，服务先做接入、校验和排队，再把文本转换成 token，交给模型处理。理解下面两个阶段，才能读懂性能指标：

- **Prefill（处理输入）**：计算输入上下文，准备注意力缓存。输入越长，通常需要越多计算；命中可复用的前缀缓存时，部分计算可以省去。
- **Decode（逐步生成）**：根据已有上下文继续生成 token，直到结束或达到输出上限。小批量时常受权重读取和显存带宽影响；大批量或不同模型下也可能受计算、KV 访问或通信限制。

**KV Cache** 保存历史 token 的 Key 和 Value，后续生成时复用，避免每一步都重新计算完整历史。它仍要占用内存；缓存越多，并不等于服务越快。

```text
接入与排队 → 分词 / 预处理 → Prefill → Decode → 流式返回 → 完成与记录
                           ↕ KV Cache
```

客户端的首段输出等待时间还包括网络、排队和前处理。对推理模型，要区分“开始输出推理内容”与“开始输出最终答案”；首个 SSE 事件、首个非空文本片段和首个模型 token 也可能是不同时间点。

## 3. 兼容性要沿着一条链检查

同一张卡能被系统识别，不代表目标模型已经得到框架支持。按下面顺序核对，比直接换启动参数更有效：

**设备与操作系统 → 驱动 / 运行库 → 框架版本与后端 → 模型架构 → 精度与算子 → API 功能。**

| 平台 | 先认识的组件 | 工程上要核对什么 |
| --- | --- | --- |
| NVIDIA | CUDA、cuBLAS、NCCL | GPU 代际、驱动兼容、实际 kernel、卡间连接 |
| AMD | ROCm、HIP、RCCL | 具体 GPU 是否在支持列表、镜像与运行库是否匹配 |
| Intel | XPU、SYCL / oneAPI、OpenVINO | 目标是 CPU、GPU 还是 NPU；采用哪个执行后端 |
| 昇腾 | CANN、HCCL、框架插件 | 驱动 / 固件、插件与框架版本、模型和算子支持 |
| 摩尔线程 | MUSA 工具链与相关后端 | 当前版本支持的模型、精度、算子及构建方式 |
| Apple Silicon | Metal、MLX | 统一内存容量、系统版本和所选引擎支持 |
| CPU / 其他端侧设备 | CPU 指令集、BLAS、Vulkan 等 | 内存、带宽、GPU 驱动及混合卸载的成本 |

这是一张排查入口表，不是所有模型与精度都已支持的承诺。vLLM 的硬件能力既包括主仓库支持，也包括独立硬件插件；llama.cpp 的后端覆盖较广，但支持某个后端也不代表所有算子和量化类型都能加速。[1][2]

NVIDIA 设备先查看 `nvidia-smi`；涉及本地编译时再查 `nvcc --version`。两者的 CUDA 版本含义不同：前者表示驱动报告的兼容能力，后者是编译工具链版本。预编译框架还可能携带自己的 CUDA 运行库，不能只比较两个数字就判断是否可运行。

模型加载失败时，先看具体缺失的架构、权重、依赖或算子。`trust_remote_code` 允许执行模型仓库里的自定义代码，应在确有需要并审查来源后启用，不能作为所有加载错误的通用修复。

## 4. 分清文件格式、数值精度和量化方法

旧知识图把这些概念放在同一层，容易形成“换个文件后缀就能变快”的误解。它们分别回答不同问题：

| 类别 | 例子 | 回答的问题 |
| --- | --- | --- |
| 文件 / 模型表示 | safetensors、GGUF、ONNX、OpenVINO IR | 权重、元数据或计算图如何保存和加载？ |
| 数值表示 | FP16、BF16、FP8、INT8、INT4、MXFP4、NVFP4 | 数值如何编码，硬件有没有相应计算能力？ |
| 量化方法与实现 | AWQ、GPTQ、GGUF 的 Q4_K_M 等配置 | 怎样压缩、如何分组 / 校准，加载时使用哪个 kernel？ |
| 优化工具 | LLM Compressor、Model Optimizer、bitsandbytes 等 | 用什么工具生成或加载目标量化模型？ |

FP16 / BF16 常作为部署精度基线，不能全部归为“量化算法”。AWQ / GPTQ 是量化方法，GGUF 是文件格式；GGUF 可以保存不同精度的张量。Q4_K_M 等配置还包含混合精度、分组和元数据，实际文件不等于“每个参数恰好 4 位”。

工程上先问：**这个模型结构 + 这份量化权重 + 当前硬件 + 当前框架，是否有可用且合适的执行实现？** 再验证目标数据上的质量和性能。INT4 占用更小，也可能因反量化或 kernel 效率而更慢；FP8 / FP4 能否受益取决于设备与实现。vLLM 官方提供按硬件区分的量化兼容表，应随项目版本一起核对。[3]

量化验收至少保留一组真实任务的基线与量化输出，比较正确性、结构化字段、工具调用或长上下文任务。模型能生成文字，只能证明基本运行链路可用。

## 5. 推理框架怎样选？

先写下设备、模型、请求长度、并发和交付约束，再选框架。下面是常见起点，不是速度排名：

| 方向 | 可优先验证的工具 | 选择理由与边界 |
| --- | --- | --- |
| GGUF、本地离线、CPU + GPU 混合推理 | llama.cpp | 部署组件较轻，后端广；也有 HTTP 服务、并发槽位和持续批处理，并非只能单人使用 |
| 多用户 API、GPU 调度、分布式服务 | vLLM、SGLang | 重点验证目标架构、缓存、调度、并行和监控；两者都能用于常规服务 |
| NVIDIA 环境的专项性能工程 | TensorRT-LLM 等 | 根据特定模型与硬件验证构建、精度和运维成本，不预设其一定最快 |
| 快速桌面体验 | Ollama、LM Studio 等 | 适合先验证可用性；做性能对照时仍需记录底层引擎和有效参数 |
| Apple 设备 | llama.cpp、MLX 生态等 | 依据设备内存、模型支持和应用集成方式实测 |

vLLM 与 SGLang 都有前缀复用、调度和多卡能力；SGLang 的 RadixAttention 也不能理解为业务层 Agent 编排工具的替代品。llama-server 已有持续批处理、监控、结构化输出和推测解码等功能，具体以版本文档为准。[2][4]

## 6. 显存先算预算，再看实际分配

可以先把设备内存拆成四部分：

```text
总占用 ≈ 常驻权重 + KV Cache + 中间张量 / 工作区 + 框架 / 图 / 通信开销
```

密集模型的权重粗估：FP16 / BF16 为“参数量 × 2 字节”，INT8 为“× 1 字节”，理想 4 位为“× 0.5 字节”。还没计入量化比例因子、混合精度和元数据。

例如 27B 参数按理想 4 位计算约为 **13.5 GB（十进制）≈ 12.6 GiB**，这不是实际 GGUF 文件大小，也不是服务显存需求。现有 Case 的实际文件约为 16.8 GB，仍需额外留出 KV Cache 和运行开销。

对普通全注意力 Transformer，可用下面的式子估算**未分片时实际缓存的 KV 数据量**：

```text
KV 字节数 ≈ 2 × 层数 × KV 头数 × 每头维度 × 每个元素的字节数 × 缓存 token 总数
```

其中 `2` 代表 K 和 V。GQA / MQA 应使用 **KV 头数**，不能直接用查询头数或 hidden size 替代。例如 32 层、8 个 KV 头、每头 128 维、BF16，每个 token 约需 128 KiB；单请求缓存 4096 token 约为 512 MiB，4 个这样的请求约为 2 GiB。它只是公式演示，不包含分页填充和其他开销。

MLA、混合注意力、滑动窗口、状态空间模型，以及 TP 下的 KV 切分 / 复制都可能改变估算。MoE 的“每次激活参数少”也不等于所有专家权重都不用驻留；容量和计算量需要分别分析。

框架可能预分配 KV 池，也可能按块管理请求。配置的最大上下文不是每次请求的实际长度；降低 `max_model_len` 也不保证已预留的 KV 池同比缩小。把框架日志中的缓存容量、可容纳 token 数与请求期间的实际峰值放在一起看。[5]

## 7. 读懂指标，才能比较优化效果

| 指标 | 通俗解释 | 记录时要说清楚 |
| --- | --- | --- |
| TTFT | 发送请求后等多久开始收到有效输出 | 客户端还是服务端，首 token 还是首非空片段，是否含推理内容 |
| 端到端延迟 | 从请求发出到完成的时间 | 是否包含排队、网络、预处理和输出截断 |
| TPOT | 每条请求在首输出后，平均每个生成 token 的耗时 | 常用估算为 `(总耗时 − TTFT) / (输出 token 数 − 1)`，输出不足 2 个时不适用 |
| ITL | 相邻输出 token / 片段的间隔 | 流式片段可能包含多个 token，客户端采样不一定等于逐 token 延迟 |
| 输出吞吐 | 整个服务每秒产生多少输出 token | 分母用哪段墙钟时间，是否只统计成功请求 |
| 请求吞吐 | 每秒完成多少请求 | 不同输入 / 输出长度下不能直接横比 QPS |
| 达标吞吐（Goodput） | 每秒有多少请求同时满足预定延迟目标 | 先固定 TTFT、TPOT / 总延迟与成功率门槛，再统计 |
| 质量 / 成功率 | 回答可用且处理过程成功的比例 | HTTP 200、非空文本、内容正确、未截断是不同验收项 |

TPOT 是请求平均值，ITL 能观察生成过程的卡顿，两者不能直接画等号。平均延迟也会掩盖慢请求，应同时报告 P50 / P95 等分位数。很少的样本不足以可靠描述 P99，20 次成功更不能证明生产环境的长期可用率。

一份可以比较的压测，至少固定下面六件事：

1. **版本与输入**：模型 revision / 哈希、模板、框架、输入文件和实际 token 分布。
2. **负载方式**：固定并发属于闭环压测；固定到达速率属于另一种负载方式，两者不能混称。
3. **输出条件**：实际输出长度、采样参数、推理模式、输出上限和结束原因。
4. **缓存与预热**：冷启动、预热、重复前缀及命中情况分别记录；重复同一问题会改变测量条件。
5. **运行状态**：设备温度、时钟、其他进程、CPU / 网络是否成为瓶颈。
6. **证据与重复**：保存逐请求时间、错误、资源采样和完整参数；做多轮对照，说明波动。

`llama-bench` 适合引擎层计算测试，HTTP 压测还包含排队和传输。用通用 HTTP 工具统计 QPS，不能自动得到有效 TTFT / ITL；要确认工具解析了流式响应。[2][6]

## 8. 调优时，按“现象 → 证据 → 实验”推进

| 现象 | 先收集什么证据 | 可验证的改动与代价 |
| --- | --- | --- |
| 模型启动或请求时 OOM | 失败阶段、权重与 KV 分配、实际输入、内存峰值 | 改量化、减小请求上限 / 并发、调整并行；同时检查质量与吞吐 |
| 首段输出慢 | 排队时间、输入 token、缓存命中、预处理耗时 | 减少无效上下文、前缀复用、调度预算；不能直接归因于 prefill |
| 生成卡顿或 TPOT 高 | ITL 分布、批量、KV 读取、计算与通信状态 | 调度预算、适用的 attention kernel、量化或推测解码；重新检查 TTFT |
| 并发一高就慢 | 待处理队列、KV 容量、成功率和延迟曲线 | 找达标并发、限流、扩副本；不是只提高最大并发参数 |
| 多卡比单卡慢 | 卡间拓扑、实际通信、模型分片方式 | 比较 TP / PP / 副本；通信成本可能抵消计算收益 |

`max_num_seqs` 约束可同时调度的序列数量，`max_num_batched_tokens` 约束一次调度的 token 预算，`max_model_len` 约束单序列长度；它们不属于同一个“越大越快”的开关。调小分块 prefill 的预算可能改善正在生成请求的 ITL，却拉长长输入自己的 TTFT；应同时看两个指标。[5]

同样要区分两种 attention 优化：**Flash Attention** 主要减少注意力计算的内存读写与中间开销；**分页 KV 管理 / PagedAttention** 关注 KV 的分块管理与访问。它们可以共同存在，不是互相替代的量化技术。

建议每轮只验证一个主要假设：保存基线 → 改一项配置 → 重复相同负载 → 比较达标请求与资源 → 接受或撤回改动。没有测出改善，也是一条有价值的工程结论。

## 9. 现在还应认识哪些技术？

先掌握单机基线，再了解下面的扩展方向：

| 技术 | 解决什么问题 | 何时值得尝试 |
| --- | --- | --- |
| 持续批处理 | 已完成的请求退出，新请求继续加入调度 | 多请求长度不同，需要提高资源利用率 |
| 前缀缓存 / 分层缓存 | 复用相同 token 前缀的 KV，或扩展缓存存储层级 | 重复系统提示、工具说明、长公共上下文；还需考虑隔离与传输成本 |
| 推测解码 / MTP | 先提出候选 token，再由目标模型验证，争取一次接受多个 token | 单请求生成延迟重要且候选接受率足够；草稿成本与模型支持可能抵消收益 |
| TP / PP | 分别切分层内计算、模型层，分担单卡容量 | 模型或上下文需要多卡；必须计算通信与流水线空泡成本 |
| DP / EP | 分别分配请求到副本、分配 MoE 专家 | 需要扩吞吐或部署 MoE；副本、路由和通信设计不同 |
| Prefill / Decode 分离 | 为输入处理和生成使用不同资源池 | 有明确混合负载瓶颈且规模足够；KV 传输与调度复杂度要纳入成本 |

TP / PP / DP / EP 是并行方式，Ray 等工具帮助组织分布式执行，NCCL / RCCL / HCCL 负责相应平台的通信能力，三者不要混为一类。推测解码也不代表所有模型“打开开关就更快”，需要对应实现、质量一致性验证和实际负载测试。[4][7]

## 10. 最后交付什么，才算工程完成？

先在本机地址跑通最小请求，再逐项完成这些交付物：

- **可复建环境**：OS、设备、驱动、运行库、包版本、源码 commit / 镜像摘要、构建日志。
- **可追踪模型**：来源、版本 / revision、文件哈希、许可证、分词器和 chat template。
- **可操作服务**：启动 / 停止 / 重启、健康检查、超时、请求上限、鉴权与限流的配置方法。
- **可复查验收**：公开或脱敏输入、质量样例、性能门槛、逐请求数据、错误用例和最终报告。
- **可维护运行**：监控指标、日志脱敏、容量告警、配置变更记录和回滚步骤。

“OpenAI 兼容”通常只说明一部分接口约定兼容，不代表工具调用、结构化输出、多模态或所有响应字段都相同。按业务实际使用的接口分别验收。业务就绪检查也不能只证明端口打开：它还要确认模型、模板和必要能力可用。

## 11. 新手按什么顺序练习？

1. 读懂一个请求的 Prefill / Decode 与 KV Cache，能解释显存四部分。
2. 在一种硬件和一个框架上完成部署，保存正常与异常请求。
3. 固定输入与输出条件，分别测单并发和多并发，画出延迟与吞吐变化。
4. 从日志提出一个瓶颈假设，只改变一项配置，重复验证并写出限制。
5. 再做量化质量比较或第二种硬件适配；有容量需求时再扩展到多卡 / 多节点。

下一步可阅读 [Case 目录](../../cases/README.md)，或用[部署复盘模板](../../templates/deployment-review.md)整理自己的项目。现有 Case 保留了证据缺口说明；学习概念和满足公开投稿要求，是两个分别需要完成的目标。
