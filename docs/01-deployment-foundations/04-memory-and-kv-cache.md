# 04 内存预算、KV Cache 与容量规划

[返回总目录](README.md) · [上一章](03-model-and-quantization.md) · [下一章](05-llama-cpp-practice.md)

## 1. 先区分“文件大小”和“运行占用”

磁盘上的权重大小、进程虚拟地址空间、实际驻留 RAM、GPU 已分配内存、框架预留缓存不是同一个数字。文件通过 mmap 映射后，虚拟地址可以很大；首次访问才引发缺页和实际读入。GPU 后端还可能重新排列或复制部分权重，不能用文件大小直接替代运行显存。

工程预算可先写为：

```text
设备内存需求 = 设备上的权重 + KV/其他序列状态 + 常驻运行时
             + 阶段性临时空间 + 通信/图捕获等开销 + 安全余量

主机 RAM 需求 = CPU 权重与映射页 + 分词/服务/预处理 + 主机临时缓冲
             + 后端可能保留的副本 + 系统与其他应用余量
```

这些项的峰值不一定同时发生；但在没有峰值证据时，不能假定它们总能完美复用。程序启动、首请求、长 Prefill、多请求重叠和图捕获阶段都可能形成不同峰值。

## 2. 权重的第一步估算

对包含 P 个参数、平均每参数 b 位的权重，可用 `P × b / 8` 得到不含其他开销的字节估算。区分 GB（10^9 字节）与 GiB（2^30 字节），避免把差异误认为框架多占用了内存。

**理论算例，非模型实测：**27×10^9 参数，若所有参数恰好按 4 位保存，则是 13.5 GB，约 12.57 GiB；若按 FP16 保存，则是 54 GB，约 50.29 GiB。实际 Q4_K_M 有分组信息、混合精度张量与元数据，不能把 12.57 GiB 当成真实文件大小或显存保证。

MoE 的“激活参数少”不等于常驻权重少。每个 token 只访问部分专家，但不同请求可能路由到不同专家；是否能卸载和按需搬运由引擎决定，且要支付带宽与调度代价。

## 3. 标准 Attention 的 KV 估算

对普通 MHA/GQA/MQA 的文本 Decoder，假设每层 K/V 维度一致、所有历史均保留：

```text
每 token KV 字节数 = L × H_kv × (D_k × S_k + D_v × S_v)

若 K/V 维度与精度一致：
每 token KV 字节数 = 2 × L × H_kv × D × S

活跃 KV 字节数 ≈ 每 token KV 字节数 × 所有活跃序列保留 token 数之和
```

其中 L 为相关层数，H_kv 为 KV 头数，D 为每头维度，S 为每元素字节数。**不能直接用 attention query 头数替代 KV 头数**，也不能无条件用 hidden size 估算。GQA/MQA 的 H_kv 较少，是降低 KV 体积的重要原因之一。

**假设架构算例：**L=32、H_kv=8、D=128、K/V 均 FP16，每 token 为 `2×32×8×128×2 = 131072 bytes = 128 KiB`。一条保留 8192 token 的序列约需 1 GiB；四条都达到这一长度约需 4 GiB。这里的 8192 包含已处理输入和已生成历史，不是只有输入 prompt。

这是一台假想标准 GQA 模型的计算，**不是仓库 27B 模型的结构说明**。实际配置应读取模型元数据。量化 KV 还包含 scale、对齐和实现开销，不能简单按位宽比例精确折算。MLA、滑窗、混合全局/局部 Attention、循环状态与多模态模型要分层或按引擎日志计算。

## 4. 逻辑容量与物理分配

逻辑上当前只用了 1000 token，框架可能已经为整个 KV 池分配了设备内存。分页管理减少连续分配和内部浪费，不会让 KV 本身不占空间；块大小会引入尾部浪费。前缀共享可让多个请求复用部分块，但还涉及引用计数、驱逐和缓存策略。

某些版本的 llama-server 使用固定槽位上下文切分；另一些配置使用统一 KV 池或自动槽位。不能永久假设 `-c` 就是每个请求上限，也不能始终用 `-c / -np` 计算。应记录该版本的 `--help`，并检查启动日志中的总容量、每序列限制和 KV 分配。相关参数关系见 [07](07-serving-and-scheduling.md)。

vLLM 的 `gpu-memory-utilization` 是执行器内存预算比例，并非仅给权重的比例，也不是强制 GPU 利用率。KV 空间常从权重和其他开销后剩余预算推导。某些版本可显式配置 KV 容量；具体参数名随版本核对，不能照抄其他版本的日志。

## 5. 从预算得到初始容量

**示例规划，非测量：**假设设备实际可用 24 GiB，预计设备权重 15 GiB、运行时 1 GiB、峰值临时空间 2 GiB、余量 2 GiB，则可给 KV 的初步预算为 4 GiB。若每序列最坏需要 1 GiB KV，理论同时容纳四条；这还没有计入块浪费、缓存保留、额外输入等因素，不能直接承诺并发四条达到延迟目标。

容量要经过两道门槛：先判断能否容纳，再判断能否按时完成。内存容纳四条不代表 TTFT 或 TPOT 在四并发时达标。最终有效并发应由性能曲线和边界测试确定。

| 预算项 | 估算方法 | 运行期核对 |
| --- | --- | --- |
| 权重 | 文件与量化元数据、实际卸载比例 | 加载日志、空载内存 |
| KV/状态 | 架构公式、序列上限、缓存策略 | KV 分配日志、活跃/空闲块 |
| 临时空间 | 输入长度、microbatch、Attention 后端 | 长 Prefill 峰值 |
| Runtime/图 | 编译、图捕获、线程和后端 | 首请求/预热后的常驻占用 |
| 余量 | OS、显示、其他应用、波动 | 长时间与多场景采样 |

## 6. CPU/GPU 混合卸载为什么不是免费扩容

llama.cpp 的 `--n-gpu-layers` 控制层卸载；层数不等于精确字节数，不同层可能大小不同。日志里实际 offload 的层、输出层和 buffer 才是证据。较新版本还可能自动调整容量，应检查最终有效配置。

将部分层留在 CPU 可以放下更大模型，但 CPU 层的计算、跨设备激活传输、KV 放置与内存带宽都影响端到端延迟。有时多卸载几层会减少 CPU 瓶颈，有时因显存紧张和临时空间不足造成失败。应在相同上下文、batch 和输入下逐档比较，而非只截图显存占满。

分层卸载通常移动层边界的激活，不能简单描述为“每个 token 必然把全部权重经 PCIe 传一次”。某些专家卸载、动态权重搬运或具体后端会有不同数据流，需要 profiler 证据。

## 7. 统一内存、mmap、swap 与 mlock

统一内存设备的 CPU/GPU 共享物理容量。不能将系统 RAM 与“GPU 可用内存”相加；设备的进程限制、驱动工作集限制与 OS 保留也要考虑。启动浏览器、视频或其他模型可能直接改变推理可用容量。

mmap 有利于映射文件与利用页缓存，暖启动可能快于冷启动；它不能绕过物理内存需求。swap/压缩内存可能帮助避免立即失败，但权重或 KV 反复换入换出会显著增加延迟。不要把依靠 swap 勉强运行的结果描述为流畅部署。

mlock 尝试锁定内存页，受权限和资源限制约束，也会减少系统可回收内存。不是通用加速开关。应先测缺页与 I/O 是否为瓶颈，再决定是否使用，并在共享设备上保留系统余量。

## 8. OOM 必须按发生阶段排查

启动加载 OOM：先看权重、副本、设备分配与已有进程；初始化/预热 OOM：看 KV、图捕获、工作区；长输入 OOM：看 Prefill microbatch、Attention 和预处理；并发增长 OOM：看活跃状态、队列、缓存与临时空间。

Linux 进程被系统直接杀死也可能是主机 RAM 或容器内存限制，与 GPU OOM 不同。采样间隔过长还可能漏掉瞬时峰值；“监控只到 22 GiB，所以 24 GiB 卡不该 OOM”不能成立。详细操作见 [10](10-troubleshooting.md)。
