# Qwen3.6-35B-A3B 部署与推理性能优化

[项目索引](README.md) · [通用性能优化测试方法论](../edge-llm-performance-methodology.md)

> 验证基线：AMD Ryzen AI MAX+ 395 / Radeon 8060S / `gfx1151` /
> 128 GB UMA / Vulkan RADV 与 ROCm 7.2.4。  
> 事实截止：2026-09-08 的本地实测记录；文档整理日期：2026-10-19。

## 1. 结论先行

Qwen3.6-35B-A3B 有两条不同的最优路径：

| 目标 | 推荐后端 | 推荐配置 | 实测结果 |
|---|---|---|---|
| 单路请求、追求 Decode | Vulkan | no-spec 或 MTP-on | 单路 MTP-on 在 32K 窗口约 84.5 tok/s Decode |
| 多路并发、生产服务 | HIP/ROCm | no-spec | 双副本边界约为 short 24、normal 27、RAG 18、long 9 offered |

最重要的经验：

- MTP 能显著提高单路 Decode，但在高并发代表点大多变成负收益。
- Vulkan 在 8 到 9 个活跃 slot 左右出现明显吞吐断崖。
- HIP 明显改善 8 到 9 路断崖，并改善 4K/8K/16K 的 E2E。
- 当前并发生产建议默认关闭 MTP。
- `-c` 是服务总上下文，不是每个 slot 的上下文。每槽上下文约等于
  `-c / -np`，必须显式核算。

## 3. 硬件和软件要求

### 3.1 已验证环境

```text
APU: Ryzen AI MAX+ 395
GPU: Radeon 8060S / gfx1151
内存: 122-123 GiB 可用 UMA
Vulkan: RADV GFX1151
ROCm: 7.2.4
llama.cpp: server 10235 / commit 221f0f635
batch/ubatch: 4096/512 或 2048/512
线程: 16/16
HTTP 线程: 8
```

模型约 21.3 GiB，单机 128 GB 内存足以容纳模型和多个 KV slot。真正的限制
通常不是权重，而是高并发下的 KV cache、计算 buffer、内存带宽和调度。

### 3.2 预检

```bash
free -h
awk '/MemAvailable|SwapFree/ {print $1,$2,$3}' /proc/meminfo
vulkaninfo --summary
rocminfo | grep -m 5 -E 'Name:|gfx1151'

llama-server --version
llama-server --list-devices
```

Vulkan 设备应显示类似：

```text
Vulkan0: AMD Radeon Graphics (RADV GFX1151)
```

HIP 设备应显示：

```text
ROCm0: AMD Radeon Graphics (gfx1151)
```

不要同时把 Vulkan 和 HIP 后端编译进同一个性能对比二进制，除非你明确
知道当前版本如何选择 backend。最稳妥的做法是分别构建、分别记录版本。
不要设置 `HSA_OVERRIDE_GFX_VERSION` 伪装架构，驱动应原生识别 `gfx1151`。

### 3.3 功耗和干扰

```bash
powerprofilesctl set performance
rocm-smi --showperflevel
rocm-smi --showuse
```

压测时不要在目标节点上同时运行浏览器、ComfyUI、另一个模型服务或大型编译。
双机压测时负载生成器应放在第三台机器，或者至少不要和被测服务抢 CPU。

## 5. 构建 llama.cpp

Ubuntu 上常用构建依赖：

```bash
sudo apt-get update
sudo apt-get install -y build-essential cmake ninja-build git \
  libvulkan-dev vulkan-tools glslc
```

ROCm/HIP 构建还需要与目标机器匹配的 ROCm 开发工具链。不要在同一台机器
混装来源不明的多个 ROCm 版本。

建议在固定源码目录下分别构建 Vulkan 和 HIP：

```bash
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
git checkout 221f0f635
```

### 5.1 Vulkan 构建

```bash
cmake -S . -B build-vulkan-gfx1151 \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_VULKAN=ON \
  -DLLAMA_BUILD_UI=OFF \
  -DLLAMA_USE_PREBUILT_UI=OFF \
  -DLLAMA_CURL=OFF

cmake --build build-vulkan-gfx1151 \
  --target llama-server llama-bench llama-tokenize \
  -j"$(nproc)"
```

### 5.2 HIP/ROCm 构建

```bash
cmake -S . -B build-hip-gfx1151 \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_HIP=ON \
  -DGGML_HIP_ROCWMMA_FATTN=ON \
  -DGGML_HIP_MMQ_MFMA=ON \
  -DCMAKE_HIP_ARCHITECTURES=gfx1151 \
  -DAMDGPU_TARGETS=gfx1151 \
  -DLLAMA_BUILD_UI=OFF \
  -DLLAMA_USE_PREBUILT_UI=OFF \
  -DLLAMA_CURL=OFF

cmake --build build-hip-gfx1151 \
  --target llama-server llama-bench llama-tokenize \
  -j"$(nproc)"
```

验证：

```bash
build-vulkan-gfx1151/bin/llama-server --list-devices
build-hip-gfx1151/bin/llama-server --list-devices
```

HIP 运行时若出现 OpenSSL/libstdc++ 缺失，应固定一套与二进制匹配的运行库
目录，不要直接替换系统库。本工作区曾通过把 HIP build 和所需 OpenSSL/
libstdc++ 复制到用户目录修复 Node B 启动问题。

## 6. 启动方式

### 6.1 HIP 单机生产模板

这是并发优先的起始配置：

```bash
MODEL=<MODEL_ROOT>/Qwen3.6-35B-A3B-MTP-GGUF/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf
BIN=<LLAMA_CPP>/build-hip-gfx1151/bin/llama-server
SLOTS=9
CTX_PER_SLOT=6144
TOTAL_CTX=$((SLOTS * CTX_PER_SLOT))

"$BIN" \
  -m "$MODEL" \
  --alias qwen36-35b-a3b \
  -ngl 999 \
  --fit off \
  -c "$TOTAL_CTX" \
  -np "$SLOTS" \
  -cb \
  -b 4096 \
  -ub 512 \
  -t 16 \
  -tb 16 \
  --threads-http 8 \
  -fa on \
  -ctk f16 \
  -ctv f16 \
  --device ROCm0 \
  --host 127.0.0.1 \
  --port 8381 \
  --metrics \
  --slots \
  --no-ui
```

`-c 55296 -np 9` 时，每槽约 6144 token。输入加输出都必须落在单槽预算内。

### 6.2 Vulkan 单路 MTP 模板

这是单路性能测试模板，不是默认并发生产配置：

```bash
MODEL=<MODEL_ROOT>/Qwen3.6-35B-A3B-MTP-GGUF/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf
BIN=<LLAMA_CPP>/build-vulkan-gfx1151/bin/llama-server

"$BIN" \
  -m "$MODEL" \
  --alias qwen36-35b-a3b-mtp \
  -ngl 999 \
  --fit off \
  -c 32768 \
  -np 1 \
  -cb \
  -b 4096 \
  -ub 512 \
  -t 16 \
  -tb 16 \
  -fa on \
  -ctk f16 \
  -ctv f16 \
  --device Vulkan0 \
  --host 127.0.0.1 \
  --port 8381 \
  --no-cache-prompt \
  --metrics \
  --slots \
  --no-ui \
  --spec-type draft-mtp \
  --no-spec-draft-backend-sampling \
  --spec-draft-type-k f16 \
  --spec-draft-type-v f16
```

单路测试关闭 prompt cache 是为了避免前缀缓存污染 Prefill。生产环境如果
有稳定的 system prompt、多轮对话或 RAG 前缀，应开启 cache 并单独测量
cache hit、TTFT 和内存。

### 6.3 上下文和 slot 预算

本工作区的正式建议：

| 输入桶 | 每节点 slots | 每槽上下文 | 每节点 `-c` |
|---|---:|---:|---:|
| 短交互 1K/512 | 12 | 2048 | 24576 |
| 常规问答 4K/512 | 9 | 6144 | 55296 |
| RAG 8K/512 | 6 | 10240 | 61440 |
| 长文 16K/512 | 3 | 18432 | 55296 |

双副本时，把两台节点的相同配置分别启动，再在负载均衡器后暴露。

## 8. 性能数据

### 8.1 单路 Vulkan MTP-on 与 MTP-off

测试条件：单机单路、Vulkan、128 token 输出、关闭 prompt cache。

| 总上下文 | MTP-off Decode | MTP-on Decode | 提升 |
|---:|---:|---:|---:|
| 32K | 49.13 tok/s | 84.50 tok/s | +72.0% |
| 64K | 42.37 tok/s | 72.18 tok/s | +70.4% |
| 128K | 32.84 tok/s | 58.85 tok/s | +79.2% |

对应 MTP-on 的完整请求指标：

| 总上下文 | Prompt TPS | Decode | TTFT | 总耗时 | E2E 输出 TPS |
|---:|---:|---:|---:|---:|---:|
| 32K | 913.63 | 84.63 | 35.92 s | 37.44 s | 3.42 |
| 64K | 643.76 | 72.31 | 101.46 s | 103.23 s | 1.24 |
| 128K | 343.25 | 58.99 | 381.46 s | 383.64 s | 0.33 |

这些是 Decode 阶段速度，不是完整请求速度。128K 输入的主要成本是 Prefill，
MTP 不能消除它。

### 8.2 并发边界

临时 SLO：完整性 100%，5 次正式轮中最慢一路 Decode 不低于 10 tok/s。

单机 HIP 稳定活跃 slot：

```text
short 12, normal 9, RAG 6, long 3
```

双副本推荐 offered：

```text
short 24, normal 27, RAG 18, long 9
```

双机 HIP formal 结果：

| 场景 | offered | E2E TPS 均值 | 最慢 Decode 均值/最差 | TTFT p95 |
|---|---:|---:|---:|---:|
| 1K/512 | 24 | 241.12 | 12.44 / 11.64 | 11.29 s |
| 4K/512 | 27 | 148.14 | 10.69 / 10.65 | 74.93 s |
| 8K/512 | 18 | 97.30 | 11.51 / 11.38 | 78.90 s |
| 16K/512 | 9 | 45.41 | 13.25 / 13.24 | 87.89 s |

这些 offered 数包含排队能力，不等同于同时执行推理的 slot 数。

### 8.3 HIP 与 Vulkan

同 offered 对照中，HIP 在 normal/RAG/long 的 E2E 明显高于 Vulkan；
短交互场景要同时看最慢一路 Decode，不能只看总 E2E。典型结果：

| 场景 | Vulkan E2E | HIP E2E | Vulkan 最差 Decode | HIP 最差 Decode |
|---|---:|---:|---:|---:|
| 4K/512, offered 18 | 99.50 | 152.77 | 10.62 | 10.79 |
| 8K/512, offered 14 | 64.48 | 92.68 | 10.07 | 11.50 |
| 16K/512, offered 6 | 37.22 | 49.71 | 11.06 | 14.50 |

Vulkan 的 8 到 9 路断崖是真实存在的：

```text
short c8 -> c9: E2E -32.9%，最慢 Decode -45.9%
normal c8 -> c9: E2E -19.8%，最慢 Decode -30.9%
RAG c8 -> c9: E2E -16.3%，最慢 Decode -30.2%
```

### 8.4 MTP 在高并发下是负收益

代表点：

| 后端 | 场景 | no-spec E2E | MTP E2E | 最慢 Decode 变化 |
|---|---|---:|---:|---:|
| HIP | 1K/512 c12 | 121.44 | 75.24 | -35.6% |
| HIP | 4K/512 c9 | 77.02 | 46.31 | -44.5% |
| HIP | 8K/512 c6 | 50.42 | 38.70 | -23.8% |
| Vulkan | 1K/512 c8 | 95.91 | 71.42 | -28.7% |
| Vulkan | 4K/512 c7 | 52.22 | 47.36 | -8.3% |

所以不要把“单路 MTP 快 70%”直接套到并发生产。

## 9. 性能优化顺序

### 9.1 先确定业务目标

先写清楚：

```text
输入长度：1K / 4K / 8K / 16K
输出长度：128 / 512 / 其他
并发：offered 还是 active slots
SLO：TTFT p95、ITL p95、E2E p95、最慢一路 Decode
```

没有 SLO 时，不能只看聚合 TPS 做决策。高并发下聚合吞吐可能上升，但最慢
一路体验已经不可接受。

### 9.2 后端 A/B

固定相同模型、上下文、batch、线程和请求，分别测试 HIP 与 Vulkan：

```bash
# HIP
--device ROCm0

# Vulkan
--device Vulkan0
```

如果目标是并发容量，优先 HIP no-spec。如果目标是单路短输出极限，保留
Vulkan 和 MTP 作为候选。

### 9.3 active slots

不要一次把 `-np` 拉到很高。先测：

```text
1, 2, 4, 6, 7, 8, 9, 10, 12
```

观察：

```text
E2E TPS、最慢一路 Decode、TTFT p95、ITL p95
MemAvailable、SwapFree、GPU busy、请求排队
```

### 9.4 batch/ubatch

从以下矩阵开始：

| batch | ubatch |
|---:|---:|
| 2048 | 256 |
| 2048 | 512 |
| 4096 | 512 |
| 4096 | 1024 |
| 8192 | 512 |
| 8192 | 1024 |

约束是 `ubatch <= batch`。不要同时改线程和 cache 类型。

### 9.5 线程

建议：

```text
threads:       12 / 16 / 20
threads-batch: 16 / 24 / 32
threads-http:  4 / 8
```

先固定 batch 线程，单独扫描 generation threads，再反过来。HTTP 线程过多
不会提升 GPU 推理，反而增加调度开销。

### 9.6 KV cache

先保持 `f16/f16` 质量基线。长上下文、内存紧张或需要更多 slot 时，再单独测
`q8_0/q8_0`。必须同时记录：

```text
输出质量、TTFT、Decode、KV 占用、最大并发
```

不要只因为 Q8 KV 省内存就默认切换。

### 9.7 MTP

只在单路或低并发、长输出场景做 MTP A/B：

```bash
--spec-type draft-mtp \
--no-spec-draft-backend-sampling \
--spec-draft-type-k f16 \
--spec-draft-type-v f16
```

记录：

```text
draft tokens、accepted tokens、acceptance rate
Decode、TTFT、E2E、最慢一路 Decode
```

接受率高不等于 E2E 快。当前 Qwen3.6 的并发结论是默认关闭 MTP。

## 10. 压测方法

### 10.1 合成基线

```bash
MODEL=<MODEL_ROOT>/Qwen3.6-35B-A3B-MTP-GGUF/Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf

llama-bench \
  -m "$MODEL" \
  -ngl 999 \
  -fa 1 \
  -b 4096 \
  -ub 512 \
  -t 16 \
  -p 512,4096 \
  -n 128 \
  -r 3
```

`llama-bench` 是合成负载，不等同于聊天模板、采样、HTTP 和真实 token 分布。
它可以用来校准 PP/TG，但不能替代 API 压测。

### 10.2 请求级压测

至少保存：

```text
request_id、prompt_id、HTTP 状态、错误
prompt_tokens、completion_tokens、finish_reason
TTFT、ITL、总耗时
每路 Decode、最慢一路 Decode
缓存命中 token、排队时间、GPU/内存采样
```

每点 1 次 warmup 加 5 次正式轮。每次正式轮都要完整返回，失败单独保存，
不要按 0 tok/s 混入均值。

### 10.3 双副本负载均衡

Nginx 最小示例：

```nginx
upstream qwen36 {
    least_conn;
    server <NODE_A>:8381 max_fails=2 fail_timeout=10s;
    server <NODE_B>:8381 max_fails=2 fail_timeout=10s;
    keepalive 32;
}

server {
    listen 8080;
    location / {
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_pass http://qwen36;
        proxy_read_timeout 600s;
    }
}
```

生产还需要认证、请求体限制、超时、重试策略和访问日志。不要直接把
`llama-server` 暴露到公网。

## 11. 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `failed to load model` | 路径/权限/分片不完整 | 核对路径、大小、SHA |
| Vulkan 设备不存在 | 没有 RADV/驱动或设备名变化 | `--list-devices`，不要猜设备名 |
| HIP 启动缺 `libssl`/`libstdc++` | 运行库不一致 | 固定匹配的用户目录运行库 |
| `n_ctx_slot` 小于预期 | `-c` 被当成每槽上下文 | 用 `-c = slots * ctx_per_slot` |
| 9 路并发突然变慢 | Vulkan 断崖 | 降到 8 路或改 HIP |
| 高并发 MTP 更慢 | draft 成本叠加 | 生产关闭 MTP |
| 首 token 很慢 | Prefill 或 prompt cache 冷 | 开 cache，分输入桶测 TTFT |
| 输出被截断 | 单槽 context 不足 | 增加 `-c` 或减少输入/输出 |
| 内存持续下降 | KV/cache 或泄漏 | 观察 MemAvailable、SwapFree、restart |
| 双机表现不一致 | 二进制/驱动/模型/构造不一致 | 固定 commit 和 SHA，逐项对齐 |
