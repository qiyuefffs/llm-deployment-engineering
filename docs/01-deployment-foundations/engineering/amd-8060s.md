## 部署与基线

1. 完成Vulkan编译与设备枚举；固定GGUF摘要、程序commit、RADV和Mesa版本。
2. 保持模型与输入相同，先以`-ngl 0`获得CPU基线，再`-ngl 99`检查实际`offloaded 41/41`与GPU buffer。
3. 恢复原ctx32768配置，再逐步改为ctx16384、batch4096、ubatch1024、threads16/threads-batch32、np1。完整命令和各buffer在下方原记录中。
4. API检查使用同一个模型别名，保存usage与finish_reason；引擎eval速度与HTTP墙钟吞吐分别记录。

## 实际加速优化过程

| 阶段 | 配置变化 | decode token/s |
| --- | --- | --- |
| CPU基线 | GPU层0 | 22.9 |
| Vulkan卸载 | GPU层99，原ctx32K | 47.2 |
| 参数组合 | ctx16K、batch4096、threads-batch32 | 58.4 |
| 后续组合 | cache-ram0、mlock、poll50 | 58.3 |
| BF16基础 | 约64.60GiB、原预算 | 10.8 |
| BF16增大工作区 | ctx8K、ubatch2048、batch8192、threads-batch64 | 10.1 |

Q4的CPU→GPU观察比值约2.06；GPU初版→参数组合约1.24。每组同时变更多个条件，保留为组合观察，未提供误差条和质量对照。BF16加大batch没有改善decode，compute buffer从1172MiB增至2312MiB；不是参数越大越快。

## 关键技术修订与验收

- MoE每步不必读取所有专家，不能用65GB文件体积假定每token读取65GB。Roofline需按实际数据流和有效带宽计算。
- 原文关于“到达带宽极限”“所有SSM的Flash Attention无效”等表述范围过大。本次保留测量，结论限于固定模型、后端和已测配置。
- `--cache-ram 0`控制相应版本的主机prompt缓存，不等于关闭所有KV或必然节省GPU带宽；`--mlock`防止换出，不能凭启用就宣称加速。
- 原“Q4比BF16快5.8倍”使用圆整数，且缺同任务质量与完整计时；不作为无损量化结论。

下方完整保留部署文章与BF16优化文章；原未验证的预测明确保留为预测。正式验收补固定输入、实际token、重复轮次、资源峰值和质量题集。

##### 4.2 启动推理服务

**完整启动命令：**

```text
LD_LIBRARY_PATH=/srv/llm/llamaCPP \
/srv/llm/llamaCPP/llama-server \
  --model /srv/llm/models/Qwen3.6-35B-A3B-GGUF/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  --ctx-size 16384 \
  --n-gpu-layers 99 \
  --parallel 1 \
  --threads 16 \
  --threads-batch 32 \
  --ubatch-size 1024 \
  --batch-size 4096 \
  --cache-ram 0 \
  --poll 50 \
  --mlock
```

##### 4.3 关键参数说明

| 参数 | 值 | 说明 |
| --- | --- | --- |
| --n-gpu-layers 99 | 99 | 将所有 41 层加载到 GPU Vulkan 后端 |
| --ctx-size 16384 | 16384 | 推理上下文长度（减少 KV 缓存带宽压力） |
| --parallel 1 | 1 | 单槽位模式，节省显存给模型 |
| --threads 16 | 16 | CPU 推理线程数 |
| --threads-batch 32 | 32 | 批处理线程数（充分利用全部核心） |
| --ubatch-size 1024 | 1024 | 微批大小（提升 GPU 并行度） |
| --batch-size 4096 | 4096 | 提示处理批大小 |
| --cache-ram 0 | 0 | 禁用提示缓存，释放内存带宽 |
| --poll 50 | 50 | 减少 GPU 轮询延迟 |
| --mlock | - | 锁定内存页防止 swap |

##### 优化说明

- **全部 41 层离线到 GPU**：充分利用 AMD Radeon 8060S 的统一内存架构

- **Flash Attention**：自动启用

- **Gated Delta Net**：fused (自回归) + chunked 模式均在 GPU 启用

- **Graph splits**：降至 2（纯 CPU 时为 844），大幅减少 kernel launch 开销

- **Prompt Cache**：已禁用 (`--cache-ram 0`)，节省内存带宽

- **mlock**：锁定内存页面，防止系统 swap 影响推理延迟

- **采样器优化**：简化为 top-k 采样 (`--sampling-seq k`)，减少开销

#### 优化历程

##### 测试 1: 基础配置

```text
LD_LIBRARY_PATH=/srv/llm/llamaCPP /srv/llm/llamaCPP/llama-server \
  --model "/srv/llm/models/Qwen3.6-35B-A3B-GGUF-BF16/BF16/Qwen3.6-35B-A3B-BF16-00001-of-00002.gguf" \
  --host 0.0.0.0 --port 8080 \
  --ctx-size 16384 \
  --n-gpu-layers 99 \
  --threads 16 --threads-batch 32 \
  --ubatch-size 1024 --batch-size 4096 \
  --cache-ram 0 --poll 50 --mlock
```

**结果:** 10.8 tok/s (92.30 ms/token)

##### 测试 2: Flash Attention + Cache Reuse

```text
# 添加参数:
--flash-attn on --cache-reuse 256
```

**结果:** 10.8 tok/s (无变化) **原因:**

- Flash Attention 对 Gated Delta Net 架构无效

- Cache reuse 不被 Qwen3.5-MoE 的 SSM/RNN 层支持

##### 测试 3: 增大 Batch + 减小 Context

```text
--ctx-size 8192 \
--threads-batch 64 \
--ubatch-size 2048 \
--batch-size 8192 \
--flash-attn on
```

**结果:** 10.1 tok/s (98.55 ms/token) - 略降 **分析:**

- KV cache 从 320 MB 降至 160 MB

- Compute buffer 从 1172 MB 增至 2312 MB

- 对 UMA 带宽瓶颈无实质影响

#### 性能对比

| 精度 | 大小 | 速度 | 延迟 | 显存占用 |
| --- | --- | --- | --- | --- |
| Q4_K_M | 21 GB | 58 tok/s | 17.1 ms | ~22 GB |
| BF16 | 65 GB | 10 tok/s | 92-98 ms | ~67 GB |

**速度比:** Q4_K_M 是 BF16 的 **5.8 倍**

#### 瓶颈分析

##### 内存带宽限制

- AMD 集成 GPU 使用统一内存架构 (UMA)

- 实际带宽: ~100 GB/s

- BF16模型文件约65 GB；每步实读取决于激活专家、共享层、KV与kernel

- 理论分析修订：带宽模型应为有效内存带宽÷每生成token实际读取的字节数。MoE只激活部分专家，不能以总文件大小或16 bytes/token推导速度；6–12 tok/s不是由原式可得的理论结果。

- 实际达到: **10 tok/s** (已达带宽上限)

##### 为什么 Q4_K_M 快 5.8 倍?

| 指标 | Q4_K_M | BF16 |
| --- | --- | --- |
| 模型大小 | 21 GB | 65 GB |
| 文件体积，非每步实读 | 21 GB | 65 GB |
| BPW (每权重比特) | 5.11 | 16.0 |
| 带宽利用率 | 高效 | 低效 (3x 数据量) |

#### 已尝试的优化手段

| 优化项 | 状态 | 效果 |
| --- | --- | --- |
| --n-gpu-layers 99 | ✅ 全层 GPU | 必须 |
| --flash-attn on | ✅ 已启用 | 对 SSM 架构无效 |
| --cache-reuse 256 | ❌ 不支持 | SSM 层不支持 KV reuse |
| ubatch 1024→2048 | ✅ 已测试 | 无提升 |
| ctx-size 16384→8192 | ✅ 已测试 | 节省 160 MB, 无速度提升 |
| threads-batch 32→64 | ✅ 已测试 | 无提升 |
| --mlock | ✅ 已启用 | 防止 swap |
| --poll 50 | ✅ 已优化 | 减少延迟 |

#### 结论

**BF16在这组已测参数中约10 tok/s。**当前实验未找到更快配置；未提供roofline或带宽计数器，不能宣称硬件性能极限。

##### 推荐方案

1. **生产环境:** 使用 Q4_K_M (58 tok/s, 精度损失需以目标任务验证)

2. **速度优先:** 使用 IQ4_XS (17.73 GB, 预计 65+ tok/s)

3. **BF16 仅适用于:**

  - 精度敏感的研究场景

  - 有独立 VRAM 的 GPU (如 RTX 4090 24GB + PCIe 带宽更高)

  - 批量推理 (通过增大 parallel slots)
