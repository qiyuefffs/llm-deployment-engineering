# 01 工程目标与请求链路

[返回总目录](README.md) · [下一章：硬件兼容](02-hardware-compatibility.md)

## 1. 端侧部署究竟在解决什么问题

端侧指模型主要在用户设备或靠近数据产生位置的设备上运行，例如 PC、手机、工业网关、车载设备和边缘工作站。判断重点是计算在哪里发生、设备受什么限制，以及断网后还需要哪些功能。云端 Notebook 便于获取 GPU、验证模型和开展对照实验，但云端 GPU 的性能与温度条件不能直接代表终端。

典型需求是数据留在设备上、断网仍可使用、交互等待可接受、硬件成本受限。对应的工程约束包括内存、存储、带宽、功耗、散热、操作系统权限、安装体积和用户设备差异。一个 27B Q4 模型可能适用于某些工作站；同一模型不一定适合手机。应允许通过更小模型、任务约束和上下文管理满足需求，而不是把参数规模当成最终目标。

例如，“离线读取本地说明书并回答问题”还包含文档解析、检索和引用验证。推理部署子系统负责把给定消息转成可靠回答，并说明它能承受的输入、输出与并发范围。只有端到端应用才能证明业务任务是否完成，两类验收要分别设计。

## 2. 把一句模糊需求变成部署合同

“这个模型能在我的电脑上跑吗”缺少设备、质量和体验目标。实施前填写下表，没有测量的数据写“待测”。

| 项目 | 应写清的内容 | 为什么影响部署 |
| --- | --- | --- |
| 任务 | 问答、摘要、JSON 抽取、代码补全、工具参数生成 | 输出格式与质量验收不同 |
| 设备 | 型号、RAM/VRAM、CPU 指令集、OS、驱动、功耗模式 | 决定可用后端和内存上限 |
| 输入 | 语言、实际 token 分布、图片数量、上下文最大值 | 决定 Prefill 和 KV 需求 |
| 输出 | 常见长度、上限、是否流式、是否含推理内容 | 决定用户等待与 Decode 时间 |
| 负载 | 单人交互、多窗口、局域网共享、后台批任务 | 决定调度、队列和隔离 |
| 服务目标 | 首个可见答案、完成时间、达标请求比例 | 明确优化优先级 |
| 资源目标 | 内存峰值、安装包大小、持续功率或能耗 | 端侧通常不能耗尽设备资源 |
| 生命周期 | 离线安装、开机启动、休眠恢复、升级回滚 | 决定交付形式 |

如果目标是“边输入边回答”，首段答案延迟可能更关键；如果目标是批量生成报告，总完成时间和质量更关键。把两种任务混在一个 tokens/s 数字里，会导向错误配置。

## 3. 五层能力之间怎样衔接

| 能力层 | 输入 | 工程动作 | 可检查的输出 |
| --- | --- | --- | --- |
| 硬件后端 | 设备清单、系统版本 | 驱动检查、后端构建、算子与精度确认 | 兼容矩阵、设备识别日志 |
| 模型与量化 | 原始模型、许可证、任务样例 | 校验、转换、量化、模板确认 | 模型清单、哈希、质量对照 |
| 推理框架 | 兼容的模型与设备 | 单请求推理、内存配置、服务启动 | 命令、有效配置、API 响应 |
| 性能优化 | 固定版本与负载 | 建基线、采样、定位、对照实验 | 原始记录、资源轨迹、结论 |
| 工程交付 | 候选配置与验收结果 | 封装、监控、重启、回滚、文档 | 可安装制品和运维手册 |

七个工程模块是工作分解：硬件后端、模型格式与量化、推理框架、内存与 KV、压测与优化、多设备并行、服务与交付。学习时可以分开，验收时必须串起来。没有质量基线的性能优化，无法判断是否以错误答案换来了速度。

## 4. 从消息到 token：模板也是模型的一部分

服务收到 `messages` 后，通常经过输入校验、chat template 渲染、分词、排队与调度。模板把 system/user/assistant 角色和特殊符号拼成模型期望的序列。模型学习了特定序列约定，错误模板可能导致复述问题、角色混乱、工具调用失败或无法正常停止。

模型交付包至少应关联权重、配置、分词器、特殊 token、chat template、生成参数与许可证。不能只复制权重后就认为“同名模型完全一样”。GGUF 可携带分词器和模板元数据，但仍需检查转换工具与目标引擎是否正确解释。

token 不是中文字符、英文单词或 HTTP 片段的同义词。相同文本由不同分词器处理时，token 数量可能不同。测量 1024 token 输入，应以实际模型分词结果为准，不能简单重复 1024 个字。多模态输入还包含视觉等专用 token 或嵌入，其资源成本不能按文本字数估计。

## 5. Prefill：一次处理输入并建立状态

在常见自回归 Transformer 中，Prefill 处理输入 token，计算各层状态和需要保存的 KV。多个输入位置可并行进行大量矩阵运算，所以常有较高计算密度；普通全注意力还会随序列增长增加计算与内存访问。具体复杂度受滑窗、混合架构和实现影响。

第一次生成所需的计算并非只有 Prefill。排队、模板、分词、图片预处理、模型首次编译与输出传输都会增加等待。长输入的 TTFT 高，应先拆分这些阶段，再决定缩短输入、启用前缀复用或调整调度。

## 6. Decode：已有状态上逐步生成

Decode 每轮利用已有上下文继续生成。单条序列的普通自回归生成存在前后依赖，不能把后面所有 token 一次并行算完。小批量 Dense 模型 Decode 常受权重读取带宽影响；长上下文可能受 KV 读取影响；批量增大后计算和调度也可能成为限制。

**KV Cache** 保存历史位置各层的 Key/Value，后续无需为同一历史反复做完整投影。历史 KV 仍需被读取，缓存也占内存；保存 KV 不意味着长上下文没有额外代价。GQA/MQA 可减少 KV 头数，MoE、MLA、滑窗与状态空间模型则需按实际结构分析，不能统一套一条公式。

```text
请求进入 → 模板/分词 → 排队 → Prefill → 第一次输出 → Decode 多轮 → 停止
                                 │                     │
                                 └──── KV 状态复用 ────┘
```

## 7. 输出可见不等于任务完成

推理模型可能先输出思考内容，再输出最终答案。应用有时隐藏思考内容，此时用户看到的首字时间晚于模型首次输出。应分别说明首个模型内容、首个非空文本片段与首个可见答案的时间。收到角色字段或空 SSE 帧不应算成首字。

结束原因同样影响结果：EOS、到达输出上限、超时、客户端取消、格式验证失败是不同状态。`HTTP 200` 只说明请求成功返回；不证明输出完整、JSON 有效或答案正确。

## 8. 用一个项目建立工程思维

可以以已有 llama.cpp 部署为起点，依次回答：模型从哪里来，为什么使用这份 Q4，运行在哪个后端，多少层在设备上，输入输出多长，慢在哪个阶段，优化后质量是否保持，别人怎样复建。回答必须对应日志、文件、命令或原始记录。

遇到失败，把“显卡不行”“框架太慢”改写成可验证的假设。例如：“相同权重和输入下，CPU 线程数从物理核心附近继续增加后，Decode 变慢；需要检查带宽与线程竞争。”这是可复查的工程推理，也能迁移到其他平台。
