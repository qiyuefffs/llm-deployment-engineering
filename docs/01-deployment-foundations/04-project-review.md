# 第四部分：项目复盘模板

[总目录](README.md) · [上一部分：核心概念](03-core-concepts.md) · [下一部分：知识库目录](05-knowledge-base.md)

项目复盘用于保存可继续工作的工程事实：当时的目标、运行组合、遇到的问题、修改依据和最终边界。按原稿的十项结构填写，命令和数字链接真实文件。

## 4.1 标准项目复盘

### 一、项目背景

说明谁在什么设备、什么任务下遇到问题。写清输入形式、需要的输出、目标长度、并发与延迟约束。不要从框架功能介绍开始。

```text
需求：在一台16GB共享内存设备上运行本地中文文本生成。
输入：公开短文本与后续准备的长文本任务。
输出：完整答案、运行指标和部署步骤。
边界：先验证文本，不把视觉和NPU成功作为默认条件。
```

阈值若尚未确定写“待定义”，不能补一个看似合理的数字，再说已经达标。

### 二、硬件与环境

记录型号、CPU架构、物理内存、后端可用内存、系统/内核、驱动、Runtime、编译器、Python、框架与源码/镜像身份。采集命令见[硬件层](02-capability-layers/01-hardware-backends.md)。

版本变化分别记录，尤其是驱动、Runtime、框架三者。最终应能判断某个结果对应哪套环境。

### 三、模型与输入

记录模型仓库、revision、许可证、量化、转换过程、tokenizer、模板、分片和校验。输入材料说明来源、格式、大小与预处理；私人样本以授权的公开或脱敏样本替代。

### 四、推理框架

写选择理由与替代路线，保留构建开关、安装命令、最终环境和程序帮助。将“模型结构支持”“量化支持”“功能支持”分别检查。

### 五、部署方案

给出执行顺序、启动命令、端口与别名、资源预算、健康检查、正常请求和停止方法。每一步说明输入、输出文件和检查方法。

### 六、遇到的问题

问题记录至少包括触发输入、首次错误、失败阶段和影响。将观察与推测分开：报错原文是观察，“可能是某kernel不支持”是待验证假设。

### 七、排查过程

按“证据 → 假设 → 检查 → 修改 → 复测”写。只保留帮助理解根因的步骤；避免堆满所有尝试却看不出最终依据。

| 字段 | 示例 |
| --- | --- |
| 现象 | GPU可枚举，NPU模型编译失败 |
| 阶段 | 编译，尚未生成 |
| 证据 | 编译异常与完整日志位置 |
| 假设 | 当前插件/图/形状组合不支持 |
| 检查 | 同模型GPU运行；核对版本与算子支持 |
| 结论 | GPU路线可继续，NPU该组合未通过 |

### 八、优化实验

先列基线，再列变更项。每组保持模型、输入输出、并发、采样、缓存和计时一致；多个变量联动时写组合方案。模板见[实验记录](templates/experiment-record.md)。

### 九、性能与质量

保留请求总数、成功失败、实际token、总时间、吞吐、TTFT/TPOT/ITL、尾延迟、资源与质量。不适用的指标写清原因。语义质量不由速度代替，截图不由统计表代替。

### 十、结论与限制

分别列可用范围、失败组合、未测项和下一步。不确定的结果保留为待验证；对外结论中的每个数字应能追溯到原始文件或明确注明的历史转录。

## 4.2 根据 Intel 工程填写的节选

以下根据 E02 历史记录整理，用来展示填写深度；完整原始运行文件未随笔记公开，不将它包装成新的端到端复现实验。

| 项目 | 已有事实 |
| --- | --- |
| 设备 | Core Ultra 7 256V / Arc Lunar Lake /16GB统一内存 |
| 系统 | Ubuntu24.04.4 |
| 后端 | OpenVINO2026.2.1、GenAI/Tokenizers2026.2.1.0；另有Vulkan/SYCL路线 |
| 模型 | Qwen3.5-9B，IR INT4/INT8，revision见来源表 |
| GPU管线 | 完成19输入/128输出的受限生成 |
| INT4结果 | 21.1599token/s、TTFT184.02ms、TPOT47.26ms |
| INT8结果 | 10.1047token/s、TTFT169.73ms、TPOT98.96ms |
| NPU结果 | INT4编译失败；INT8在420秒超时，未得到推理吞吐 |
| 质量缺口 | 两个GPU输出均在思考阶段到达上限，完整答案待验证 |
| 后续工作 | 完整答案集、长输入、同口径多轮、持续运行 |

**应得结论：** 在该固定组合上，IR GPU路线已有生成记录；INT4短生成速率较高。NPU未通过，完整任务质量和服务容量仍需补验收。

**不能得出的结论：** 所有Intel NPU都不支持该类模型，或者该GPU路线一定比所有llama.cpp路线快。硬件、制品、版本与计时边界不足以支持这种推广。

## 4.3 多硬件适配模板

同一任务迁移多个设备时，保持输入和验收标准一致；各平台模型格式可能不同，应在表中标明。

| 平台/版本 | 制品/精度 | 文本 | 视觉 | 长度/并发 | 性能口径 | 失败与证据 |
| --- | --- | --- | --- | --- | --- | --- |
| 设备A | revision与量化 | 通过/失败/未测 | 同左 | 实际测试值 | 引擎/管线/HTTP | 日志链接 |
| 设备B | revision与量化 | 同左 | 同左 | 同左 | 同左 | 同左 |

填表规则：枚举成功不填生成通过；短请求不填长上下文通过；文本不代替视觉；上游宣称支持不等于当前设备已测。跨平台数值先统一长度、质量和计时，再谈收益。

详细表可从[适配记录](templates/adaptation-record.md)开始。

## 4.4 完整填写示例：本机 CPU 服务演练

这份示例对应本体系实际执行的[完整教程](practice/first-service/README.md)，下面按原来的十项写成一份简短工程记录。原始请求、响应、日志与指标保存在同一结果目录，结论可以逐项复查。

**一、项目背景。** 在普通Windows电脑上完成一次不依赖GPU的模型部署链路，检查下载、校验、服务、功能、流式与性能文件。目标是教学流程和工程验收，不承诺该小模型满足实际业务质量。

**二、硬件与环境。** Windows10.0.26200、AMD64、i5-12600KF、16逻辑线程、Python3.13.12。llama.cpp b9557、提交0f7fada56，纯CPU、4线程。环境字段见[environment.json](practice/first-service/results/2026-10-18-windows-cpu/environment.json)。

**三、模型与输入。** Qwen3-0.6B-Q8_0，固定revision与SHA256见清单。输入包括三道功能题、单字符畸形JSON和两组各四条列举任务；所有提示词保存在程序与结果中，不依赖私人样本。

**四、推理框架。** 使用固定官方Windows CPU二进制，Python标准库负责HTTP、SSE与进程管理。选择它是为了先完成低资源链路，再学习GPU后端，不用额外安装PyTorch。

**五、部署方案。** `.runtime`保存引擎与模型，监听回环18080，别名book-qwen3-06b，ctx2048、parallel2、4线程。程序等待ready后执行请求，采集metrics，停止自己的服务，再运行引擎基准。

**六、遇到的问题。** 计算2+2输出“2”；畸形JSON返回HTTP500。另两道功能题通过，性能请求均得到流式正文与usage。

**七、排查过程。** 保存原始模型响应、结束原因和服务日志，检查错误请求后的健康仍为ok。当前证据能定位到任务输出错误与异常协议问题；尚没有进一步对照证明算术错误来自模型、模板或其他具体因素，因此不编造根因。

**八、优化实验。** 保持模型、线程与服务不变，观察c1/c2两组HTTP。每组四请求、输出上限32，属于小样本并发演练，不是充分的长期优化实验；没有用修改功能题来提高通过率。

**九、性能与质量。** c1/c2输出吞吐53.18/82.12token/s，平均TTFT131.16/217.49ms，平均E2E601.56/778.99ms。引擎pp64为319.08±17.26、tg32为69.88±0.22token/s，另列计时边界。功能2/3，异常协议失败。

**十、结论与限制。** 链路完成，总验收false。应先核对质量与异常处理，再增加任务集、重复轮次和稳态资源测试。它不支持大模型容量、稳定尾延迟或生产可用性的推广结论。

## 4.5 文件级证据怎样保存？

每次运行用独立run-id，保存环境快照、模型清单、最终命令、输入与请求、原始响应、错误、资源采样与统计。统计脚本读取这些文件，结果表不要手改。

```text
results/2026xxxx-platform-model-c2-r1/
├── manifest.json
├── command.txt
├── requests.jsonl
├── responses.jsonl
├── errors.jsonl
├── resource.csv
├── server.log
└── summary.json
```

文件名是建议组织，按工具实际格式保留原件，不要为了凑齐目录制造空证据。公开版本先做授权和脱敏；私有原件与公开副本分开。

## 4.6 怎样更新已有项目记录？

结论发生变化时写明新版本和新证据。例如原文标题写成功，后续运行却有明确kernel失败，应按具体失败输出修订能力范围，保留必要的版本沿革。

知识条目引用最新适用结论，同时保留旧结果对应的版本。这样后续重做时可以判断是环境变化、模型变化，还是原记录不完整。
