# 11 多设备并行、通信与服务扩展

[返回总目录](README.md) · [上一章](10-troubleshooting.md) · [下一章](12-delivery-and-learning.md)

## 1. 先说明为什么需要更多设备

扩展有三种不同目标：单设备放不下、单请求延迟不达标、总吞吐不足。模型分片解决容量，资源复制解决吞吐，降低单请求延迟则要看计算与通信比。不能因为有多张卡就默认 TP 越大越好。

端侧多设备更常见的是 CPU+GPU 混合，或不同任务使用不同加速器；它不自动等同于服务器 TP。网络连接的设备还会增加传输、失败恢复与权限边界，需在单设备基线成立后再扩展。

## 2. 四种并行方式

| 方式 | 切分对象 | 主要目标 | 关键成本 |
| --- | --- | --- | --- |
| TP：Tensor Parallel | 层内部矩阵/张量 | 分担权重与计算 | 频繁集合通信、kernel 尺寸变化 |
| PP：Pipeline Parallel | 模型不同层 | 分担层与容量 | 阶段传输、负载不均、流水线空泡 |
| DP：Data Parallel | 请求/批次到模型副本 | 提高总吞吐 | 额外权重、路由、缓存局部性 |
| EP：Expert Parallel | MoE 专家 | 分布专家参数与计算 | token 路由、all-to-all、专家负载不均 |

这些方式可以组合。框架对 MoE 的 DP/EP 组有特定定义，不能简单套“所有 DP rank 永远完整复制全部专家”。按实际模型、进程组与日志核对每台设备持有什么。

## 3. TP 的内存与延迟并非简单除以卡数

把矩阵分到两张卡后，每卡权重可能减少，但还有未切分参数、通信 buffer、运行时和 KV。KV 头数少于 TP 规模时，部分实现可能复制 KV 而非继续均分。量化布局、Attention 头数与专家结构也可能限制合法 TP 值。

单层计算分担后还需要同步。模型较小或 batch 很低时，通信成本可能占主导，TP=2 反而慢于单卡。NVLink、PCIe 拓扑、跨 CPU socket 与网络差异会改变结果。应把单卡、TP 与副本方案放在相同任务质量和 SLO 下比较。

## 4. PP 适合容量分配，不天然加速单人对话

单请求依次通过不同层，生成下一个 token 仍有依赖。把前半模型放 A、后半放 B，并不意味着同一 token 的所有工作并行完成。多个 microbatch 填满流水线时才可能提高总体利用率；低负载时有空泡。

层数平均也未必负载平均：embedding、输出层、MoE 与多模态模块的内存与计算不同。PP 验收要看阶段时间、等待和传输，不只看每卡显存是否相近。

## 5. DP、副本和路由

若单卡已经满足单请求目标，增加副本可能比增加 TP 更适合扩吞吐。副本复制模型与状态池，通过网关分配请求。路由考虑队列、输入长度、容量与前缀缓存命中，不能只看轮询计数。

多轮会话与前缀缓存可能受益于亲和路由；过强亲和也可能造成部分实例拥塞。故障重试不能无限转发，生成请求若已部分输出，还涉及重复内容与客户端语义。应保留 request ID、取消传播和总时限。

## 6. MoE 与专家并行

MoE 每个 token 通常只选择部分专家，减少激活计算，但总专家权重仍可能很大。专家分布在不同设备后需要将 token 发送到对应专家，再合并结果。热门专家、不同长度与 batch 会造成负载不均。

测量时同时观察专家负载、路由通信与计算，不只比较激活参数数。小 batch 下路由/通信可能抵消收益；端侧专家卸载还可能受主机内存和总线限制。“激活 3B”不能直接当作“只需 3B 权重容量”。

## 7. 通信栈与执行编排不是一回事

NCCL、RCCL、HCCL 等提供特定平台通信能力；Ray、分布式执行器等组织 worker 和资源；TP/PP/DP/EP 是模型与请求的分配方式。三者处于不同层，启动 Ray 不能自动修复设备间通信。

NVIDIA 单机可用 `nvidia-smi topo -m` 检查拓扑；还需确认设备互访、驱动、容器映射和对应通信测试。多节点还涉及网络接口、RDMA/以太网、地址可达、时间同步和模型路径。只针对自己获准使用的节点测试，不扫描未知地址或绕过平台网络限制。

通信故障的最小路径是先单卡推理，再做独立的小型通信验证，然后同机多卡，最后多节点。保存每步版本、拓扑与日志。不要照搬网上一串禁用 P2P/指定网卡环境变量而不解释原因；禁用某路径可能暂时绕过故障，也会改变性能。

## 8. Prefill / Decode 分离

两阶段对计算、带宽与调度有不同需求，规模足够时可放到不同资源池。它需要将 Prefill 产生的 KV 交给 Decode，传输、序列状态、路由、失败恢复与缓存布局都需要处理。

P/D 分离可能改善混合负载隔离，但不保证单请求更快。KV 很大或网络弱时传输可能成为新瓶颈。对单台端侧设备，优先完成本地输入管理、batch、量化和缓存调优；当数据证明需要规模化分离时再评估。

## 9. 扩展实验如何验收

先固定单设备基线，再比较两类配置：在相同请求分布下测吞吐与延迟；在相同 SLO 下测可承受负载与资源成本。分别报告每请求延迟、总输出、Goodput、每设备内存、通信、能耗和错误。

加速比 `T_single / T_multi` 应针对同一任务；扩展效率还要除以设备数。吞吐扩展不能借用单请求时间计算，硬件代际不同也不能称为纯卡数扩展。若新方案只解决“放得下”，可以如实报告容量收益，不强行写成速度提升。
