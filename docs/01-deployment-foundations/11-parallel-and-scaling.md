# 11 单机放不下之后：双卡、多副本与 RPC

[总目录](README.md) · [上一章](10-troubleshooting.md) · [下一章：打包与交付](12-delivery-and-learning.md)

**本章目标：** 先说明扩展是为了解决容量、吞吐还是延迟，再选择并行方式。设备数量增加，并不自动让单请求更快。

## 1. 先选择要解决的问题

| 需求 | 可能路线 | 主要代价 |
| --- | --- | --- |
| 模型单卡放不下 | 模型切分、TP、PP、CPU/GPU 混合、RPC | 通信和调度开销 |
| 单模型已能放下，希望接更多独立请求 | 多副本、请求分流 | 多份权重和额外资源 |
| MoE 跨设备分配专家 | 支持的专家并行 | 专家通信与负载不均 |
| 输入处理与生成互相干扰 | 调度优化；必要时考虑 P/D 分离 | KV 传输与系统复杂度 |

先验证单设备可用配置，再扩展。没有最小基线时，难以判断故障来自模型还是通信。

## 2. 几种并行怎样区分

| 名称 | 分的是什么 | 直观理解 |
| --- | --- | --- |
| TP，张量并行 | 同一层的一部分张量计算 | 多设备共同算一层，通常有频繁通信 |
| PP，流水线并行 | 不同层/阶段 | 请求依次经过设备，受流水线与批次影响 |
| DP / 服务副本 | 完整模型和不同请求 | 每份模型服务一部分用户 |
| EP，专家并行 | MoE 专家 | 根据路由访问分布在不同设备的专家 |
| llama.cpp RPC | 远程后端设备访问与分配 | 主机通过 RPC 使用其他机器资源，具体切分依引擎 |

llama.cpp 的 `--tensor-split`、分层卸载和 RPC，不等同于所有框架中名为 TP 的实现。按实际数据流与日志解释。

## 3. 双 RTX 4080：先核对拓扑

FlowUs 的 32B GPTQ INT4 服务使用 `--tensor-parallel-size 2`。两张 16GB 卡不会自动变成一块无代价的 32GB 显存；权重分片、KV、缓冲和通信都要在各自设备上安排。

```bash
nvidia-smi -L
nvidia-smi topo -m
```

**修订旧记录：** RTX 4080 不支持 NVLink，不能照抄旧笔记中“安装 NVLink 桥接器”的建议。以设备规格和实际 PCIe 拓扑判断，通信能力需要独立测量。

原笔记保存过约 35、55、52 token/s 的不同配置观察，但同时变更了上下文、活跃序列、显存预算、执行方式或镜像版本，且吞吐口径记录不足。它们可用于恢复当时尝试过什么，不能写成一个参数带来确定提升。

正确补测：固定镜像、权重、输入输出长度和客户端负载，从已通过的双卡配置出发，一次只改一个因素，保存每卡内存与通信、延迟和质量。

## 4. 多节点先分三层

FlowUs《多节点部署排障》的顺序很实用：

```text
控制面：Ray 等调度器能否发现节点和资源
数据面：NCCL/RCCL/HCCL 能否完成设备通信
模型面：分布式引擎能否加载权重并完成请求
```

Ray 已连接，只说明控制面可用。通信测试通过后，还要小模型实际推理，最后才加载目标大模型。

推荐执行顺序：版本一致 → 设备与权限 → 基础网络 → 通信测试 → PyTorch all-reduce → 调度资源 → 小模型 → 大模型 → API → 压测。

### 4.1 同机两卡的最小 all-reduce 模板

本仓库提供[示例脚本](examples/all_reduce_check.py)。前提是 NVIDIA CUDA 或 ROCm 版 PyTorch 环境、两张可用设备、对应通信后端和权限已准备好。

```bash
torchrun --standalone --nproc-per-node=2 \
  docs/01-deployment-foundations/examples/all_reduce_check.py
```

每个 rank 放入数值 1，求和后应为 2，进程应正常退出。该脚本是后续设备验证入口，本轮没有在双 GPU 环境执行。

同机通过后，才按各节点环境扩展；不要把此处单机参数直接当成多节点启动命令。

## 5. 实际容量案例：AMD 五机 HIP RPC

原记录设备为五台 Ryzen AI Max+ 395 / Radeon 8060S，运行 Kimi-K2.5 的 Q2 GGUF 制品。已记录组合：

| 项目 | 原记录 |
| --- | --- |
| 内核 | `6.17.0-35-generic` |
| ROCm / HIP | 7.2.1 / 7.2.53211-e1a6bc5663 |
| llama.cpp | `b9557-0f7fada56` |
| 构建 | HIP、RPC、目标 `gfx1151` |
| 设备核验 | 本机与 4 个 RPC 设备各报告 `120000 MiB` total |
| 小上下文 Kimi 观察 | Prompt 19.3 token/s，Generation 8.2 token/s |
| Qwen 小模型冒烟 | Prompt 40.3 token/s，Generation 21.3 token/s |

这些是小上下文引擎观察，没有单机对照，不能算“五机加速比”；也没有证明建议中的 32768 上下文 HTTP 服务已通过正式负载。

### 5.1 先验证每台设备实际可见容量

第 10 章的 TTM 问题导致部分机器只报告 `63215 MiB`，从而无法分配约 81GiB 的目标缓冲。必须让每台机器的运行时容量检查通过，再建立 RPC。

这不是简单把“5 × 128GB”相加。系统和主机额外缓冲、每台可用上限、分配粒度与切分比例都需要分别检查。

### 5.2 构建并检查选项

下面是原记录的构建结构，路径改为当前源码目录：

```bash
cmake -S . -B build-hip-rpc \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_HIP=ON -DGGML_RPC=ON \
  -DGGML_HIP_ROCWMMA_FATTN=ON -DAMDGPU_TARGETS=gfx1151
cmake --build build-hip-rpc --config Release -j 4
rg 'GGML_HIP|GGML_RPC|AMDGPU_TARGETS' build-hip-rpc/CMakeCache.txt
./build-hip-rpc/bin/llama-cli --list-devices
```

版本、运行库和二进制在各节点应一致。即使构建探测到 `GGML_RPC_RDMA=ON`，也不能据此宣称实际经过 RDMA；原记录的 USB4 直连使用 TCP/RPC。

### 5.3 先小模型，再加载大制品

先启动受控网络中的 worker，再在主机枚举 RPC 设备。RPC 不应暴露到公网，地址与端口只允许实验主机访问。

下面使用保留示例地址，**必须替换为自己的授权实验网络地址**，不包含原笔记内网信息：

```bash
RPC_ENDPOINTS='192.0.2.11:50053,192.0.2.12:50053,192.0.2.13:50053,192.0.2.14:50053'
./build-hip-rpc/bin/llama-cli --rpc "$RPC_ENDPOINTS" --list-devices
```

检查本机和四个远程设备的身份、total 与可用量。通过小模型后，目标大模型先使用小上下文、低批量加载，再逐项增加。

原记录的分层比例为：

```text
--split-mode layer
--tensor-split 0.143,0.21425,0.21425,0.21425,0.21425
```

主机比例较小，是为了给本地加载和执行保留空间。比例属于该模型与设备组合，不能原样套所有多机项目。还需核对设备枚举顺序。

### 5.4 加载慢时怎样判断有没有进展

该大制品首次加载为十几分钟量级，包含主机读盘、网络发送和远端分配。可查看目标进程的 I/O 与连接：

```bash
MODEL_PID=12345  # 替换为正在加载模型的实际进程 ID
ps -p "$MODEL_PID" -o pid,stat,etime,%cpu,%mem,rss,cmd
cat "/proc/$MODEL_PID/io"
ss -tinp
```

输出可能包含地址和路径，分享前脱敏。观察读取字节、发送字节、重传和远端内存是否持续变化；按层分段加载时，远端内存先后增加可以是正常现象。

## 6. MoE 的两个规模不要混

总参数量影响主要模型存储需求；每 token 激活参数量影响计算和访问。少数专家激活，并不等于其余权重都可以不存，也不等于推理只需要按激活参数量准备容量。

是否能把专家移到 CPU、其他设备或动态加载，要看引擎实现和实际带宽。先用日志确认分配，再测真实路由负载和尾延迟。

## 7. 本章验收

| 检查 | 通过条件 |
| --- | --- |
| 环境与资源 | 各节点版本、设备、模型制品一致，容量逐台核对 |
| 通信 | 最小通信测试通过，无稳定 hang 或错误 |
| 正确性 | 小模型和目标模型输出功能正常 |
| 目标 | 达到预定容量/吞吐/延迟要求，质量合格 |
| 故障 | 单节点失败能定位，服务有明确恢复步骤 |
| 结论 | 区分“模型放下了”与“性能改善了” |

**本章交付：** 拓扑、版本与分配表、通信结果、目标模型结果和限制。最后进入[工程交付](12-delivery-and-learning.md)。
