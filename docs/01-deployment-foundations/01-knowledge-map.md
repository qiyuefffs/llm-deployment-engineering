# 第一部分：整体知识体系地图

## 本部分概览

本部分建立全书的总路线。先看一个部署项目从哪里开始、到哪里结束，再把沿途问题分配到七个模块和五层能力。后续章节会沿着这张地图逐步展开。

## 1. 一条主线

大模型部署的输入是模型制品、设备和任务要求，输出是能够完成任务的推理服务。这里的任务要求包括输入形式、最长上下文、输出格式、并发、等待时间与资源边界。相同模型用于个人离线问答和多用户服务，合理配置可能完全不同。

```text
模型选择 → 模型格式转换 / 量化 → 硬件后端适配 → 推理框架部署
 → 显存与并发配置 → 性能压测 → 瓶颈定位 → 参数优化
 → 服务化接口 → 监控与交付
```

这是一条常见执行顺序。工程中会回到前面的步骤：发现质量下降时重新选择量化，遇到kernel缺失时重新选择后端，长输入OOM时重新计算内存预算。每次回退应有明确依据，保留变更前后的配置。

### 1.1 七个模块分别负责什么

**硬件后端适配**确认系统、驱动、Runtime和框架能否共同执行目标模型。设备管理器能看到GPU，只完成了设备识别；目标模型完成生成后，才获得了模型执行层面的证据。

**模型格式与量化**准备引擎能读取的制品。模型目录除了权重，还可能需要tokenizer、模板、架构配置、量化配置和视觉处理器。格式与精度的选择要同时考虑兼容性、资源和任务质量。

**推理框架选型**负责加载、计算、KV管理、调度与接口。选型从任务和支持条件开始，随后比较目标负载下的表现。

**显存与KV Cache**确定模型能容纳多长输入、多少活动请求。权重只是预算的一部分，生成中的KV、临时空间、图与框架开销也需要空间。

**性能压测与调优**建立可重复负载，测量吞吐、等待和资源，再依据瓶颈做对照实验。结果要同时包含成功数、实际token和质量。

**多卡与多节点并行**用于扩展容量或服务能力。它引入模型切分、通信和调度，先验证设备通信，再验证目标模型与API。

**工程服务化与交付**把已经验证的组合保存下来。它包括安装、启动、停止、接口、日志、监控、异常恢复和结果文档。

### 1.2 项目开始前先写一页任务说明

以本书CPU演练为例，目标是学习本地服务链路。设备使用Windows x64 CPU；模型为公开Qwen3-0.6B Q8_0；输入是三道自建功能题和一组固定上限的生成请求；输出是响应、日志和测量文件。练习不承担大模型能力或生产容量验收。

真实项目则需要写具体业务任务。例如文档问答要说明文档长度与引用要求，结构化抽取要说明字段和错误标准。性能门槛也必须对应请求长度和并发，不能只写“响应快”。

把任务说明保存到项目README，后续每次修改都回查它。这样优化不会偏离最初需要解决的问题。

## 2. 五层能力模型

原框架把知识分为五层：硬件后端、模型格式与量化、推理框架、显存与性能、工程交付。七个模块是工作内容，五层是知识组织方式。

| 层次 | 这一层回答的问题 | 交给下一层的材料 |
| --- | --- | --- |
| 第1层：硬件后端 | 设备与软件组合能否执行 | 环境记录、后端检查与兼容范围 |
| 第2层：模型格式与量化 | 哪份模型制品可以使用 | 固定模型、文件校验、模板与精度 |
| 第3层：推理框架 | 怎样加载、调度和调用 | 有效命令、可调用服务和功能结果 |
| 第4层：显存与性能 | 目标负载下是否容纳、是否足够快 | 预算、基线、实验和质量判断 |
| 第5层：工程交付 | 怎样重复运行与维护 | 部署入口、验收材料和恢复手册 |

多卡知识贯穿这些层。设备层检查互连，框架层选择TP/PP或RPC，性能层测通信与延迟，交付层记录各节点环境及失败恢复。因此它在目录里有专题入口，也会在各层出现相应交接点。

### 2.1 用一次运行串起五层

在入门演练中，第一层记录Windows、CPU、Python与引擎版本；第二层固定GGUF来源和SHA256；第三层启动llama-server并调用API；第四层保存引擎和HTTP指标；第五层提供完整脚本与实际产物。

同一套程序也发现了质量与异常处理问题。它说明链路检查需要分阶段：进程启动、模型生成、答案正确、错误处理和负载验收，各有独立结果。

### 2.2 各阶段的检查关口

环境阶段确认程序实际使用目标设备；制品阶段确认文件完整与模板匹配；生成阶段检查完整正文和结束原因；接口阶段检查正常、流式和异常请求；压力阶段检查目标负载与资源；交付阶段检查其他人能否按步骤复跑。

检查关口让故障停留在可定位的范围。例如模型尚未加载成功时，先处理制品或后端；单请求正确后再进入并发，避免在压力下同时排查模板和内存。
