# 第一部分：整体知识体系地图

[总目录](README.md) · [下一部分：硬件后端适配](02-capability-layers/01-hardware-backends.md)

## 1. 一条主线

大模型部署工程的主线是：**让指定模型在指定设备上完成指定任务，并用可复查的结果交付。**

```text
模型选择
 → 模型格式转换 / 量化
 → 硬件后端适配
 → 推理框架部署
 → 显存与并发配置
 → 性能压测
 → 瓶颈定位
 → 参数优化
 → 服务化接口
 → 监控与交付
```

图中的顺序是常见交付链路。实际工作会返回前面修正：加载失败时回查模型与后端，内存不足时重新选择量化，质量不过线时撤回优化。

### 1.1 先写明输入、输出和约束

在安装任何包之前，写一页任务说明。下面是填写方式，数值由自己的设备和应用决定：

| 项目 | 必须写什么 | 例子应怎样表述 |
| --- | --- | --- |
| 任务 | 文本、图像、结构化抽取、离线批处理 | 本地中文问答，必须完成最终回答 |
| 设备 | CPU 架构、GPU/NPU、系统、可用内存 | 记录实际型号，不写“某集显” |
| 模型 | 仓库、revision、格式、精度、模板 | 同名模型的不同转换制品分开 |
| 输入 | 来源、实际 token 长度、图片尺寸/数量 | 常见长度和上界分别记录 |
| 输出 | 上限、停止条件、是否流式、是否思考 | 明确首个推理片段与首个最终答案 |
| 负载 | 并发、到达速率、请求数 | 区分单人交互与集中批处理 |
| 质量 | 题目、评分规则、格式规则 | 哪些错误会导致不通过 |
| 性能 | TTFT、完成时间、吞吐、成功率 | 什么负载下达到什么门槛 |
| 资源 | 内存、存储、功率、温度 | 运行期间的峰值和持续状态 |
| 运维 | 安装、启停、重启、升级与恢复 | 接手人能从停止状态恢复服务 |

“显卡已经识别”“模型加载成功”“接口返回 200”“质量通过”“目标负载通过”是不同检查点，不能互相替代。

## 2. 七个工程模块

| 模块 | 主要问题 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1. 硬件后端适配 | 设备、系统、Runtime、框架、算子能否配合 | 设备与模型要求 | 兼容记录、后端验证 |
| 2. 模型格式与量化 | 选哪份制品，能否放下且质量合格 | 源模型、后端限制 | 固定制品、模板、哈希 |
| 3. 推理框架选型 | 用哪个引擎，怎样加载和提供功能 | 模型与任务 | 构建产物、启动配置、API |
| 4. 显存与 KV Cache | 资源能承受多长上下文和几路请求 | 架构、精度、负载 | 预算、采样与容量边界 |
| 5. 性能压测与调优 | 慢在哪里，改动是否有效 | 固定输入和服务 | 基线、对照、质量回归 |
| 6. 多卡 / 多节点并行 | 为容量还是速度扩展，通信是否够 | 模型规模、拓扑 | 分配、通信与端到端结果 |
| 7. 工程服务化与交付 | 怎样稳定安装、使用和维护 | 已通过的配置 | 运行包、监控、验收与恢复 |

每个模块都有明确产物。这样换模型、换平台或交接给别人时，能知道上一步提供了什么、当前还缺什么。

## 3. 五层能力模型

原稿的五层划分保留为第二部分的章节：

```text
第 1 层：硬件后端适配层
第 2 层：模型格式与量化层
第 3 层：推理框架层
第 4 层：显存与性能优化层
第 5 层：工程交付层
```

### 3.1 七个模块怎样落到五层

| 五层能力 | 主责模块 | 与其他层的交接 |
| --- | --- | --- |
| 硬件后端 | 硬件适配，多设备通信条件 | 告诉模型层和框架层可用架构、精度和运行库 |
| 模型与量化 | 模型格式、转换与压缩 | 提供可加载、可校验、质量有依据的制品 |
| 推理框架 | 引擎、API、调度与并行配置 | 提供真正生效的模型、参数、日志与接口 |
| 显存与性能 | 内存预算、测量、瓶颈与优化 | 给出目标负载下可接受的配置和限制 |
| 工程交付 | 封装、验收、监控与恢复 | 把已验证结果变成可重复维护的服务 |

多卡不是单独悬空的技巧：硬件层先验证互连，框架层选择切分，性能层判断收益，交付层处理节点失败。

## 4. 怎样沿着一个项目使用这套知识

以“16GB Intel 笔记本运行 9B 模型”为例，按层推进：

1. **硬件层：** 确认 CPU/GPU/NPU、驱动、OpenVINO 或 Vulkan/SYCL 条件。
2. **模型层：** 为 OpenVINO 选择完整 IR，为 llama.cpp 选择受支持 GGUF，分别记录版本与量化。
3. **框架层：** 先在对应设备完成一次生成，再接接口或应用。
4. **性能层：** 测输入与输出长度、TTFT、生成速度、资源，比较同口径结果。
5. **交付层：** 写清可用后端、当前不通过的功能、启停和回退方式。

这条线来自已有 Intel 工程记录。记录中 GPU 生成可用，9B NPU 编译失败；因此交付结论应具体到“该模型在该 GPU 路线可生成”，不能写成“整个平台全部适配成功”。

## 5. 部署时的检查关口

| 关口 | 通过后才继续 | 常见遗漏 |
| --- | --- | --- |
| 环境 | 版本已记录，最小设备运算通过 | 只检查设备枚举 |
| 模型 | 文件完整，架构与模板匹配 | 只记模型名称 |
| 单请求 | 目标设备实际执行，输出完成任务 | 输出被截断仍当成通过 |
| 服务 | 正常、异常、流式和模型身份检查 | 只看端口开放 |
| 压力 | 目标负载、质量、资源和错误均满足门槛 | 只记最高 tokens/s |
| 交付 | 干净复建、启停、恢复和资料完整 | 沿用作者本机隐藏依赖 |

建议用[适配记录](templates/adaptation-record.md)边做边填；每次优化另开一份[实验记录](templates/experiment-record.md)。
