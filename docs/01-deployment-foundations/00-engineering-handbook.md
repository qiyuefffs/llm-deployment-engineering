# 大模型部署适配基础知识体系

[返回知识体系目录](README.md) · [查看实战 Case](../../cases/README.md)

这份手册回答一个实际问题：**怎样把一个模型稳定地部署到指定设备，并用数据证明它可用。**

内容面向大模型部署工程师、推理优化工程师和多硬件适配工程师。阅读时不需要先掌握完整的模型理论。先按主线走一遍，再按问题查专题章节即可。

## 1. 先记住一条工程主线

```text
明确任务和设备
  → 核对模型与硬件兼容性
  → 准备模型制品和量化版本
  → 跑通单请求
  → 建立性能基线
  → 找出瓶颈并做对照实验
  → 验证质量、稳定性和资源边界
  → 封装服务、监控和回滚
```

“模型能输出一句话”只完成了最小验证。完整交付还要回答：

- 输入多长时仍然可用？
- 并发多少时开始排队或报错？
- 首个可见答案要等多久？
- 长时间运行是否降速、升温或 OOM？
- 更换设备、模型版本或量化格式后，怎样复现原结果？

## 2. 五层知识地图

| 层级 | 解决的问题 | 主要产物 |
| --- | --- | --- |
| 需求与验收 | 什么叫“部署成功” | 任务说明、质量门槛、延迟和资源目标 |
| 硬件与后端 | 设备、驱动、运行库能否支持 | 设备信息、兼容矩阵、后端构建日志 |
| 模型与量化 | 使用什么模型文件，怎样放进内存 | 模型清单、哈希、量化说明、质量对照 |
| 推理与性能 | 怎样运行，慢在哪里 | 启动命令、基线、压测原始数据、优化结论 |
| 服务与交付 | 怎样让别人稳定使用和维护 | API、监控、启动/停止/回滚手册 |

这五层不是五个互相独立的课程。每次改动都要回到上一层检查。例如换成 Q4 可能解决显存问题，但必须重新验证输出质量和 token 速度；换成另一张卡可能需要重新编译后端和重新测量功耗。

## 3. 第一步：把需求写成部署合同

在安装框架前先写下表格。没有实测数据的地方标记为“待测”，不要用估计值冒充结果。

| 项目 | 需要写清楚的内容 | 示例 |
| --- | --- | --- |
| 任务 | 问答、摘要、抽取、代码、工具调用 | 本地文档问答 |
| 输入 | 语言、常见长度、最大长度、图片数量 | 1～4K token，最长 16K |
| 输出 | 常见长度、最大长度、是否流式 | 256 token，流式输出 |
| 设备 | CPU、内存、GPU/NPU、显存、系统 | 目标设备的实际型号 |
| 负载 | 单人、多人、批处理、离线运行 | 交互式单用户 |
| 质量 | 测试样例、格式要求、允许的错误 | JSON 必须可解析 |
| 体验 | TTFT、完成时间、尾延迟 | 95% 请求首字小于 1 秒 |
| 资源 | 峰值内存、磁盘、功耗、温度 | 不超过设备可用内存的 85% |
| 生命周期 | 安装、启动、升级、回滚、断网 | 可离线安装和回滚 |

### 3.1 验收标准要可测量

不要只写“速度快”或“效果好”。至少写三类标准：

1. **功能**：服务能启动，API 能返回，停止条件正确，结构化输出能解析。
2. **质量**：准备固定样例，记录正确率、人工评分或格式通过率。
3. **资源和性能**：记录 TTFT、TPOT/ITL、吞吐、p95/p99、峰值显存和错误率。

每次实验只改变一个主要变量。这样才能知道收益来自量化、后端、并发参数还是输入变化。

## 4. 第二步：确认硬件和软件栈

### 4.1 “支持设备”要逐层成立

```text
硬件型号
  → 操作系统和驱动
  → Runtime / 编译器
  → 推理框架后端
  → 模型架构和算子
  → 精度与量化 kernel
  → API 和业务功能
```

设备管理工具能发现 GPU，只能说明系统看到了设备；不代表当前模型全部在 GPU 上运行，也不代表所有量化 kernel 都可用。

### 4.2 只读采集命令

按设备选择命令，不需要全部执行：

```bash
# Linux 通用
uname -a
lscpu
free -h
lspci

# NVIDIA
nvidia-smi
nvidia-smi topo -m
nvcc --version

# AMD
rocminfo
hipcc --version
# rocm-smi 或 amd-smi 以当前 ROCm 版本为准

# Intel
sycl-ls
# xpu-smi discovery 以已安装工具为准

# 昇腾
npu-smi info
```

这些命令只收集版本和设备信息。公开日志时要去掉用户名、主机名、序列号、内网地址和任何 Token。

### 4.3 兼容矩阵

不要只写“支持 NVIDIA”或“支持 NPU”。每行至少记录：

```text
设备型号 / OS / 驱动 / Runtime / 框架版本 / 后端
模型架构 / 模型 revision / 量化 / 上下文长度
构建状态 / 加载状态 / 正确性状态 / 性能状态
日志位置 / 验证日期 / 已知限制
```

状态建议使用：`未测`、`构建通过`、`可加载`、`功能通过`、`性能通过`。单次短请求成功不能直接升级为“生产可用”。

## 5. 第三步：理解模型制品和量化

### 5.1 一个可运行模型不只有权重

模型制品通常包括：

- 权重文件和文件哈希；
- `config`、模型架构和层数；
- tokenizer、特殊 token 和 chat template；
- 量化方式、校准数据说明和许可证；
- 推理框架、转换工具和版本。

只复制权重文件，可能出现角色混乱、中文分词异常、工具调用失败或停止不了。模型名称相同，也不代表模板、revision 和量化版本相同。

### 5.2 格式、精度、量化不是一回事

| 名称 | 它描述什么 | 常见用途 |
| --- | --- | --- |
| safetensors / PyTorch | 权重文件格式 | Transformers、vLLM 等服务化路线 |
| GGUF | 包含权重和元数据的容器 | llama.cpp、本地和端侧推理 |
| ONNX / IR / Engine | 面向特定运行时的图或引擎 | 需要专用转换和运行时的部署 |
| FP16 / BF16 / FP8 | 数值精度 | 影响显存、速度和硬件要求 |
| INT8 / INT4 | 权重或激活的低比特表示 | 降低内存，需验证质量和 kernel |
| AWQ / GPTQ | 常见的权重量化方法 | 服务化框架中的量化模型 |
| Q4_K_M / Q5_K_M / Q8_0 | GGUF 中常见的量化类型 | llama.cpp 端侧和低显存场景 |

### 5.3 量化的选择顺序

1. 先确认目标框架能加载该格式。
2. 再确认目标硬件有对应 kernel，避免静默回退到 CPU。
3. 用固定样例比较格式正确性和输出质量。
4. 在相同输入、输出上测速度和峰值内存。
5. 记录量化版本、转换命令和模型哈希。

量化的目标是满足整体约束，不是让数字越小越好。Q4 可能降低内存，也可能增加解码误差；某些硬件上 Q8 反而更快，因为 kernel 更成熟。

## 6. 第四步：选择推理框架

### 6.1 用场景选框架

| 场景 | 首选路线 | 主要原因 |
| --- | --- | --- |
| 多用户 API 服务 | vLLM 或同类 serving 框架 | 调度、批处理、监控和 OpenAI 兼容接口 |
| 单机本地服务 | llama.cpp `llama-server` | GGUF、部署简单、可混合卸载 |
| 端侧和低资源设备 | llama.cpp、MLX 或厂商运行时 | 量化、跨平台和资源可控 |
| NVIDIA 专项极致优化 | TensorRT-LLM 等 | 需要固定硬件和较高工程投入 |
| 结构化或复杂工作流 | SGLang 等 | 按实际功能验证，不能只看宣传支持 |

这只是起点。最终选择由模型格式、硬件后端、并发目标和维护成本决定。

### 6.2 vLLM：偏服务化

```text
请求 → 模板/分词 → 调度 → Prefill → Decode → 流式响应
                         ├─ KV Cache
                         ├─ continuous batching
                         └─ PagedAttention
```

常见参数：

| 参数 | 作用 | 调大后的代价 |
| --- | --- | --- |
| `--max-model-len` | 单请求最大上下文 | KV Cache 需求增加 |
| `--max-num-seqs` | 同时运行的序列数 | 并发能力增加，内存和排队压力增加 |
| `--max-num-batched-tokens` | 一轮批处理 token 上限 | 影响 prefill、吞吐和 TTFT |
| `--gpu-memory-utilization` | 允许框架使用的显存比例 | 太高会挤压运行时余量 |
| `--tensor-parallel-size` | 张量并行卡数 | 降低单卡权重压力，但增加通信 |

### 6.3 llama.cpp：偏本地和端侧

llama.cpp 常用 GGUF 模型，支持 CPU 以及多个 GPU/加速后端。常见工具：

- `llama-cli`：单次命令行验证；
- `llama-server`：提供 HTTP API；
- `llama-bench`：固定参数下测量矩阵和生成性能。

CUDA 构建示例：

```bash
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j
```

服务启动示例：

```bash
./build/bin/llama-server \
  -m /models/model.Q4_K_M.gguf \
  -c 8192 \
  -ngl 99 \
  --host 127.0.0.1 \
  --port 8080
```

`-ngl` 表示尝试卸载到 GPU 的层数。层数越高不一定越快；必须结合速度、内存和温度实测。对局域网提供服务时再明确配置监听地址，并配合认证和防火墙。

## 7. 第五步：理解一次推理发生了什么

```text
输入消息
  → chat template
  → tokenizer
  → 排队
  → Prefill（处理输入，建立 KV Cache）
  → 第一个输出 token
  → Decode（逐 token 生成）
  → EOS / 长度上限 / 取消 / 超时
```

### 7.1 Prefill 和 Decode 的区别

- **Prefill**：一次处理输入，通常更偏计算密集；输入越长，TTFT 越容易变大。
- **Decode**：逐步生成输出，通常受权重带宽、KV 读取和调度影响；输出越长，总耗时越大。
- **KV Cache**：保存历史 Key/Value，避免重复计算，但会占用内存；上下文和并发越高，缓存越大。

不要把“收到 HTTP 200”当成完整成功。还要检查停止原因、输出是否完整、JSON 是否有效、流式片段是否正常。

## 8. 第六步：看懂显存和内存

```text
可用内存
  = 模型权重
  + KV Cache
  + Runtime / CUDA Graph / 通信缓冲区
  + 临时工作区
  + 操作系统和其他进程
```

### 8.1 粗略估算

```text
FP16/BF16 权重 ≈ 参数量 × 2 bytes
INT8 权重     ≈ 参数量 × 1 byte
INT4 权重     ≈ 参数量 × 0.5 byte
```

这只是权重估算。实际启动前还要给 KV Cache、临时 buffer 和系统留余量。常见现象是“模型加载成功，一发长请求就 OOM”，原因通常是权重占满后没有给 KV Cache 留空间。

### 8.2 端侧要额外关注

- 统一内存会被 CPU、GPU 和系统共同使用；
- 磁盘 mmap 减少一次性复制，但不等于没有内存压力；
- 温度和功耗会改变长时间运行速度；
- 后台应用、浏览器和显存共享会改变峰值；
- 冷启动、休眠恢复和首次编译应单独测量。

## 9. 第七步：建立性能基线

### 9.1 先固定实验条件

每次记录：

```text
模型文件和哈希
框架/后端版本
设备和电源模式
输入 token 数和输出上限
并发数和请求间隔
随机种子、采样参数
测量工具和时间
```

不能把不同输入长度、不同输出上限、不同温度下的结果直接比较。

### 9.2 指标要分清

| 指标 | 含义 | 主要说明 |
| --- | --- | --- |
| TTFT | 从请求开始到第一个有效输出 | 输入处理、排队和首轮调度 |
| TPOT | 平均每个输出 token 的时间 | Decode 阶段平均速度 |
| ITL | 相邻输出 token 的间隔 | 流式体验和抖动 |
| Output tok/s | 输出 token 速度 | 单请求或批量生成能力 |
| Throughput | 所有请求合计 token/s | 服务承载能力 |
| p95/p99 | 尾延迟 | 长尾请求和稳定性 |
| 峰值内存 | 运行中最高显存/内存 | 资源安全边界 |
| 错误率 | OOM、超时、5xx 等 | 服务可靠性 |

SSE 片段不一定等于一个 token，因此不要直接用“收到多少段”代替 token 速度。

### 9.3 最小压测矩阵

至少测试：

| 维度 | 建议取值 |
| --- | --- |
| 输入长度 | 短、常见、接近上限 |
| 输出长度 | 短、常见、长 |
| 并发 | 1、2、4、8 或设备实际上限 |
| 运行时间 | 单次、连续 5～10 分钟、长时间稳定性 |
| 配置 | 基线、一个优化变量、最终配置 |

每行结果要能回到原始日志或 JSON。只保留平均值会掩盖排队和 OOM。

## 10. 第八步：用假设驱动优化

性能优化不是“把参数都调一遍”，而是：

```text
现象 → 假设 → 最小实验 → 数据 → 结论 → 是否保留
```

### 10.1 常见现象和优先检查项

| 现象 | 先检查什么 | 可能的动作 |
| --- | --- | --- |
| 一启动就 OOM | 权重、精度、后端、并行度 | 换量化、降低并行占用、释放其他进程 |
| 长请求 OOM | `max_model_len`、并发、KV Cache | 降上下文、限并发、启用合适的 KV 量化 |
| TTFT 高 | 输入长度、排队、prefill | 缩短上下文、前缀复用、chunked prefill |
| TPOT 高 | GPU/CPU 利用率、带宽、层卸载 | 调整 offload、量化、线程和 batch |
| 并发上不去 | 调度、KV 余量、队列 | 调 `max_num_seqs` 等参数，先找 OOM 边界 |
| 长时间变慢 | 温度、功耗、内存压力 | 固定性能模式、改善散热、降低持续负载 |
| GPU 利用率低 | CPU 分词、数据复制、回退算子 | 查看日志和 profiler，不要只盯利用率 |

### 10.2 一个优化实验的最小记录

```text
目标：降低 p95 TTFT
基线：配置、输入分布、并发、5 次或更多重复
变量：只开启 prefix cache
保持不变：模型、版本、采样参数、设备状态
结果：TTFT、吞吐、峰值内存、质量、错误率
结论：在何种前缀命中率下保留该配置
```

“GPU 利用率升高”只是过程信号。最终结论要写成“在某种输入和并发下，质量不变，p95 TTFT 从 A 降到 B，峰值内存增加 C”。

## 11. 多卡和多设备并行

| 方式 | 做法 | 适用情况 | 主要代价 |
| --- | --- | --- | --- |
| Tensor Parallel | 一层内部切分到多卡 | 单卡放不下、需要共同计算 | 卡间通信 |
| Pipeline Parallel | 不同层放到不同卡 | 模型很大、需要分层放置 | 流水线气泡和调度复杂 |
| Data Parallel | 每张卡独立一份模型 | 多请求吞吐、请求可路由 | 权重重复占用 |
| 设备分工 | CPU/GPU 或不同加速器分层 | 内存或后端受限 | 复制和同步延迟 |

多卡不是越多越快。先查看 PCIe/NVLink/网络拓扑和通信日志，再比较单卡、多卡的相同负载结果。每个并行配置都要重新测 TTFT、TPOT、吞吐、峰值显存和错误率。

## 12. 服务化和交付

一个可以交付的部署目录至少包括：

```text
README.md                 # 从零开始的执行顺序
environment.txt           # 系统、驱动、运行库、框架版本
model-manifest.json       # 模型来源、revision、哈希、量化
configs/                  # 启动配置，不放密钥
scripts/start.*           # 启动
scripts/stop.*            # 停止
scripts/health.*          # 健康检查
scripts/benchmark.*       # 固定负载压测
results/                  # 原始日志和汇总结果
rollback.md               # 回滚条件和步骤
```

交付前至少验证：

1. 新环境能按文档启动；
2. `/v1/models` 或等价健康检查可用；
3. 一条最小请求和一条边界请求都有结果；
4. 达到内存或延迟边界时，服务能报错或限流，而不是无提示崩溃；
5. 配置、模型和版本可以回滚；
6. 日志不包含 Token、密码、个人信息和内部地址。

## 13. 故障排查顺序

### 模型加载失败

1. 检查路径、权限、磁盘和文件哈希；
2. 检查模型架构和 tokenizer/template；
3. 检查框架版本和后端构建；
4. 用最小模型或最小上下文复现；
5. 保存完整错误日志，不要只截最后一行。

### OOM

1. 区分启动 OOM、首请求 OOM 和长请求 OOM；
2. 记录权重、KV Cache、临时 buffer 和其他进程；
3. 先降低上下文和并发，再评估量化；
4. 每次只改一个变量，并保留可回滚配置。

### 速度低

1. 分开测 Prefill 和 Decode；
2. 检查是否发生 CPU 回退或频繁复制；
3. 查看线程、GPU/CPU 利用率、显存带宽、温度和功耗；
4. 用 profiler 或后端日志验证假设；
5. 优化后重新做质量和稳定性回归。

### API 可用但结果不对

检查 chat template、角色顺序、停止词、采样参数、模型名、流式解析和结构化输出校验。HTTP 状态码正常不代表业务结果正确。

## 14. 需要沉淀的七项结果

每个项目最终都应留下：

1. 硬件和软件环境；
2. 模型来源、revision、哈希和量化信息；
3. 框架、后端和启动命令；
4. 单请求功能验证；
5. 基线和优化后的压测数据；
6. 已知限制、失败边界和回滚方案；
7. 可复建的 README、脚本和结果文件。

没有原始数据的“提升 30%”无法复查；没有限制说明的“支持某平台”不适合作为交付结论。

## 15. 每个知识点都按同一张卡片记录

```markdown
# 知识点名称

## 它是什么？
用一句话说明。

## 它解决什么问题？
说明会影响哪一步部署。

## 什么时候使用？
列出前提和不适用情况。

## 关键参数
```

## 16. 学习和实施顺序

如果刚开始做部署，按以下顺序最省时间：

1. 先用一个小模型跑通单请求和 API；
2. 再理解权重、量化、KV Cache 和上下文；
3. 固定输入和输出，建立单请求基线；
4. 增加并发，观察排队、显存和尾延迟；
5. 只做一个优化实验，并记录代价；
6. 最后再做多卡、端侧迁移和服务封装。

不要一开始同时换模型、框架、量化和硬件。变量太多时，即使结果变好，也无法知道为什么。

**本章的完成标准：**你能根据一份设备和模型清单，写出兼容检查表；能启动一个最小服务；能解释显存和 TTFT/TPOT；能用固定实验判断一次优化是否值得保留。
