# 10 故障排查：现象、证据与最小实验

[返回总目录](README.md) · [上一章](09-profiling-and-optimization.md) · [下一章](11-parallel-and-scaling.md)

## 1. 排障先保留现场

记录原始命令、完整错误、发生阶段、版本、最近变更、输入长度和设备状态，再做修复。不要连续升级驱动、框架和模型后只保留最后成功截图；那会丢失原因和可复现条件。

先判断失败层：系统看不到设备、后端不能初始化、模型不能读取、请求不能解析、计算失败、输出错误、性能不达标。最小实验只跨必要层。若小模型正常而目标架构失败，应优先查模型/算子；若所有模型都无法初始化同一后端，应先查运行栈。

## 2. 构建失败

| 现象 | 优先证据 | 最小修复方向 |
| --- | --- | --- |
| CMake 找不到 CUDA compiler | `nvcc` 路径、CMakeCache、Toolkit 安装 | 明确工具链路径，使用新构建目录 |
| host compiler 不支持 | 完整编译器版本与错误行 | 使用所选 Toolkit 支持的编译器组合 |
| unsupported architecture | `CMAKE_CUDA_ARCHITECTURES` 与 GPU 能力 | 核对目标架构和 Toolkit 支持，不能随意填值 |
| 编译中进程被 killed | 主机 RAM、容器限制、系统日志 | 降编译并发，补足内存，区分 GPU OOM |
| 缺头文件/库 | 配置失败处与依赖搜索路径 | 安装对应开发包，按后端文档配置 |
| 换后端后出现奇怪链接错误 | 旧缓存、残留库、构建路径 | 新建独立构建目录，保留原日志对照 |

并行构建输出的最后一行可能不是最早的错误。搜索日志中首个真实编译/链接错误，并保留其上下文。管道记录使用 `pipefail`。不要通过忽略编译错误、拷贝不明动态库或启用所有实验选项“尝试修好”。

## 3. 运行时找不到设备或 kernel

检查程序是否真包含目标后端、`--list-devices` 结果、驱动/Runtime、可见设备设置及动态库来源。容器内还要核对设备映射与权限；容器镜像提供用户态依赖，不能替代宿主驱动。

`no kernel image` 常指设备代码与目标架构不匹配；动态库符号错误可能来自版本或搜索路径混乱；`illegal instruction` 还可能是 CPU ISA 不匹配。使用正确二进制或重新构建，而不是将它们都归为“显存不够”。

对 LLVM/编译器、SDK 或驱动敏感的后端，先按官方经过验证的版本组合复现。复现成功后每次升级一项，并记录回归，避免无法归因。

## 4. 模型加载失败、输出乱码或不停止

先核对文件完整性、分片、哈希和实际路径，再看加载器支持的架构与量化类型。新模型可能需要更新引擎，旧引擎不会因重命名文件就学会新算子。

可加载但输出异常时，检查 tokenizer、chat template、特殊 token、EOS/stop、Base/Instruct 区别、思考模式、上下文和位置编码。重复问题或角色文本泄漏可能是模板问题；不停止可能是停止符或输出上限问题；长文本退化可能是超出模型或实现支持范围。

`trust_remote_code` 只适用于相应框架的自定义代码机制，不能修复 GGUF 加载器缺架构。需要启用时审查来源和版本。不要为解决所有错误默认执行远程模型代码。

## 5. OOM：按时间点拆分

| 时机 | 重点核对 | 对照实验 |
| --- | --- | --- |
| 读取权重时 | 文件/布局、设备层数、已有进程、主机副本 | 小模型或少卸载层验证 |
| 分配 KV/初始化 | ctx、槽位、统一池、缓存类型 | 缩短上下文与单槽位分别测试 |
| 图捕获/首请求 | 捕获形状、编译、临时 workspace | 适用版本 eager 模式作定位 |
| 长 Prefill | 输入实际长度、microbatch、Attention、多模态预处理 | 降 microbatch，比较峰值 |
| 高并发后 | 活跃 token、队列、预留/驱逐、请求取消 | 单并发→逐档并发，观察释放 |
| 跑很久后 | 泄漏、缓存保留、碎片、其他进程 | 固定周期记录空载与活跃内存 |

主机内存不足、cgroup 限制和 GPU OOM 要分开。权限允许时读系统 OOM 日志；无权限就保留失败与资源数据，不为查看日志随意改系统权限。监控采样可能漏掉峰值，空闲内存也可能不足以满足某个大分配。

修复选项包括更合适量化、更小上下文/输出上限、较低 microbatch/并发、调整缓存或卸载与增加资源。每项影响不同，修复后重新测质量与性能，不能只凭“没有 OOM”宣布最优。

## 6. TTFT 高

先用无负载短输入测试，再增加长度与并发。短输入单请求快、并发慢，优先看队列/槽位；单请求随输入显著变慢，优先看 Prefill；只第一条慢，优先看加载、编译、页缓存与预热。

再检查模板/分词、图像预处理、前缀缓存命中、代理缓冲与网络。用直连本机流式请求和相同服务的代理请求比较，不能仅用最终完整 JSON 响应测首字。思考输出被应用隐藏时，报告用户可见答案延迟，别拿首个隐藏 token 掩盖体验。

有证据后再尝试分块 Prefill、减少无效上下文、前缀复用、调度或限流。Chunked Prefill 可能改善其他请求的 ITL，而不改善长输入自己的 TTFT。

## 7. Decode 慢、生成卡顿或长时间后变慢

检查实际 GPU 卸载、CPU 线程与频率、内存带宽、KV 长度、batch、kernel、跨设备复制与通信。用相同输入对比引擎 bench 与 HTTP：引擎快而 HTTP 慢，继续查服务链路；两者都慢，查设备执行与数据路径。

运行初期快、后来慢，按时间对齐温度/功耗/时钟、主机内存压力、swap 与其他进程。不先修改温控或电压；调整模型、batch、功耗目标、散热和负载设计，保持设备在支持范围内。

卡顿还可能来自长 Prefill 插入、垃圾回收、日志写盘、队列调度或代理攒包。区分精确 ITL 与片段间隔，避免把网络批量到达当成引擎逐 token 波动。

## 8. 并发更高，为什么“性能更差”

先确定“差”是单用户延迟、总吞吐、错误率还是 Goodput。总吞吐上升而单用户变慢可能是正常资源共享；总吞吐下降且排队激增则可能超过有效容量。

观察排队长度、KV 压力/抢占、CPU、输入输出分布、温度、超时和客户端瓶颈。只增加 `-np`、`max-num-seqs` 或线程数，不会创造新的算力。常见方案是将并发限制在 SLO 拐点、限制排队、按任务分池或增加副本。

## 9. API、端口与多模态故障

Linux 本机可先检查 `ss -ltnp`、`curl /health` 和 `/v1/models`。没有监听、模型仍加载、端口被占用、地址仅回环、代理路径错误与权限错误是不同问题。不要通过结束所有 Python/模型进程解决端口占用，只处理自己确认归属的实例。

模型不存在时比较请求 `model` 和实际 served alias；JSON 错误时检查请求体与 Content-Type；流式中断时检查超时、SSE 解析、代理缓冲与客户端取消。服务忙与服务崩溃使用不同重试策略，重试还要受总时限和队列预算约束。

VLM 的图片请求方式取决于接口：可能支持 URL、data URI 或专用上传端点，不能把所有接口写成统一的 multipart 或统一 base64。核对图像格式/大小、projector、预处理与 token/内存预算。API 接收图片成功，不代表模型实际使用了正确视觉编码器。

## 10. 排障结束应留下什么

```text
现象与影响范围 → 可复现条件 → 原始错误与资源证据
→ 被排除的假设 → 最小修复 → 同负载复测
→ 质量/稳定性回归 → 版本和配置变更 → 回滚办法
```

根因尚未确认时写“当前证据支持的可能原因”，不要把一次偶然重启成功写成已定位。能解释为什么修复有效、什么条件下再次失败，才形成可复用经验。
