# E29 · DeepSeek W4A16 TP1 与 TP2 对照

来源文件：`comparison.md`。本地文本 API 测试，2026-07-22；剪枝量化衍生权重，非多模态测试。

本页为脱敏归档：仅替换私人路径、地址、身份、摘要值及附件引用；历史措辞与失败记录保留。命令中的尖括号为占位符，不能原样在 shell 中执行；已执行事实与部署方案按来源说明区分。

## DeepSeek V4 W4A16：395 单机 TP1 / 双机 TP2 vLLM A/B 报告

测试日期：2026-07-22（Asia/Shanghai）

### 1. 结论

单机加载成功，未发生 OOM、段错误或 API 进程退出。`/health`、`/v1/models`、真实中文生成以及从 `<NODE_IP>` 跨机器访问均验证成功。

但在当前 `gfx1151 + vLLM 0.23.1rc1 + Torch MLA Prefill 回退 + Gloo` 实现下，双机 TP2 不只是增加容量，也有明确的性能优势：

- 32/128-token Decode 的双机端到端延迟分别低约 6.2% 和 5.2%（按 warm R2/R3 的绝对值换算）；双机 Decode 吞吐高约 0.9% 和 3.7%。
- 145～3505-token Prompt 的双机 TTFT 低约 18.2%、13.2%、13.4%、13.7%（以单机耗时为分母）；等价地，单机相对双机慢 22.2%、15.3%、15.5%、15.8%。
- 1K～3.5K Prompt 的双机有效 Prefill 吞吐高约 15%～16%。
- 单机权重加载耗时 208.03 秒，双机关键路径 103.61 秒；权重阶段双机约快 2.01 倍。

当前建议：为了方便继续做功能验证和参数调整，保留单机服务运行；如果目标变为最低延迟、长 Prompt 性能或更大 KV/并发余量，应切回双机 TP2。当前 4096 上下文和单请求场景不建议增加第三台机器。

### 3. 测试口径

- 模型：`Israeli-AI/DeepSeek-v4-flash-180b-W4A16-VOLTA-Ampere`
- vLLM：`0.23.1rc1.dev1327+gf25953cc5`
- 数据类型：BF16；权重为 W4A16；KV cache 为 FP8。
- 两边均使用 `--enforce-eager`、`--disable-custom-all-reduce`、`max_model_len=4096`、`max_num_seqs=1`、`max_num_batched_tokens=2048`。
- 单机 `gpu_memory_utilization=0.94`；双机每节点为 `0.75`。
- 单机 TP1；双机 TP2 + Ray + Gloo，节点为 `<NODE_IP>` 和 `<NODE_IP>`。
- 两边均关闭 Prefix Cache；18 个正式请求顺序执行，避免排队和并发调度污染。
- 每种场景运行 3 次。主对比使用 R2/R3 中位数，R1 单独作为新形状/JIT 冷态观察。
- TTFT 从 HTTP 请求发出到首个实际文本 token；Decode tok/s 使用首 token 之后的 `completion_tokens - 1` 个 token 间隔。
- `effective_prompt_tps = prompt_tokens / TTFT`，包含固定调度与首 token 开销，因此短 Prompt 只用于端到端观察，不应视为纯矩阵 Prefill 峰值。
- 该轮是文本 OpenAI API 加载与性能基线，不是图像输入测试，也不是 FlashAttention 开/关专项 A/B。gfx1151 当前 MLA Prefill 使用 Torch SDPA 兼容回退。

### 6. 新形状/JIT 冷态 R1

服务启动后的第一次真实生成触发 Triton kernel JIT。单机从 API health-ready 到首个 4-token 验证请求完成约 82 秒；完成后后续请求恢复正常。启动脚本已增加真实生成 warmup，今后 `[ready]` 将代表 HTTP 与首请求 JIT 均完成。

正式矩阵的每种长度在 R1 也可能触发该长度相关的新 kernel/shape 准备：

| 场景 | 单机 R1 TTFT | 双机 R1 TTFT | 单机变化 | 单机 R1 E2E | 双机 R1 E2E | 单机变化 |
|---|---:|---:|---:|---:|---:|---:|
| Decode 32 | 1.366 s | 1.189 s | +14.86% | 8.007 s | 7.749 s | +3.33% |
| Decode 128 | 0.988 s | 0.600 s | +64.60% | 29.164 s | 27.776 s | +5.00% |
| Prefill 128 | 2.430 s | 0.993 s | +144.54% | 2.859 s | 1.434 s | +99.38% |
| Prefill 1024 | 5.860 s | 4.515 s | +29.78% | 6.269 s | 4.950 s | +26.63% |
| Prefill 2048 | 6.919 s | 6.230 s | +11.05% | 7.355 s | 6.666 s | +10.33% |
| Prefill 3500 | 11.337 s | 9.694 s | +16.94% | 11.788 s | 10.147 s | +16.18% |

双机 API 重启后的独立 warmup 曾出现 79.43 秒 E2E 的一次性 JIT 尾延迟；它不在 18 个正式请求聚合中。单机的首次真实验证请求也承担了相同类型的 JIT，所以正式矩阵前两边都已经做过基础 warmup。

### 7. 单机稳定性

在完整 18 请求矩阵之后，又追加 10 次顺序 Decode-32 稳定性测试：

| 指标 | 结果 |
|---|---:|
| 成功率 | 10/10，100% |
| TTFT median / p95 | 0.988 s / 1.398 s |
| E2E median / p95 | 7.627 s / 8.808 s |
| Decode median | 4.684 tok/s |
| HTTP 5xx / OOM / crash | 0 / 0 / 0 |

第 8、10 次出现 E2E 尾延迟，主机当时可用内存约 7.8 GiB 且 swap 已使用 6.4 GiB；服务没有报错或失去健康状态。若后续追求长期交互稳定性，可把 `gpu_memory_utilization` 从 0.94 下调到约 0.90，以减少 KV 预留和统一内存压力，但需要重新加载后再做一次性能确认。
