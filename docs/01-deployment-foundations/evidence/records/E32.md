# E32 · Qwen-Image 故障复现与验收记录

来源文件：`Qwen-Image-2.1-问题解决与部署文档.md`。本地测试报告，2026-10-19；复现了 Find 搜索路径，没有故意持续触发 GPU reset。

本页为脱敏归档：仅替换私人路径、地址、身份、摘要值及附件引用；历史措辞与失败记录保留。命令中的尖括号为占位符，不能原样在 shell 中执行；已执行事实与部署方案按来源说明区分。

## Qwen-Image 2.1 在 EVO-X2 gfx1151 上的问题复现、修复与部署

文档版本：1.0  
测试日期：2026-10-19  
适用设备：AMD Ryzen AI MAX+ 395 / Radeon 8060S / gfx1151  
适用系统：Ubuntu 24.04.4，ROCm 7.2.4

### 1. 执行摘要

客户日志中的 GPU 崩溃发生在 Qwen-Image 2.1 的 VAE 解码阶段，而不是
模型下载损坏或统一显存不足。根因是 ROCm 上的 PyTorch/MIOpen 进入了
卷积 Find 路径，首次遇到新分辨率时执行大量候选 kernel 的 trial launch，
最终在 gfx1151 上触发 `specified launch failure`。Linux 内核同时报告
`ring gfx_0.0.0 timeout`。

本机已复现该触发机制：

| VAE 路径 | exhaustive search | 512x512 解码耗时 |
|---|---:|---:|
| 默认 MIOpen Find | 20 次 | 178.28 秒 |
| MIOpen immediate | 0 次 | 1.87 秒 |

修复后解码耗时降低约 95.3 倍。采用官方 Qwen-Image 2.1 Turbo 后：

| 推荐配置 | 耗时 |
|---|---:|
| Turbo Q8_0，1024x1024，8 步 | 45.90 秒 |
| Turbo Q8_0，1536x1536，8 步 | 127.64 秒 |
| 原 Q8_0，1024x1024，20 步 | 201.91 秒 |

当前 `sd-server` 服务已切换为 Turbo Q8_0、8 步、CFG 1.0、Euler 和
Turbo sigma schedule，监听：

```text
http://127.0.0.1:18092
```

### 2. 客户现象

客户在 Windows 11 和 Ubuntu 上运行 Qwen-Image 2.1 GGUF 时，采样完成后
在图片渲染/VAE 解码瞬间出现：

- 屏幕闪烁或黑屏；
- AMD 驱动重启；
- `Error setting device 0: unspecified launch failure`；
- Ubuntu 日志出现 `amdgpu: ring gfx_0.0.0 timeout`；
- Python 栈落在 `autoencoder_kl_qwenimage21.py` 的卷积和 `decode()`；
- 调整 64 GB / 96 GB BIOS 显存划分后现象不变；
- 修改驱动超时和内存检测没有解决。

典型栈：

```text
MIOpen(HIP): Error [EvaluateInvokers]
  handlehip.cpp:142: Error setting device 0: unspecified launch failure
at::cuda::miopen_convolution
autoencoder_kl_qwenimage21.py:decode
studio/backend/core/inference/diffusion.py:generate
```

### 4. 问题复现

#### 4.1 复现方法

使用实际 Qwen-Image 2.1 BF16 VAE，在独立 MIOpen 冷缓存目录中执行
512x512 latent 解码：

- `torch.backends.cudnn.benchmark = True`
- `torch.backends.miopen.immediate = False`
- `MIOPEN_SEARCH_CUTOFF=0`
- 开启 `MIOPEN_ENABLE_LOGGING=1`

对照组仅改变 MIOpen 路径：

- `torch.backends.miopen.immediate = True`
- `MIOPEN_SEARCH_CUTOFF=1`

#### 4.2 复现结果

（原文图片：MIOpen VAE A/B；此快照保留文字与数据。）

默认 Find 路径在日志中出现 20 次 `exhaustiveSearch = 1`，耗时 178.28 秒；
immediate 模式为 0 次搜索、1.87 秒。现场日志中 1024x1024 及更高分辨率的
搜索数量更多，因此会进一步放大 Windows TDR 和 Linux GPU timeout 的风险。

完整日志：

```text
logs/vae_miopen_find_512.log
logs/vae_miopen_guard_512.log
```

#### 4.3 复现范围说明

本次已稳定复现导致崩溃的 MIOpen trial launch 路径，但没有故意在 1024x1024
冷缓存下持续跑到 GPU reset，以避免重置共享测试机。修复后的 512x512 和
1024x1024 VAE 均正常完成，完整生成过程中内核日志没有 amdgpu reset、ring
timeout 或 page fault。

### 5. 根因分析

Unsloth Studio 旧版本在设备名为 `cuda` 时设置
`torch.backends.cudnn.benchmark=True`。ROCm 仍使用 `torch.cuda` 命名空间，
因此该设置同样作用于 MIOpen。

启用 benchmark 后，MIOpen 对新卷积形状执行 exhaustive search，对候选
solver 逐个 trial launch 并测量耗时。Qwen-Image 2.1 VAE 解码包含多组大尺寸
卷积，gfx1151 在 trial launch 阶段发生 launch failure。异常发生在 native
MIOpen/HIP 代码中，最终使 Studio 进程终止，Windows 侧表现为驱动重启。

相关上游记录：

- Unsloth issue `#9130`：gfx1151 GPU 崩溃导致 Studio 服务退出。
- Unsloth issue `#11636`：ROCm 上开启 cudnn benchmark 触发长时间 MIOpen 搜索。
- Unsloth PR `#13323`：ROCm 图像和视频卷积使用 MIOpen immediate mode。
- Unsloth PR `#12359`：gfx1151 默认设置 `MIOPEN_SEARCH_CUTOFF=1`。
- Unsloth PR `#12335`：gfx1151 大图 attention query 分块。

BIOS 显存划分、Windows TDR 时间和内存检测只能改变症状出现的阈值，不能
消除 MIOpen trial launch 根因。

### 6. 修复方案

#### 6.1 推荐：升级 Unsloth Studio

升级到 `unsloth>=2026.10.6`，该版本已包含 MIOpen immediate mode 修复。

同时确认没有显式设置以下环境变量：

```bash
unset MIOPEN_FIND_MODE
unset MIOPEN_FIND_ENFORCE
```

#### 6.2 旧版本临时保护

旧版本可先用：

```bash
./scripts/start_unsloth_rocm.sh -H 0.0.0.0 -p 8888
```

脚本通过 `integrations/sitecustomize.py` 在导入 PyTorch 时设置：

- `MIOPEN_SEARCH_CUTOFF=1`
- `torch.backends.cudnn.benchmark=False`
- `torch.backends.miopen.immediate=True`

#### 6.3 不经过 MIOpen 的部署路径

本目录同时提供 `stable-diffusion.cpp` HIP 版本。该路径使用 ggml/ROCm kernel
完成 VAE 卷积，不经过 PyTorch MIOpen，已完成完整图片生成验证。

### 8. 性能结果

（原文图片：Generation time benchmark；此快照保留文字与数据。）

| 模型 | 分辨率 | 步数 | 文本编码 | 采样 | VAE | 总耗时 |
|---|---:|---:|---:|---:|---:|---:|
| Q8_0 | 1024x1024 | 20 | 1.82 秒 | 194.86 秒 | 5.22 秒 | 201.91 秒 |
| Turbo Q4_K_M | 1024x1024 | 8 | 0.82 秒 | 38.89 秒 | 5.16 秒 | 44.88 秒 |
| Turbo Q8_0 | 1024x1024 | 8 | 0.84 秒 | 39.87 秒 | 5.17 秒 | 45.90 秒 |
| Turbo Q8_0 | 1536x1536 | 8 | 0.86 秒 | 115.01 秒 | 11.73 秒 | 127.64 秒 |

Turbo 8 步在 1024x1024 下比基础模型 20 步快约 4.4 倍。1536x1536 的
基础模型 40 步任务实测首步约 29.44 秒，按此推算约需 20 分钟；Turbo
8 步实测仅需 127.64 秒。

#### 8.1 量化选择

（原文图片：Quality and speed tradeoff；此快照保留文字与数据。）

官方 Turbo 模型卡给出的 LPIPS：

- Q4_K_M：0.153；
- Q8_0：0.036。

本机 Q8_0 仅比 Q4_K_M 慢 2.3%，但 LPIPS 降低约 76%，因此质量优先时选择
Q8_0。显存非常紧张或需要极限速度时才选择 Q4_K_M。

#### 8.2 加速方法汇总

1. 使用 Turbo checkpoint 的 8 步 schedule，收益最大。
2. 保持 HIP Flash Attention：`--flash-attn off,diffusion=on`。
3. 保持 `--offload-to-cpu`，权重预取不会显著降低采样速度。
4. Qwen-Image 2.1 prefix KV cache 默认开启。
5. 速度优先使用 1024x1024；1536/2048 的计算量按像素面积增长。
6. `spectrum` 和 `cache-dit` 可进一步跳步，但会产生质量漂移，不建议用于
   只有 8 步的 Turbo 模型。
7. Unsloth Studio 路径应使用最新版 MIOpen immediate mode 和 gfx1151
   attention query chunking。

### 10. 故障排查

#### 10.1 VAE 解码长时间卡住

检查是否存在 MIOpen 搜索日志：

```bash
docker logs qwen-image2-sdserver-turbo 2>&1 | grep -E 'exhaustiveSearch|EvaluateInvokers'
```

Unsloth Studio 路径应确认：

```bash
python - <<'PY'
import torch
print(torch.version.hip)
print(torch.backends.miopen.immediate)
PY
```

ROCm 环境下应输出 `True`。

#### 10.2 服务不可用

```bash
docker ps --filter name=qwen-image2-sdserver-turbo
docker logs --tail 100 qwen-image2-sdserver-turbo
./scripts/start_sd_server.sh
```

#### 10.3 下载返回 429

HF mirror 在多个下载任务同时使用大量连接时可能返回 429。减少并发：

```bash
ARIA2_CONNECTIONS=8 ./scripts/download_qwen_image_2_1.sh
```

脚本支持断点续传，重复执行不会重新下载已校验文件。

#### 10.4 4 步冒烟图模糊

4 步 CFG 6.0 只用于 API 连通性测试，不代表模型质量。正式输出应使用：

- 基础模型：20 步以上、CFG 6.0；
- Turbo：8 步、CFG 1.0、Turbo sigma schedule。
