# E26 · vLLM ROCm 基准测试口径

来源文件：`benchmark_methodology.md`。工程测试方案；默认请求矩阵、流式计时、失败处理和输出文件约定。

本页为脱敏归档：仅替换私人路径、地址、身份、摘要值及附件引用；历史措辞与失败记录保留。命令中的尖括号为占位符，不能原样在 shell 中执行；已执行事实与部署方案按来源说明区分。

## 阶段 3：标准化 Benchmark 方法

### 测试矩阵

每个 `eligible` 模型分别启动独立服务，并执行两组实验：

| 模式 | Decoder backend | RDNA 视觉 encoder | 目的 |
|---|---|---|---|
| `flash_on` | `TRITON_ATTN` | `FLASH_ATTENTION_TRITON_AMD_ENABLE=TRUE` | Triton/Flash 优化组 |
| `flash_off` | `ROCM_ATTN` | `FLASH_ATTENTION_TRITON_AMD_ENABLE=FALSE`，视觉塔回退 SDPA | 非 Flash 基线组 |

这不是简单地切换一个布尔变量：VLM 同时有语言 decoder attention 与视觉 encoder attention。报告必须查看 `observed_attention_backend` 和对应 server log。若启动时 backend 无效，整组标记失败，不允许自动回退后继续声称是指定实验。

DeepSeek V4 当前不能进入该矩阵：其公开架构无视觉输入且权重超限。相关行仍写入 `summary.csv`，用于证明强制目标已被检查。

### 固定变量

- 同一张确定性 PNG：三色条、三种形状/色块及文字 `ROCM 395`；
- 同一 prompt；
- `temperature=0`；
- 相同 `max_tokens`；
- 相同 `max_model_len`、dtype 和 `gpu_memory_utilization`；
- 同一模型缓存；
- 每个 attention 模式重新启动服务，避免 kernel/cache 状态互相污染；
- warmup 不进入正式汇总，但保留请求级记录；
- 默认并发阶梯：1、2、4、8、16、32；
- 每级请求数：`concurrency × 2`。

模型自身的安全上限优先于全局固定值：DeepSeek-VL2 固定为 4096 context；约 50 GiB 以上权重使用 0.7 的 GPU memory fraction，其余默认 0.5。Flash on/off 对同一个模型始终使用完全相同的这些模型级参数，因此组内对照仍受控。Qwen 视觉 profile 统一限制在 262144 pixels，防止框架按不现实的最大分辨率预分配。

### 指标定义

#### 加载

- `load_time_s`：服务进程创建到 `/health` 或 `/v1/models` 首次成功；包含首次模型下载。如果需要区分下载，应先预下载后再跑第二轮；
- `host_used_load_delta_gib`：服务 ready 时主机已用内存减启动前基线；
- `process_rss_ready_gib`：服务主进程及其子进程 RSS；Docker 使用容器 init PID；
- `vram_used_peak_gib`：sysfs `mem_info_vram_used` 峰值；
- `gtt_used_peak_gib`：sysfs `mem_info_gtt_used` 峰值；
- `host_used_peak_gib`、`process_rss_peak_gib`：整个模式运行期间峰值。

APU 必须联合解读 VRAM/GTT/host/RSS。RDNA3.5 的 PyTorch 分配可由 GTT-backed memory 承载，单看 `rocm-smi` 的 firmware VRAM 不足以描述统一内存。

#### 单图图文推理

请求使用 OpenAI `/v1/chat/completions` 流式响应：

- TTFT：发出请求到第一个非空 content/reasoning delta；
- 总延迟：发出请求到 SSE 结束；
- generation time：SSE 首 token 到结束；
- generation tok/s：`(completion_tokens - 1) / generation_time`；
- total tok/s：`completion_tokens / total_latency`。

token 数优先使用 vLLM 返回的 usage。若服务未返回 usage，会标记 `token_count_source=estimated_whitespace`；该行不应和精确 token 行做严肃比较。

#### 并发与上下文

- 每个并发级别用固定 worker 数同时发请求；
- 输出吞吐：所有成功请求 completion token 总数 / 该级 wall time；
- 请求吞吐：成功请求数 / wall time；
- `max_successful_concurrency`：全部请求成功的最高已测试并发；
- `max_concurrency_status=failure_boundary`：下一档已经出现失败；
- `max_concurrency_status=capped`：最高配置档仍成功，因此数值只是下界；
- `max_model_len`：服务启动时限制的单上下文上限，与并发上下文数分开报告。

如果要寻找更高上限：

```bash
./scripts/run_benchmark.sh \
  --runtime docker \
  --model qwen3_vl_4b_instruct \
  --concurrency-levels 1,2,4,8,16,32,64,128
```

### 输出

- `raw_requests.csv`：每个 warmup/single/concurrency 请求；
- `summary.csv`：加载、单请求、并发和最大并发摘要；
- `manifest.json`：命令、配置、环境和最终状态；
- `inventory.json`：硬件/ROCm/内存证据；
- `logs/*.log`：backend 与服务错误证据；
- `report.md`：人类可读汇总；
- `charts.svg`：无需 matplotlib，包含最高测试吞吐、加载耗时、GTT/主机内存峰值和 Flash 相对差值。

### 有效性规则

以下情况不产生真实性能值：

- 模型不存在、模态不符或权重超限；
- 当前空闲 GTT 与 `MemAvailable - host reserve` 的安全估计小于 `min_runtime_gib`；
- vLLM 服务启动失败；
- attention backend 被 vLLM 判定为不兼容；
- 所有请求失败。

这些情况写成 `status=skipped/failed` 和明确 `reason`。不得将其填成 0 tok/s。
