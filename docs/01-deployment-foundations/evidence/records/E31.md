### 结论

现场日志中的崩溃不是模型权重损坏，也不是显存不足。崩溃发生在
Qwen-Image 2.1 的 VAE 解码卷积：

1. Unsloth Studio 在 ROCm 上进入了 MIOpen 的 Find 路径。
2. 首次遇到新分辨率时，MIOpen 对每个卷积形状执行 exhaustive search，
   日志表现为 `exhaustiveSearch = 1`、大量 `EvaluateInvokers`。
3. gfx1151 在 trial launch 阶段触发 `unspecified launch failure`，
   Linux 内核同时报告 `ring gfx_0.0.0 timeout`。

修复方式是避免 MIOpen trial launch：

- 升级到包含 Unsloth PR #13323 的 Studio 版本。
- 或者设置 `MIOPEN_SEARCH_CUTOFF=1`，并让 PyTorch 在 ROCm 上设置
  `torch.backends.miopen.immediate=True`、关闭 `cudnn.benchmark`。

本目录同时提供不经过 MIOpen 的 `stable-diffusion.cpp` HIP 部署路径。

### 实机复现结果

测试环境：

```text
AMD Ryzen AI MAX+ 395 / Radeon 8060S / gfx1151
Ubuntu 24.04.4 / kernel 7.0.0-38
ROCm 7.2.4 / PyTorch 2.10.0
diffusers 0.41.0
Qwen-Image 2.1 BF16 VAE
```

同一 512x512 latent 的冷缓存 A/B：

| MIOpen 路径 | exhaustive search | 解码耗时 | 结果 |
|---|---:|---:|---|
| 默认 Find | 20 次 | 178.28 秒 | 完成，无崩溃 |
| immediate mode | 0 次 | 1.87 秒 | 完成，无崩溃 |

默认 Find 的 178 秒完全符合现场日志中 VAE 解码长时间卡住后
GPU launch failure 的机制；1024x1024 时搜索数量更多，现场因此直接
触发驱动重置。使用保护启动脚本后，512x512 和 1024x1024 解码均
在约 2 秒完成。

### Turbo 加速

非 Turbo 模型在 1536x1536 用 40 步时，首步约 29.4 秒，按此推算需要约
20 分钟。官方 Turbo checkpoint 固定使用 8 步、CFG 1，质量与速度明显
更适合这台机器：

| 模型 | 分辨率 | 步数 | 总耗时 | 官方 LPIPS |
|---|---:|---:|---:|---:|
| Turbo Q4_K_M | 1024x1024 | 8 | 44.88 秒 | 0.153 |
| Turbo Q8_0 | 1024x1024 | 8 | 45.90 秒 | 0.036 |
| Turbo Q8_0 | 1536x1536 | 8 | 127.64 秒 | 0.036 |

Q8_0 只比 Q4_K_M 慢约 2.3%，但失真明显更小，因此默认选择 Q8_0。

```bash
./scripts/generate_qwen_turbo.sh
```

高质量 1536x1536 示例：

```bash
WIDTH=1536 HEIGHT=1536 OUTPUT=output/turbo-1536.png \
  ./scripts/generate_qwen_turbo.sh
```

实机输出：

```text
output/qwen-image-2.1-turbo-q8-1024.png
output/qwen-image-2.1-turbo-q8-1536.png
```

其他可用的加速手段：

- 使用 Turbo checkpoint 的 8 步 schedule，是当前收益最大的方案。
- 保持 `--flash-attn off,diffusion=on`；已启用 HIP Flash Attention。
- 保持 `--offload-to-cpu`；权重预取不会牺牲采样速度。
- Qwen-Image 2.1 prefix KV cache 默认开启，无需额外配置。
- 速度优先时使用 1024x1024；1536/2048 的注意力计算量按面积增长。
- `--cache-mode spectrum` 或 `cache-dit` 可以进一步跳步，但会引入质量
  漂移，不建议用于只有 8 步的 Turbo 模型。
- Unsloth Studio 路径在 gfx1151 上应使用最新版本的 MIOpen immediate
  mode 和 512-row query chunking；旧版本用 `start_unsloth_rocm.sh`。

### 现场处理建议

1. 升级 Unsloth Studio 到 `unsloth>=2026.10.6`。该版本包含
   PR `#13323`，会在 ROCm 上设置 MIOpen immediate mode。
2. 不要显式设置 `MIOPEN_FIND_MODE` 或 `MIOPEN_FIND_ENFORCE`，否则
   会重新进入 Find 路径。
3. 旧版本无法立即升级时，用 `scripts/start_unsloth_rocm.sh` 启动；
   该脚本已实机验证可把 512² VAE 解码从 178.28 秒降到 1.87 秒。
4. 若需要完全绕开 MIOpen，使用本目录的 `stable-diffusion.cpp` HIP
   部署。1024² 正式图已完整生成，内核日志无 amdgpu reset。

调整 BIOS 显存划分或 Windows 驱动超时只能改变症状出现的阈值，不能
消除 MIOpen trial launch 这一根因。

### 旧版 Unsloth Studio 的临时保护

优先升级 Studio。若暂时不能升级，使用：

```bash
./scripts/start_unsloth_rocm.sh -H 0.0.0.0 -p 8888
```

该启动脚本设置 `MIOPEN_SEARCH_CUTOFF=1`，并通过
`integrations/sitecustomize.py` 在 import torch 时启用 MIOpen immediate
mode。不要同时显式设置 `MIOPEN_FIND_MODE` 或 `MIOPEN_FIND_ENFORCE`。
