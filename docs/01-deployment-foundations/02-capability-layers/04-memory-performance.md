# 第4层：显存与性能优化层

## 本章概览

性能优化从一份正确运行的基线开始。先确定要处理的任务和负载，再计算资源、测量速度和等待，最后依据瓶颈修改配置。本章保留原稿六节，配套专题分别讲压测、缓存调度、多设备和推测解码。

## 4.1 核心问题

部署中常见四个问题：为什么显存不够，为什么首token慢，为什么生成慢，为什么并发上不去。它们可能同时出现，但检查入口不同。

内存不足先区分加载、warm-up、长输入与多请求阶段。首token慢要分解排队、模板处理、prefill和传输。生成慢看实际后端、decode、频率与数据读取。并发上不去则要同时查看KV容量、调度、队列和目标延迟。

优化先排除错误配置和CPU回退，再调资源与负载，随后分析算子、编译或通信。每次实验保存基线和变更项，多个参数一起改变时，结论写为组合方案比较。

## 4.2 显存组成

权重保存模型参数，KV保存已处理token的状态，运行时负责图、内存池与管理，临时缓冲用于中间计算。通信、编译和系统也可能需要额外空间。

```text
设备预算 ≈ 权重 + KV + 临时激活/工作区 + 图与运行时 + 预留
主机预算 ≈ 进程与加载缓冲 + 文件映射/缓存 + 应用数据 + 系统预留
```

这些项可能复用或由内存池统一管理，公式用于列清需求，不能把多个监控数字机械相加。框架reserved、进程allocated、设备used和物理容量也有不同口径。

统一内存设备上，CPU、GPU和系统竞争同一资源。观察设备占用时同步看可用内存、swap、磁盘和温度。AMD395工程中，物理容量很大但Runtime可见量受GTT/TTM限制，说明系统容量与后端可分配量需要分别检查。

### 内存峰值与失败阶段

同一服务在不同阶段可能有不同峰值。加载时出现源权重、转换缓冲与目标张量；warm-up时建立执行图与工作区；长输入prefill增加激活与临时空间；持续生成让KV增长；多请求又把这些阶段交错。

| 失败时刻 | 优先核对 | 对应真实记录 |
| --- | --- | --- |
| 大权重/RPC缓冲分配 | 权重、设备可分配量、加载峰值 | AMD TTM把可见量钳到63215MiB |
| warm-up进入kernel | 类型/shape支持、图捕获、工作区 | Mac Metal type42失败 |
| 增加输入长度 | KV、prefill分块、视觉token与窗口 | GB10应补真实长输入验收 |
| 增加活动请求 | 总KV、工作区、调度、抢占 | oMLX并发吞吐和等待变化 |
| 持续运行后变慢 | swap、温度、频率、泄漏和后台竞争 | 统一内存设备需长测 |

加载失败先修容量/兼容，不能用延长HTTP超时解决；kernel缺失先修执行路径，不能把内存比例调到0.99期待通过。把失败时刻写进记录，排错就更直接。

## 4.3 粗略显存估算

先对权重做数量级估算。以下使用十进制GB，仅算理想张量存储：

```text
FP16/BF16：参数量 × 2字节
INT8：参数量 × 1字节
INT4：参数量 × 0.5字节

7B FP16约14GB；32B FP16约64GB；70B FP16约140GB。
```

实际量化还有尺度、元数据、未量化层和布局开销。MoE需要存储总权重，激活参数少主要影响每token计算。权重估算后，还要为KV和执行空间留预算。

GB与GiB也要统一：1GB是10^9字节，1GiB是2^30字节。接近容量上限时，不能直接用模型页面的GB减去设备工具的MiB。

### 将估算与真实文件对应

CPU演练的GGUF文件为639446688字节，引擎报告的模型张量大小为633495552字节。两者差异来自制品与引擎统计口径。这个例子说明文件大小、权重统计和进程总内存是不同数值。

建立预算后，先测模型加载，再测目标长度与并发峰值。只有短请求通过时，尚不能确认业务最大长度可运行。

## 4.4 KV Cache 为什么重要？

生成时复用历史Key和Value，可以减少重复计算；代价是缓存随活动token增长。GQA使用KV头数估算，不能直接拿Query头数代替。

对各层形状相同的标准注意力，可用：

```text
KV字节 ≈ 2 × 层数 × KV头数 × 每头维度
          × 每元素字节 × 所有活动序列的缓存token总数
```

教学算例：32层、8个KV头、每头128维、FP16，每token约128KiB；单路4096token约512MiB，两路各4096约1GiB。这里没有包含块取整、元数据或其他开销，也不能直接套到MLA、混合注意力或滑动窗口结构。

上下文预算包含系统提示、历史、材料、用户输入、模板标记和预期输出。模型宣称上限、服务配置上限与当前资源可承受长度分别确认。权重能够加载，只通过了第一步。

### 调整顺序

先以单请求短输入验证质量，再增加到目标输入输出长度，最后提高活动序列预算。一次只改一个主要变量，并保留失败点。降低KV精度时同时做长上下文质量回归。

## 4.5 性能指标体系

客户端看到的等待包含排队、处理和传输。TTFT是首个有效生成内容到达的时间；E2E是请求至完整接收；TPOT常按首token后的时间除以剩余输出token计算；ITL还受到事件打包和客户端实现影响。

| 指标 | 用途 | 需要同时说明 |
| --- | --- | --- |
| TTFT | 首次响应等待 | 首个有效片段、思考/正文、排队与缓存 |
| TPOT/ITL | 后续生成与流式节奏 | 实际token数、事件与计时方法 |
| 输出吞吐 | 整组输出token/墙钟时间 | 负载、成功数与实际输出 |
| 请求吞吐 | 完成请求数/时间 | 长度、失败和超时 |
| P95/P99 | 延迟分布尾部 | 请求量、重复与持续时间 |
| Goodput | 满足质量和SLO的有效产出 | 预先定义的验收门槛 |
| 资源 | 内存、温度、功率与频率 | 采样窗口与设备/进程口径 |

引擎pp/tg、Pipeline指标和HTTP客户端属于不同边界。跨框架比较前先统一输入输出和计时；无法统一时分列观察。

### 本书实跑的一个例子

Windows CPU演练在c1与c2各发出4个请求、每请求输出上限32。两组均成功，总输出各128token。HTTP输出吞吐为53.18与82.12token/s；平均TTFT约131.16与217.49ms，平均E2E约0.602与0.779s。

总吞吐上升，单个请求平均等待也增加。样本只有4个，因此没有稳定P99结论；该列举任务到上限可能截断，性能请求与功能题分开验收。完整文件和计算见[入门演练结果](../practice/first-service/README.md)。

完整压测的准备、参数和工具选择见[性能测试教程](../chapters/performance/benchmarking.md)。

## 4.6 常见瓶颈与优化方向

内存问题先看失败阶段与预算，首token问题先看排队和prefill，decode问题先看后端与数据读取，多设备问题先看拓扑和通信。监控和Profiler用于验证假设，改动后回到同一负载复测。

| 问题 | 先检查 | 对应专题 |
| --- | --- | --- |
| 长输入/并发OOM | KV、prefill工作区、图、活动序列 | 本章预算与[故障速查](../06-troubleshooting.md) |
| TTFT高或长短请求干扰 | 到达模式、队列、prefill与缓存 | [缓存和调度](../chapters/performance/cache-scheduling.md) |
| 吞吐/延迟关系不清 | 长度、输出、计时与实际并发 | [压测教程](../chapters/performance/benchmarking.md) |
| 多卡/多机更慢或失败 | 互连、通信、切分和版本 | [多设备专题](../chapters/performance/parallelism.md) |
| 尝试MTP/DFlash | 接受率、草稿成本、服务配置 | [推测解码实验](../chapters/performance/speculative-decoding.md) |

### 为什么小batch生成常受带宽影响

每生成一个token都要使用相关权重与历史状态。设备即使有很高的矩阵算力，如果数据搬运跟不上，decode仍会慢。batch较小时权重复用有限，batch增大后有机会让一次读取服务更多序列；代价是KV与每个请求等待变化。

教学算例：假设一个稠密模型每步需读取13.5GB数据，有效带宽200GB/s，仅这部分读取理想下限约67.5ms，对应约14.8步/秒。它忽略计算、KV、缓存与反量化，只用来理解数量级，不是某设备的实测预测。MoE、权重缓存和张量切分要按实际访问重新分析。

这解释了为什么低位宽、内存带宽与有效batch都可能影响速度，也解释了为什么GPU利用率接近100%并不能说明还有多少算力优化空间。RTX2060的5.26token/s要结合CPU/GPU路径和系统压力判断，不能仅看GPU曲线决定增加并发。

### 按成本从低到高推进

先修模板、错误后端、重复进程和不合理预算；再用相同请求扫线程、卸载、上下文与并发；之后比较量化、缓存、分块、图与推测；最后再做kernel、编译或多机改造。每一步先看是否解决当前瓶颈，避免为引入复杂机制而引入。

量化对照还要检查kernel与质量，见[量化验证专题](../chapters/models/quantization.md)。统一内存长测则要看swap、温度和频率，短测成绩不自动代表稳态。

优化验收包含功能、质量、性能和资源四部分。原始响应保存下来，超时、取消、截断和错误单独统计。实验模板见[实验记录](../templates/experiment-record.md)，下一章把已验证组合整理成交付材料。
