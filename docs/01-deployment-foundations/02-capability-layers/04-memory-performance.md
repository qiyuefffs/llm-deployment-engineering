# 第 4 层：显存与性能优化层

[总目录](../README.md) · [上一层：推理框架](03-inference-frameworks.md) · [下一层：工程交付](05-engineering-delivery.md)

## 4.1 这一层的目标

先算资源是否容纳，再建立性能基线，最后根据瓶颈做实验。优化的结果应同时回答：处理了多少请求、输出多少 token、用户等待多久、资源花费多少、答案是否合格。

部署成功的三个阶段要分开：权重加载完成、短请求生成完成、目标长度与并发持续运行完成。前两项通过后，仍可能在 KV 增长、图捕获或并发增加时 OOM。

## 4.2 一次推理占用哪些内存？

```text
设备内存需求 = 权重 + KV + 临时激活/工作区 + 图与运行时 + 预留
主机内存需求 = 进程/加载缓冲 + 权重映射/缓存 + 应用数据 + 系统预留
```

这些项可能共享、复用或由内存池统一管理，因此公式是预算清单，不是把几个监控数直接相加。

| 项目 | 主要受什么影响 | 怎样观察 |
| --- | --- | --- |
| 权重 | 总参数、量化布局、分片与卸载 | 文件、模型加载日志、设备分配 |
| KV | 层、KV 头、head dimension、token、并发、精度 | 引擎 KV 预算、块使用率、上下文日志 |
| 激活/工作区 | prefill 长度、batch、算子实现 | 峰值采样、Profiler、失败分配日志 |
| 图与编译 | 捕获形状、框架、执行模式 | warm-up 前后差值、编译日志 |
| 主机侧 | mmap、页缓存、转换/下载、CPU 卸载 | RSS/PSS、可用内存、swap、缺页 |
| 预留 | 系统、显示、其他服务、碎片与波动 | 长时间运行的高水位 |

权重 INT4 不等于全模型运行内存是 FP16 的四分之一。尺度、元数据、未量化层、KV 和工作区仍然存在。MoE 的“激活参数少”主要影响每 token 计算，不表示只需存储激活的那几个专家。

### 单位统一

`GB = 10^9` 字节，`GiB = 2^30` 字节。记录中同时使用 GB、GiB、MB、MiB 时应先换算，再判断是否够用。尤其在接近内存上限时，不能直接拿模型页面的“大小”减监控里的“容量”。

## 4.3 KV Cache 怎样计算？

对标准、各层形状相同的注意力，可先按下面公式估算：

```text
KV 字节 ≈ 2 × 层数 × KV头数 × 每头维度
          × 每元素字节 × 所有活动序列的缓存token总数
```

前面的 2 是 Key 与 Value。GQA 使用 KV 头数，不是 Query 头数；MLA、混合注意力、滑动窗口、不同层结构和压缩缓存需按实际实现重新计算。

### 教学算例

假设模型有 32 层、8 个 KV 头、head dimension 128，KV 为 FP16：

```text
每 token KV = 2 × 32 × 8 × 128 × 2 = 131072 字节 = 128 KiB
单路 4096 token = 512 MiB
两路各 4096 token = 1 GiB
```

这是理想存储估算，尚未算块取整、元数据、前缀共享、跨卡分片和其他开销。它用于理解“长度翻倍、并发翻倍为什么要多留空间”，不是任何具体模型的实测占用。

### 上下文预算

一次请求需要考虑：系统提示 + 历史对话 + 检索材料 + 用户输入 + 模板标记 + 最大输出。模型宣传的最大上下文、服务配置的上限、当前资源可承受长度是三个不同条件。

先测试短输入，再逐步增加到实际业务长度。只用十几个输入 token 测出的结果，不能说明 32K 文档问答可用。

## 4.4 怎样设置上下文与并发？

按以下顺序调整，其他参数先固定：

1. 单请求、短上下文通过模型与模板验收。
2. 增加到目标输入输出长度，记录加载后与生成峰值内存。
3. 设定满足业务的 `max-model-len`，留出明确余量。
4. 增加活动序列预算，观察排队、KV 和单请求延迟。
5. 调整每轮 token 预算，比较 prefill 与 decode 的相互影响。
6. 最后测试峰值负载、长时间负载与取消请求后的回收。

`max-num-seqs=4` 不代表服务最多只能收到四个 HTTP 请求。更多请求可能等待调度，也可能由上游排队或拒绝。客户端并发、等待请求数、引擎活动序列数必须分开记录。

`gpu-memory-utilization=0.80` 是框架预算参数，不是把计算核心利用率设为 80%。提高它可能增加 KV 容量，也可能缩小系统余量；不能直接解释成算力提升。

## 4.5 端侧共享内存的特殊问题

统一内存减少了独立设备内存的边界，但 CPU、GPU、应用和系统仍竞争容量与带宽。交换文件能让进程存活，却可能显著拉长延迟。观察 GPU 内存时要同步看系统可用内存、swap、磁盘与温度。

### AMD 395：系统有内存，后端却分配失败

E03 的五机记录中，某设备被 HIP 识别为约 63,215MiB，而目标为 120,000MiB。一次约 87,013,675,008 字节的分配失败。排查发现 GTT 请求值为 125,829,120,000 字节，但 TTM 实际约 66,286,690,304 字节。

这里的问题在运行时可见预算和特定驱动限制。先核对设备日志、GTT 与 TTM，再评估驱动方案。不能只依据物理内存标签调大模型参数，也不要把某次特定 DKMS/内核改动写成通用系统优化命令。

### Intel 16GB：部分卸载与 IR 路线

E02 的 Vulkan/SYCL 记录采用 GPU 23 层、CPU 10 层。它属于混合执行，速度受 CPU 内存带宽与数据转移影响。另一条 OpenVINO IR 路线的布局、运行时和计时不同，应分别建基线。

### Mac：内存上限与持续运行

先检查模型加载后的可用内存，再增加上下文与并发。不要用关闭系统保护或无上限分配作为默认优化步骤。持续测温度、频率和内存压力，才能知道短测成绩是否可维持。

## 4.6 Prefill 与 Decode 分别慢在哪里？

**Prefill** 一次处理输入上下文，构建初始 KV。输入较长时，矩阵计算、注意力、临时工作区与调度预算会影响首 token 时间。

**Decode** 基于已有 KV 逐步生成。低 batch 时经常受权重读取和内存带宽约束；并发增加后可能更充分利用计算，也会增加 KV 读取与调度开销。不能不看模型和负载就认定一定是“算力瓶颈”或“带宽瓶颈”。

```text
用户等待首 token：排队 + 模板/tokenize + prefill + 首次采样 + 传输
后续生成：反复 decode + 调度 + 流式传输
```

先确认慢在哪一段，再选择工具。TTFT 高可能来自排队，不一定是 prefill kernel 慢；ITL 波动可能来自流式缓冲，不一定是每轮设备计算波动。

## 4.7 指标与计算口径

| 指标 | 常用含义 | 使用时要说明 |
| --- | --- | --- |
| E2E latency | 客户端发起至完成 | 是否包含排队、网络、重试与输出解析 |
| TTFT | 发起至首个有效生成内容到达 | 空事件、思考与正文怎样计时 |
| TPOT | 首 token 后平均每个输出 token 耗时 | 常用 `(完成时间−首token时间)/(输出token数−1)` |
| ITL | 相邻输出片段/token 的间隔 | 片段可能含多个 token，工具实现需核对 |
| 输出吞吐 | 总输出 token / 整个测试墙钟时间 | 不能加输入 token 充当生成速度 |
| 请求吞吐 | 完成请求数 / 测试时间 | 必须同时列错误率和请求长度 |
| P95/P99 | 延迟分布的高分位 | 小样本无法给出可靠尾部判断 |
| Goodput | 同时满足质量与延迟要求的有效产出 | 阈值、失败和截断处理必须预先定义 |

单请求输出速度、引擎 tg、HTTP 总吞吐和多请求聚合吞吐各有用途，表格列名写清楚。多请求总吞吐上升时，单个用户仍可能变慢。

### 三种计时边界

```text
引擎基准：              模型执行相关区间
Pipeline 指标：         管线定义的生成相关区间
HTTP 客户端：请求发出 → 排队/处理/传输 → 完整接收
```

跨框架比较时先统一边界；无法统一的只作候选观察，不计算严格加速比。

## 4.8 负载怎样设计？

一个有效测试组至少写清：输入材料及来源、tokenizer、输入分布、输出上限、实际输出、请求总数、并发或到达率、采样、预热、缓存状态、超时与错误统计。

| 测试类型 | 回答什么问题 | 示例组织 |
| --- | --- | --- |
| 冒烟 | 能否正确走通 | 少量短请求，检查正文和错误 |
| 固定长度基准 | 引擎/配置差异 | 固定输入输出 token，重复多轮 |
| 真实业务 | 对应用是否有用 | 公开或脱敏任务、质量标准、实际长度分布 |
| 并发扫描 | 容量与延迟拐点 | c=1、2、4 等独立测试组 |
| 到达率扫描 | 排队何时开始积累 | 控制每秒请求，观察队列和错误 |
| 突发 | 瞬间提交后的恢复 | 固定总请求，记录排队与尾延迟 |
| 持续运行 | 温控、泄漏和稳定性 | 达到稳态后继续观察资源与错误 |

随机 token 适合控制长度，不能验收语义。业务集适合验收质量，但长度不同会影响性能解释，两类都保留。

### 冷启动、暖启动与缓存

分别记录下载、模型加载、图编译/捕获、第一次生成和预热后生成。Prefix Cache 测试必须说明是否重复前缀、何时清空缓存，以及首轮与后续轮次。模板看似相同但 token 前缀不同，也可能无法命中。

同一组参数至少重复多轮，报告各轮结果和波动；正式评估尾延迟时增加请求量与运行时间。不要把 10 个请求算出的 P99 当作稳定线上承诺。

## 4.9 一次完整的性能测试怎样执行？

### 第一步：固定服务与输入

使用上一层已验收的 GB10 服务；复制完整启动命令，保存模型身份和环境。检查没有其他任务争用设备。先跑一条正常请求，记录完整答案。

### 第二步：采样资源

NVIDIA 环境在单独终端执行，下列数据是设备级辅助指标：

```bash
mkdir -p results
nvidia-smi --query-gpu=timestamp,name,memory.used,memory.total,utilization.gpu,temperature.gpu,power.draw \
  --format=csv -l 1 > results/gpu.csv
```

测试结束后在此终端按 Ctrl+C。统一内存设备同时采集主机内存与 swap；无法支持的字段记为不可用，不能填零。采样间隔可能漏过瞬时峰值。

### 第三步：执行可对照负载

E01 原始突发测试的公开路径改写：

```bash
vllm bench serve \
  --backend openai-chat \
  --base-url http://127.0.0.1:8001 \
  --endpoint /v1/chat/completions \
  --model Qwen3.6-35B-A3B-FP8 \
  --tokenizer /srv/models/Qwen3.6-35B-A3B-FP8 \
  --dataset-name random \
  --random-input-len 2048 --random-output-len 128 \
  --num-prompts 200 --request-rate inf --seed 42 \
  --save-result --result-dir results/gb10-fp8-burst
```

结果保存选项先用该版本 `vllm bench serve --help` 核对。`request-rate inf` 是尽快发送，不是低延迟目标；后续并发扫描可在版本支持时用 `--max-concurrency 1/2/4` 分别运行，保存不同目录，这些补测不能算作原记录已完成。

### 第四步：核查完成情况

核对请求数、成功数、实际 token、结束原因、总时间和原始错误。固定输出上限不保证实际总输出恰好等于上限乘请求数，EOS、模板或工具设置都可能改变它。

### 第五步：写结论

E01 记录 200/200 成功、297.46 秒、25,600 个输出 token、86.06 token/s；平均 TTFT 148,430.70ms，P99 TTFT 293,115.24ms。它展示了该突发负载下的处理能力，也说明等待很长。不能据此宣称交互体验快。

服务最大活动序列为 4，而客户端突发提交 200 个请求，排队是解释 TTFT 的重要因素。接下来的动作是测目标到达率与并发、检查队列，而不是直接调高输出采样温度。

## 4.10 怎样定位瓶颈？

| 现象 | 先检查 | 再做的实验 |
| --- | --- | --- |
| 模型加载就失败 | 制品、算子、权重预算 | 小模型/更低精度/部分卸载 |
| 长输入 OOM | KV、prefill 工作区、图 | 降长度或每轮 token，保留失败点 |
| 单请求 decode 慢 | 实际后端、CPU 回退、带宽与频率 | 相同输入下改卸载或后端 |
| 并发升高 TTFT 暴涨 | 队列、活动序列、prefill 干扰 | 固定长度做到达率扫描 |
| 吞吐高但流式卡顿 | ITL 分布、SSE 缓冲、批量发送 | 直连本机对比代理链路 |
| 多卡更慢 | 模型大小、P2P、互连、通信比例 | 单卡与双卡同任务比较 |
| 长测逐渐变慢 | 温度、频率、内存压力、swap | 冷暖与稳态分开比较 |
| 显存看似空闲但分配失败 | 框架预算、内存池、碎片、运行时限制 | 对照日志与失败分配字节 |

需要进一步定位时，再用 PyTorch Profiler、Nsight Systems、rocprof、VTune 或平台工具。一次 trace 只捕获代表性短窗口，标注阶段与请求；Profiler 自身会增加开销，不能把带 trace 的数字直接作为正常性能。

优化顺序通常是：排除错误后端/回退 → 修正预算和负载 → 调整调度 → 验证 kernel 与编译 → 再考虑复杂并行或推测解码。

## 4.11 真实记录一：量化与后端对比

### Intel INT4 / INT8

| 相同管线下的短生成 | INT4 | INT8 |
| --- | ---: | ---: |
| 输入/输出 token | 19 / 128 | 19 / 128 |
| 生成 token/s | 21.1599 | 10.1047 |
| TTFT ms | 184.02 | 169.73 |
| TPOT ms | 47.26 | 98.96 |

INT4 的生成速率约为 INT8 的 2.09 倍，但首 token 并未同时变快。输出在思考阶段截断，不能得出完整答案质量结论。对业务选择还需长输入、多轮和质量回归。

### Vulkan / SYCL

相同设备的 llama.cpp pp512/tg128 三轮记录，Vulkan 生成 11.54±0.13 token/s，SYCL 为 10.22±0.19。Vulkan 另有 HTTP 生成 11.38 的记录。保留引擎与 HTTP 的分列，不与 OpenVINO 管线混算。

### Gemma AWQ4 / AWQ8

E09 记录 GB10 128GB、vLLM 0.19.0+cu130、同系列 Gemma 26B-A4B、ctx16384、服务序列预算2、batched4096、内存比例0.65、prefix cache、eager。200 个请求、客户端并发2，输入目标1024、输出目标128。

| 项目 | AWQ4 | AWQ8 |
| --- | ---: | ---: |
| 测试耗时 s | 427.70 | 537.49 |
| 实际总输入 / 总输出 token | 206139 / 25696 | 206139 / 25696 |
| 输出吞吐 token/s | 60.08 | 47.81 |
| 平均 TTFT ms | 272.97 | 338.92 |
| P95 TTFT ms | 283.52 | 359.94 |
| 平均 TPOT ms | 31.32 | 39.39 |

该组说明制品与 kernel 组合值得实测。源笔记的峰值并发字段与配置存在不一致，不纳入结论；约相同的引擎总占用也不能证明 AWQ4/8 权重一样大，因为 KV 池预算会填充空间。质量等价仍未验证。

## 4.12 真实记录二：并发的吞吐与延迟权衡

E06 为 DeepSeek-V4-Flash-4bit 的 oMLX 测试，EvalScope 1.7.0，输入目标128、输出上限256：

| 客户端并发 | 请求数 | 输出吞吐 token/s | 平均请求延迟 s | TPOT ms |
| --- | ---: | ---: | ---: | ---: |
| 1 | 20 | 29.38 | 7.582 | 34.2 |
| 2 | 10 | 41.11 | 10.257 | 47.5 |
| 4 | 10 | 55.15 | 13.459 | 69.8 |

并发增加带来总吞吐提升，同时单请求更慢。服务容量应根据允许的延迟选取，不能只选吞吐最大的那一行。各组请求数不同、样本较少、缓存状态不全，因此该表用于理解权衡，后续需等样本量重测。

## 4.13 真实记录三：推测解码怎样评价？

推测解码先提出多个候选 token，再由目标模型验证。收益受草稿成本、接受率、目标模型执行与负载影响；吞吐增加也可能改变流式片段节奏。

E07 的 Gemma MTP 使用输入512、输出上限256：

| 并发 / 请求数 | 关闭 MTP token/s | 开启 MTP token/s | 观察增幅 |
| --- | ---: | ---: | ---: |
| 1 / 20 | 20.82 | 30.14 | 44.76% |
| 2 / 40 | 36.87 | 48.92 | 32.68% |
| 4 / 80 | 49.33 | 75.57 | 53.19% |

但 c1 的平均 ITL 从46.12ms变为78.27ms；c2 TTFT 从352.24ms变为608.22ms。评价时同时查看吞吐、TPOT、ITL、TTFT 和接受率，不能用单个字段代表全部体验。原始逐请求文件与质量等价数据未附，保留这一限制。

E08 的 DFlash 观察为21.52→43.74 token/s，约2.03倍；与此同时上下文、序列预算、内存比例和 eager 配置都变化了。它属于两套配置的观察，不能将全部增益归因于 DFlash。应先固定服务配置，再只切换推测解码，补做对照。

## 4.14 实验记录与验收

每次实验只改一个主要变量；若必须联动，明确写“组合方案比较”。保留基线命令、变更项、实际输入输出、各轮结果、质量与资源。模板见[实验记录](../templates/experiment-record.md)。

验收分四项：功能正确；答案质量达到任务标准；目标负载下延迟/吞吐达标；持续运行资源与错误率达标。阈值由任务决定，不把笔记中的某个数字设为所有设备的标准。

边界至少覆盖：超长输入、生成到上限、客户端取消、无效请求、资源不足。失败时应返回明确错误并可恢复，不能生成一段“看起来正常”的默认答案掩盖失败。

完整转录与离线重算见[来源与数据](../evidence/README.md)。本层操作完成后，把确定的模型、参数和验收方法交给[工程交付层](05-engineering-delivery.md)。
