# 第 5 层：工程交付层

[总目录](../README.md) · [上一层：显存与性能](04-memory-performance.md) · [下一部分：核心概念](../03-core-concepts.md)

## 5.1 这一层解决什么问题？

把“当前终端能运行”变成“其他人按说明能安装、调用、检查和恢复”。交付包括模型、运行环境、服务配置、输入与结果、监控、故障处理。文档中的版本、路径、别名和代码必须一致。

工程边界先写清：支持哪些设备、模型精度、输入类型、最大长度与目标并发；不具备的功能写在能力表。历史实验参数不自动成为生产配置。

## 5.2 七项交付材料

| 产物 | 至少包含 | 检查方式 |
| --- | --- | --- |
| 1. 环境说明 | OS/内核、CPU/设备、驱动、Runtime、依赖、源码/镜像身份 | 新环境按说明准备 |
| 2. 模型清单 | 仓库、revision、许可证、精度、tokenizer、模板、校验 | 文件与清单一致 |
| 3. 部署入口 | 安装、配置、启动、停止、健康检查 | 从空目录执行到 ready |
| 4. 接口与样例 | 请求、响应、流式、异常与能力范围 | 客户端可直接验证 |
| 5. 测试材料 | 输入、参数、原始结果、统计方法、质量判断 | 能重新计算和复查 |
| 6. 运维手册 | 日志、监控、告警、排错、重启、回滚 | 故障后能按步骤恢复 |
| 7. 结论与限制 | 通过项、未通过项、版本边界、已知缺口 | 不把未测项算成功 |

交付清单的目的不是增加文件数量。每项材料都应能回答一个实际问题，避免空模板占满目录。

## 5.3 推荐目录

```text
deployment/
├── README.md                 从哪里开始、适用范围
├── environment/              硬件、依赖、镜像或源码身份
├── models/manifest.json      模型身份与下载校验，不存大权重
├── configs/                  服务参数、生成参数、公开示例配置
├── scripts/                  下载、启动、检查、停止、测试
├── inputs/                   有权公开的样例与来源
├── tests/                    功能、质量、异常和性能入口
├── results/<run-id>/          请求、原始响应、资源采样、统计
├── docs/                     部署、排错、回滚
└── LICENSE                   自有代码许可与第三方说明
```

私有配置、真实凭据和原始业务输入不进入公开目录。示例使用通用路径和本机地址，公开样例单独准备；删除敏感字段后也要检查日志正文和图片。

## 5.4 环境怎样固定？

### Python 与原生组件

Python 依赖用独立环境固定；同时保存驱动、Runtime、编译器和原生库。`pip freeze` 只能描述 Python 包，不能代替 GPU 环境说明。源码安装还要保存 commit、子模块和构建开关。

```bash
python -m pip freeze > environment/python-packages.txt
cmake --version > environment/cmake.txt
git -C llama.cpp rev-parse HEAD > environment/llama-cpp-commit.txt
```

按实际框架执行对应命令。下载器、构建器与运行环境可分开，避免模型转换升级破坏已验收服务。

### 容器

容器内的用户态库与宿主驱动仍需兼容。NVIDIA 容器看不到 GPU 时，先检查宿主 `nvidia-smi`、Container Toolkit 与容器设备访问，再排模型。AMD/昇腾也有设备映射和配套库要求。

镜像标签可能变化，交付时记录 digest：

```bash
docker image inspect --format '{{json .RepoDigests}}' <已验收镜像>
```

端口、模型路径和共享内存用配置明确给出。模型挂载优先只读；根据需要配置足够的共享内存，不把 `--privileged`、整盘挂载、host 网络作为通用起点。

旧双卡笔记中存在不同 vLLM 镜像与多组参数，它们应各自保存，不能只留下最后一个 `docker run` 而丢掉对应结果。

## 5.5 配置怎样管理？

至少区分服务配置、生成配置、压测配置与应用配置：

| 配置 | 主要内容 | 常见混淆 |
| --- | --- | --- |
| 服务 | 模型、后端、上下文、活动序列、内存、端口 | 调高内存比例被写成调高计算利用率 |
| 生成 | 温度、top_p、输出上限、停止条件、思考模式 | 服务默认值与请求覆盖不一致 |
| 压测 | 输入输出分布、到达率、并发、样本、超时、缓存 | 客户端并发等同于引擎序列数 |
| 应用 | URL、模型别名、重试、业务超时、解析 | 用磁盘路径代替公开模型别名 |

每次结果保存一份最终生效配置，包含默认值和覆盖项。不要只写“开启优化”。

## 5.6 API 验收

接口验收先在本机直连，再经过应用和代理。第一步确认引擎，第二步确认调用链，出现问题时能定位在哪一层。

| 测试 | 输入 | 应检查 |
| --- | --- | --- |
| 模型发现 | `/v1/models` | 别名与应用配置一致 |
| 普通对话 | 短文本、有限输出 | 非空正文、usage、finish_reason |
| 多轮对话 | 明确依赖前文的问题 | 角色与历史被正确传递 |
| 流式 | 同一请求 `stream=true` | 有效事件、终止、无代理缓冲 |
| 无效请求 | 错别名、缺字段 | 清晰状态码和错误体 |
| 长输入 | 接近/超过服务限制 | 预算正确、越界明确失败 |
| 取消 | 客户端中止 | 服务能释放资源并继续处理 |
| 特殊能力 | 工具、JSON、图片等 | 逐项按应用标准验收 |

### 可复制的非流式检查

目标是上一层端口8001的服务，使用 Python 标准库，不引入客户端 SDK 版本变量：

```python
import json
import urllib.request

payload = {
    'model': 'Qwen3.6-35B-A3B-FP8',
    'messages': [{'role': 'user', 'content': '用一句话解释KV缓存。'}],
    'max_tokens': 256, 'temperature': 0, 'stream': False,
}
request = urllib.request.Request(
    'http://127.0.0.1:8001/v1/chat/completions',
    data=json.dumps(payload).encode('utf-8'),
    headers={'Content-Type': 'application/json'},
)
with urllib.request.urlopen(request, timeout=180) as response:
    result = json.load(response)
message = result['choices'][0]['message']
print(json.dumps(result, ensure_ascii=False, indent=2))
assert (message.get('content') or '').strip(), '最终正文为空，需要检查思考和截断'
```

这段仅检查结构和非空正文，语义仍需按任务判断。若模型在256 token内只生成思考，检查结束原因并调整业务预算，不能把断言改为“任何字段非空”来掩盖未完成答案。

## 5.7 启动、停止与回滚

启动手册包括进入哪个环境、读取哪份配置、日志写在哪里、怎样确认 ready、启动超时后查什么。服务重启后先冒烟，再恢复流量。

实验初期以前台运行加日志保存最便于排错；停止用当前终端 Ctrl+C。托管时选定 systemd 或容器等单一方式，明确服务名、状态检查和停止命令。不要使用批量 `pkill` 清理不明进程。

回滚要保留上一版模型身份、环境和配置。流程为：停止接入新请求 → 处理在途请求 → 停止当前实例 → 启动上一版 → 健康和功能检查 → 恢复调用。端侧内存无法容纳双实例时，说明这会产生维护窗口。

升级逐项进行：驱动、Runtime、框架、模型不要同时替换后再比较一张图。必须联动升级时，把它记录为完整新环境，重新跑功能和目标负载。

## 5.8 监控看什么？

| 层次 | 建议指标 | 它帮助发现什么 |
| --- | --- | --- |
| 服务 | 请求数、错误、超时、取消、队列 | 请求是否积压或失败 |
| 用户体验 | TTFT、E2E、流式间隔、实际输出长度 | 用户是否等太久、是否截断 |
| 引擎 | 活动/等待请求、KV占用、缓存命中 | 调度与缓存是否达到预期 |
| 设备 | 内存、计算、带宽相关观测、功耗、温度、频率 | 内存不足、降频、设备争用 |
| 主机 | 可用内存、RSS/PSS、swap、CPU、磁盘、网络 | CPU回退、换页、下载与通信问题 |

统计维度至少保留模型和配置版本、输入输出长度组、测试阶段。只看平均值容易掩盖尾延迟；只看 GPU 百分比无法判断服务健康。

日志默认避免保存完整用户输入。排错需要内容时使用获得授权的样例，设定保留范围；公开证据重新检查正文、命令和截图，不直接复制运行目录。

## 5.9 稳定性与故障恢复验收

先定义需要持续多久、允许多少失败、内存是否应回落、温度与性能如何判断。具体阈值随任务与设备确定。

推荐观察：长短输入交替；短时间突发后恢复；客户端取消；请求超时；正常停止重启；一次合法长输入触及资源边界。避免对共享机器做破坏性资源耗尽实验。

每次失败保存首次异常、配置和资源状态。后续级联错误不一定是根因。恢复后复跑最小请求和原失败输入，确认既恢复服务也解决触发条件。

## 5.10 公开项目和知识库怎样衔接？

工程仓库存能运行的材料；知识库解释原因和适用条件。知识条目链接固定版本的实现与结果，工程 README 链接对应知识章节，避免复制多份已经不一致的命令。

模型权重通常留在模型托管平台，仓库记录公开下载与 revision；自有代码、文档、样例、脱敏日志和合理大小的结果放 Git。外部模型、图和数据逐项注明来源与许可，自有文档许可不能替代模型许可。

公开前检查文本、JSON、Notebook输出和图片。图片即使只是终端，也可能带有账号、地址或密钥；无法可靠清理的截图用重新执行的公开样例替换，不能伪造成功日志。

## 5.11 本层验收与最终结论

交付者应能从干净目录完成环境准备、模型获取、启动、一次正确请求、目标负载测试和停止。结果既包含通过项，也包含已知失败和未测项。

例如 Intel 工程可以交付为“指定版本的 IR GPU 文本生成可用，NPU 两条路线未通过；短生成性能已记录，完整答案质量与持续负载待补”。这样下一位使用者知道可用入口与剩余工作。

项目记录使用[第四部分模板](../04-project-review.md)，知识归档方式见[第五部分](../05-knowledge-base.md)。
