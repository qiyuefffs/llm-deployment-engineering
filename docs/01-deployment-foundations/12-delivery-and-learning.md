# 12 工程交付、运行维护与能力建设

[返回总目录](README.md) · [上一章](11-parallel-and-scaling.md) · [下一章](13-glossary-and-references.md)

## 1. 一个项目至少沉淀七项结果

| 交付项 | 应包含的细节 | 完成标准 |
| --- | --- | --- |
| 硬件环境 | 型号、OS、驱动、Runtime、CPU/RAM、拓扑与功耗状态 | 其他人能判断环境差异 |
| 模型信息 | 仓库/revision、架构、量化、哈希、模板、许可证 | 能获得同一模型并核对身份 |
| 框架选择 | commit/包版本、后端、候选与理由 | 明确兼容范围与取舍 |
| 部署方案 | 目录、依赖、构建、启动/停止、端口与接入 | 按顺序可建立服务 |
| 参数配置 | 上下文、并发、batch、KV、采样与有效默认 | 文字、命令与实际日志一致 |
| 验收结果 | 输入、质量、性能、异常、稳定性与原始记录 | 可独立重算并判断是否达标 |
| 问题与结论 | 根因证据、优化代价、限制、回滚 | 故障可重现，变更可撤回 |

一份只保留启动命令的交付依赖作者记忆。把命令、配置、版本和验收材料关联起来，才便于升级、迁移和多人维护。

## 2. 推荐的交付目录

以下为新项目目录模板，不要求改动本仓库现有 Case：

```text
edge-llm-release/
├── README.md                  入口、适用设备与执行顺序
├── environment/               OS/驱动/包锁定、构建与版本记录
├── model-manifest/             来源、revision、哈希、模板与许可证
├── config/                     服务参数与不含密钥的配置
├── bin-or-image-manifest/      二进制/镜像摘要、运行库清单
├── inputs/                     可公开或脱敏的验收样例
├── validation/                 质量、异常、性能与稳定性规则
├── results/                    逐请求记录、日志、采样与汇总
└── operations/                 启停、监控、排障、升级与回滚
```

不要把模型权重、编译缓存、私人日志和密钥直接提交到普通代码仓库。模型按许可证使用模型托管或受控存储；代码仓库记录可获取地址和哈希。大文件下载可用 aria2，但授权、版本和校验仍需独立说明。

## 3. 环境封装与可复建性

源码项目记录 commit、子模块、构建参数和编译器；Python 项目在独立环境安装并保存精确依赖；容器记录镜像 digest、启动参数和宿主驱动要求。`latest`、可变网页链接和一张 `pip list` 截图不足以说明完整环境。

锁定依赖后，仍需在干净环境走一次安装和验收；锁文件不能保证硬件、系统库和模型都相同。离线交付应提前准备合法可分发的依赖、运行库、权重获取办法和校验值，断网检查是否还隐式拉取 tokenizer、模板或编译组件。

不要公开复制整个环境变量或个人 shell 历史。必要环境变量采用占位符与配置说明，真实凭证通过部署平台的秘密管理机制注入。模型与外部代码许可证也应随包保留，尤其是重新分发量化制品时。

## 4. 服务生命周期与就绪检查

存活检查判断进程或接口是否响应；就绪检查判断目标模型是否加载并能接收任务；业务验收进一步检查模板与所需能力。只探测 TCP 端口不能证明模型已就绪。启动耗时较长时应向调用端返回清楚状态，不通过无限重试掩盖启动问题。

停止服务要让新请求停止进入，已有请求在时限内完成或收到可理解错误，再释放资源。客户端取消应传播到生成任务，避免人已关闭页面而设备仍持续输出。端侧还要验证退出应用、休眠和恢复后的状态。

常驻 Linux 主机可以使用进程管理器；下方是 **systemd 结构模板**，假设管理员已准备 `llm` 用户、对应目录、可执行文件、驱动和访问权限。没有在本章安装或启动它；根据实际模型容量调整命令，Notebook 未必提供 systemd。

```ini
[Unit]
Description=Local edge LLM service
After=network.target

[Service]
Type=simple
User=llm
WorkingDirectory=/opt/edge-llm
ExecStart=/opt/edge-llm/bin/llama-server -m /srv/models/model.gguf --alias edge-model --host 127.0.0.1 --port 8080 -c 4096 -np 1 -ngl 99 --metrics
Restart=on-failure
RestartSec=5
TimeoutStopSec=30
KillSignal=SIGINT

[Install]
WantedBy=multi-user.target
```

服务注册前先在相同账号和工作目录前台验证；运行时库、模型读取权限、缓存目录与设备权限都应核对。systemd 只能管理生命周期，不会替你解决框架兼容或业务就绪。

## 5. 接入、权限与资源控制

开发先用本地回环地址；局域网/外部接入通过环境允许的入口配置鉴权、传输保护、请求大小、上下文、输出上限、并发、排队和超时。公开页面显示一个 URL 不等于模型服务已正确获得这些限制。

模型输出工具调用参数时，应用验证 schema、路径和权限后再执行；LLM 不是授权系统。输入文档里的指令也不应获得系统权限。涉及本地文件或工具能力的服务，只开放实际业务需要的能力，并有明确用户授权。

这类控制也直接影响性能：无界排队会放大尾延迟，无输出限制会占满槽位，无取消会浪费能耗。拒绝或限流应有明确错误，客户端按总时限退避，不制造重试风暴。

## 6. 监控要把用户、服务和设备连起来

用户层看首个可见答案、完成时间、任务正确率；服务层看请求量、成功率、队列、活跃序列、KV、抢占、缓存；设备层看内存、CPU/GPU 活动、温度、频率与功耗。使用 request/run ID 关联，避免只看 GPU 图表。

llama-server 可按版本启用 `--metrics`，vLLM 等也提供指标端点。Prometheus/Grafana 用于采集和展示，具体指标名随版本保存；不能凭教程某个名称写死后不检查。高频、细粒度日志会影响性能，线上采样与脱敏策略也应说明。

告警与用户影响绑定：队列持续增长、延迟超门槛、内存逼近峰值、错误率上升、温控后性能下降。只对 GPU utilization 低告警，可能在空闲时产生大量无意义提示。

## 7. 发布与回滚

发布前把模型、模板、引擎、配置作为一个版本集合验收。即使只换 tokenizer 或模板，输出 token 数与缓存也可能变化；不能当成无需回归的文档调整。

先在候选实例跑固定正常/异常/质量样例和目标负载，再小范围切换。保留上一版本模型与配置的可恢复引用，不把可变下载链接当作回滚备份。回滚后检查服务就绪、质量和容量，不只检查进程重新启动。

桌面/移动设备增加模型包损坏校验、磁盘不足、升级中断与用户主动取消测试。下载中间文件与正式模型分开，完整校验通过后再让应用使用，避免把半个 GGUF 当成发布成功。

## 8. 按现有经验继续建立能力

本仓库已有 llama.cpp、Q4、GPU Notebook 与性能对照实践，下一步应把隐含操作变为可复用证据，而不是立刻堆更多框架名。建议用五个阶段形成学习闭环：

| 阶段 | 练习 | 验收产物 |
| --- | --- | --- |
| 单设备正确部署 | 固定模型与引擎，短/长/多轮和 API 验证 | 环境、模型清单与功能报告 |
| 内存与容量 | 手算 KV，比较日志，找上下文/并发边界 | 预算与峰值解释 |
| 严格性能优化 | 一次一个假设，保留原始记录与质量 | 可重算的对照报告 |
| 第二种终端/后端 | 重用样例与口径，重新做兼容矩阵 | 迁移差异与未支持项 |
| 工程交付 | 干净环境、离线、重启、监控、回滚 | 其他人可独立运行的发布包 |

只有业务需要时再进入 TP/EP、多节点或 P/D 分离；它们有明确适用条件，并非掌握端侧部署的前置门槛。

## 9. 项目复盘与知识库维护

每个项目按“约束 → 选型 → 最小运行 → 基线 → 瓶颈 → 实验 → 验收 → 限制”整理。比如某参数提高了吞吐，记录中应同时说明输出长度、并发、尾延迟与质量，让后续维护者能够核对改动效果。

每个知识点按“它是什么、解决什么问题、作用在哪个阶段、适用条件、如何验证、失败代价、证据来源”记录。没有做过的平台写为官方资料整理或待验证计划；已经做过的记录精确设备、版本和日志。
