## Overview of this chapter

Multi-device deployments typically have two objectives: a single device cannot be deployed, or a single copy of a service cannot be deployed. The former requires cutting or offloading, while the latter may be suitable for multiple copies. The goal is to select TP, PP, DP, EP or RPC instead of connecting all devices.

This chapter is based on the RPC record of the dual RTX 4080 container, multi-node barrier and AMD five-machine FlowUs. Historical results are used to explain the actual problem, not to run successful multi-node circuits.

## 1. Differences between different ways of parallelism

TP divides the tensor computation in layers into multiple devices, often producing communication in each layer; PP allocates the model phase to different devices, passing the activation between the phases; DP deploys multiple copies of independently processed requests; MoE's EP Distribution expertise includes routing and communication. Specific combinations are constrained by models, frameworks and devices.

TP is not necessarily equal to the number of single-machine GPUs, and PP is not necessarily equal to the number of nodes. These are candidate mapping methods, which ultimately look at single-GPU capacity, layers, operators, interconnected bandwidth, workload, and flowing waterline bubbles. On-device network slow capacity expansion is likely to be successful, while single-request latency is higher.

Two 16GB cards cannot be used unconditionally as a 32GB card. Weights, KVs, workspace and communication buffers need to be ranked by budget. A single uncut tensor, extra expense or uneven layer allocation of a rank, may trigger OOM first.

## 6. What is the comparison of multi-device performance?

Keep the baseline of a single device or minimal configuration, and then record the number of devices, cuts, total resources, input, output, concurrency, actual tokens and quality. If the model precision is also changed, the benefit is that the configuration changes as a whole cannot be attributed to the device number alone.

Online services also require multiple single-GPU copies compared to a multi-GPU copy. When a single-GPU can be turned off, the DP may increase the total request capacity. When the model can't be dropped, the capacity must be addressed. In the end, however, the effective throughput to meet the latency target remains to be seen, rather than the overall utilization rate of the GPU.

## 7. The order of failure closure

## How to gradually narrow the scope of control success and model failure

### 9.1 Resources not enough or worker not registered

Compare the expected resources of the GPU and Ray, verify the visible device and worker logs of the container environment. Continuing to reduce the model length does not automatically make the GPU appear when a node is only registered with the CPU. The resources table correctly reviews whether placement is waiting and whether there is another occupation.

### 9.2 Model path is the same

The head process can read the model, not the remote worker. Check each node's uploads, file permissions, shard indexes and summaries. The safetensors are broken down into multiple files that only change the disk structure, and the TP/PP runtime still needs to read their respective tensors from a complete logical model.

### 9.3 Whether environmental variables are transmitted to the worker

Variables in the head-terminal settings do not necessarily enter the remote-ray process that has already been started. Device selection, communication Network cards and library paths should be specified in each worker's startup environment or controlled runtime configuration. When checking the actual worker environment, only the necessary technical fields are output to avoid the entire environment being transferred to the credentials.

### 9.4 Which paragraphs can only be verified with a dummy load

Fixed version supports dummy load, which temporarily bypasses real weights of I/O, to help determine if initialization, graphics and communication are still failing. But it doesn't verify model files, real weights precision or task quality. After the dummy passed, the real load was changed and the single request acceptance testing continued, and the dummy throughput could not be used as the model score.

### 9.5 See the first worker error

The API eventually displays EngineDead or overtime, usually with an upstream worker having previously failed. Check the first error of each rank by time, distinguish between weights allocation, communication initialization, warmup/kernel and input execution. Save versions, rank, device, and inputs before and after the error to create minimal reproduction.

Multi-node is a final controlled failure: a worker withdraws from a dedicated test service, records the return of the request being run, changes in the health of the main service, resources release and recovery steps. ## 11 When should multiple copies be preferred?

The model can run correctly on a single device, allowing multiple copies of the request to be independent of each other, and reducing the need for some cross-device communication. The cost is to replicate the weights with their respective KVs. When a single device cannot be dropped, the capacity is first cut, and when necessary, more copies are expanded.

Comparing two single-GPU and one dual-GPU copies with the same total hardware, the same quality model, the same input and output, and the same SLO. Total GPU utilization, single request minimum latency and service efficient throughput may refer to different schemes. The conclusion should go back to project constraints, rather than considering the number of device sequences as the degree of optimization.
